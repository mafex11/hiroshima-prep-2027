Part 5: Maths

Chapter 19 of 45

The math inside your research plan

When and how long: Days 1 to 3. The most likely maths questions.

This file works through every formula in your submitted research plan, step by step, so you can derive each one on paper while you talk. The Q&A will mostly be about your plan, so this file comes first in your revision.

It builds on 01_reliability_and_probability_primer.md sections 2 to 5 (read those first, they are short). This file goes one level deeper: the derivations, the conditions behind them, and the honest limits.

How the answers were checked. Every number in this file was recomputed on 12 Nov 2026 with Python (numpy, scipy, sympy). The plan's formulas were also checked by simulation: 2 million simulated inputs with 10 beta-binomial runs each, a beta-binomial maximum likelihood fit, a two-setting simulation, and a toy fault model for the bootstrap. The table at the end of the derivations shows formula against simulation. Items marked [CHECK] are points I am not fully sure of, or design choices to confirm with Prof. Zheng.

Notation (plain text).

  • theta_s(x): the chance that one run from setting s fails on input x. A setting is one task, one context file, one agent, one model, one temperature.
  • X: a random input from your input generator. p_s = E[theta_s(X)]: the mean failure probability of one run.
  • k: runs per input in your data (10 in the plan). J: how many of the k runs fail on one input.
  • B(a, b) = Gamma(a) Gamma(b) / Gamma(a + b), the beta function. C(n, j) = n! / (j! (n - j)!).
  • Vote "fails" means at least half of the runs plus one fail (for N = 3, at least 2).

Your model in one paragraph (memorise this).

"For each input, I treat the chance that a run fails as a number theta between 0 and 1. It differs from input to input, so I model it with a Beta distribution. Then the number of failing runs on one input is beta-binomial. Its intraclass correlation rho is 1 over (a + b + 1), and rho = 0 means the runs fail independently. From the fitted model I get the chance that two runs both fail, the chance that a majority vote fails for any N, and the best N for a given cost. I take intervals from a bootstrap that resamples runs, because the same runs meet every input."

D1. Two runs both fail: E[theta(X)^2] = p^2 + Var theta(X) (Eckhardt and Lee)

Setup. Draw an input X. Draw two runs R1 and R2 independently from the same setting.

Derivation.

Step 1. Fix the input x. The two runs are independent draws, so
        P(both fail | X = x) = theta(x) * theta(x) = theta(x)^2.
Step 2. Average over inputs (law of total probability):
        P(both fail) = E[ theta(X)^2 ].
Step 3. By the definition of variance, Var theta(X) = E[theta^2] - (E[theta])^2, so
        E[theta(X)^2] = p^2 + Var theta(X).
Step 4. Independence would mean P(both fail) = P(R1 fails) P(R2 fails) = p * p = p^2.
        This holds only if Var theta(X) = 0, that is theta(x) = p for (almost) every input.

The key idea. Given the input, the runs are independent. On a random input they are not, because both runs meet the same input, and some inputs are harder than others. Conditional independence is not independence. Eckhardt and Lee [11] called theta(x) the "intensity of coincident errors".

Example. Beta(0.5, 4.5) inputs (used throughout this file): p = 0.1, Var theta = 0.015. P(both fail) = 0.01 + 0.015 = 0.025, which is 2.5 times the independent value 0.01. Simulation: 0.0251.

Say it.

"Given the input, two runs fail independently, each with chance theta of x, so both fail with theta squared. Averaging over inputs gives E of theta squared, which is p squared plus the variance of theta. So they fail together more often than p squared unless every input is equally hard, which is the Eckhardt and Lee result."

Follow-ups.

  • Is this Jensen's inequality? Yes. x^2 is convex, so E[theta^2] >= (E theta)^2, with equality only when theta is constant.
  • Can P(both fail) be less than p^2 for one setting? No, because Var theta >= 0. For two different settings it can (D7).

D2. The Beta distribution: mean and variance

Density. f(theta) = theta^(a-1) (1 - theta)^(b-1) / B(a, b), for 0 < theta < 1, with a > 0, b > 0.

The one trick you need. Multiplying by theta^r just raises a by r, so

E[theta^r] = B(a + r, b) / B(a, b).
Use B(a, b) = Gamma(a) Gamma(b) / Gamma(a + b) and Gamma(z + 1) = z Gamma(z):

r = 1:  E[theta]   = Gamma(a+1) Gamma(a+b) / ( Gamma(a) Gamma(a+b+1) ) = a / (a + b)
r = 2:  E[theta^2] = a (a + 1) / ( (a + b)(a + b + 1) )
r = 3:  E[theta^3] = a (a + 1)(a + 2) / ( (a + b)(a + b + 1)(a + b + 2) )

Var theta = E[theta^2] - (a/(a+b))^2
          = [ a(a+1)(a+b) - a^2 (a+b+1) ] / ( (a+b)^2 (a+b+1) )
          = a [ a^2 + ab + a + b - a^2 - ab - a ] / ( (a+b)^2 (a+b+1) )
          = a b / ( (a + b)^2 (a + b + 1) )
          = p (1 - p) / (a + b + 1),       where p = a / (a + b).

Example. Beta(0.5, 4.5): p = 0.1, Var = 0.09 / 6 = 0.015, sd = 0.122, E[theta^2] = 0.75/30 = 0.025, E[theta^3] = 1.875/210 = 0.008929.

Shapes to know. Beta(1, 1) is uniform. a < 1 piles mass near 0 (most inputs easy, a few hard), which is what you expect for code. Large a + b squeezes theta close to p.

Why Beta for theta. It lives on [0, 1]. Its two parameters set the mean and the spread separately. It is conjugate to the binomial, so the count of failing runs has a closed-form distribution (D3).

Say it.

"The mean of a Beta(a, b) is a over a plus b. The variance is p times 1 minus p, divided by a plus b plus 1, so a plus b works like a precision: the bigger it is, the closer every input's theta is to p."

D3. The beta-binomial: pmf, mean and variance

Setup. On one input, J = number of failing runs among k. Given theta, J ~ Binomial(k, theta). theta ~ Beta(a, b).

pmf.

P(J = j) = integral_0^1 C(k,j) theta^j (1-theta)^(k-j) * theta^(a-1) (1-theta)^(b-1) / B(a,b) dtheta
         = C(k,j) / B(a,b) * integral_0^1 theta^(j+a-1) (1-theta)^(k-j+b-1) dtheta
         = C(k,j) B(j + a, k - j + b) / B(a, b).

Mean. Law of total expectation: E[J] = E[ E[J | theta] ] = E[k theta] = k p.

Variance. Law of total variance:

Var J = E[ Var(J | theta) ] + Var( E[J | theta] )
      = E[ k theta (1 - theta) ] + Var( k theta )
      = k (p - E[theta^2]) + k^2 Var theta
      = k (p - p^2 - Var theta) + k^2 Var theta
      = k p (1 - p) + k (k - 1) Var theta
      = k p (1 - p) [ 1 + (k - 1) rho ],      with rho = Var theta / ( p (1 - p) ).

The binomial variance is k p (1 - p). The factor [1 + (k - 1) rho] is the overdispersion.

Examples (Beta(0.5, 4.5)).

  • k = 3: P(J = 0, 1, 2, 3) = 0.7661, 0.1768, 0.0482, 0.0089. So P(J >= 2) = 0.0571.
  • k = 10: Var J = 10 * 0.09 * (1 + 9/6) = 2.25, against 0.9 for a binomial. P(J = 0) = 0.547, against 0.349 for a binomial. Dependence gives more inputs where no run fails, and more inputs where many fail. Simulation: Var J = 2.252.

Say it.

"Given theta, the count is binomial. Integrating theta out against the Beta gives C of k, j times B of j plus a, k minus j plus b, over B of a, b. The mean is k p, and the variance is the binomial one times 1 plus (k minus 1) rho, so any rho above zero spreads the counts out."

D4. The intraclass correlation rho = 1 / (a + b + 1)

Derivation. Let F_i = 1 if run i fails on the input, 0 if not. For two different runs i and j:

E[F_i F_j] = P(both fail) = E[theta^2]                 (D1)
Cov(F_i, F_j) = E[theta^2] - p^2 = Var theta
Var(F_i) = p (1 - p)                                   (a Bernoulli with mean p)
Corr(F_i, F_j) = Var theta / ( p (1 - p) ) = rho
For the Beta: Var theta = p (1 - p) / (a + b + 1), so rho = 1 / (a + b + 1).

What rho means, three ways.

  1. The correlation between two runs' fail/pass results on the same random input.
  2. The share of a single run's failure variance that comes from differences between inputs: p(1 - p) = Var theta + E[theta(1 - theta)], and rho = Var theta / (p(1 - p)).
  3. rho = 0: theta is the same for every input, so runs fail independently. rho = 1: theta is 0 or 1, so on each input either all runs fail or none do, and voting cannot help at all.

Values. a + b = 1 gives rho = 0.5. a + b = 5 gives 1/6. a + b = 20 gives 0.048. a + b = 100 gives 0.0099.

Using (p, rho) instead of (a, b). a = p (1 - rho) / rho and b = (1 - p)(1 - rho) / rho. Example: p = 0.1, rho = 1/6 gives a = 0.5, b = 4.5. Fitting in (p, rho) is easier to explain, because p is "how often one run fails" and rho is "how much they fail together".

Design effect. With k = 10 and rho = 1/6, the factor 1 + (k - 1) rho = 2.5. Ten runs on one input tell you as much about p as about 4 independent runs would.

Link to Ron et al.'s pairwise phi [5]. Their phi is the correlation, across inputs, between two fixed versions' failure vectors. That is related but not the same. Averaged over random pairs of runs, the pairwise covariance equals Var theta, so the average phi is close to rho when runs have similar failure rates. [my derivation; a check, not a claim from their paper]

Say it.

"rho is the correlation between two runs' failures on the same input. For the beta-binomial it is 1 over a plus b plus 1. Zero means they fail independently. One means that on each input either every run fails or none does, so voting is useless."

D5. The 2-out-of-3 vote: E[3 theta^2 - 2 theta^3]

Derivation.

Given theta, J ~ Binomial(3, theta). The vote is wrong when J >= 2:
P(J >= 2 | theta) = C(3,2) theta^2 (1 - theta) + theta^3
                  = 3 theta^2 - 3 theta^3 + theta^3
                  = 3 theta^2 - 2 theta^3.
Average over inputs: P(vote fails) = E[3 theta^2 - 2 theta^3] = 3 E[theta^2] - 2 E[theta^3].
Independent case (theta = p on every input): 3 p^2 - 2 p^3 = 3 p^2 (1 - p) + p^3.

Numbers.

  • Independent, p = 0.1: 3(0.01) - 2(0.001) = 0.028.
  • Beta(0.5, 4.5): 3(0.025) - 2(0.008929) = 0.0571. That is about twice the independent value, but still better than one run (0.1). Simulation: 0.0574.

When voting hurts. On one input, the gain from voting is

theta - (3 theta^2 - 2 theta^3) = theta (1 - 3 theta + 2 theta^2) = theta (1 - theta)(1 - 2 theta).

This is positive only when theta < 1/2. On inputs where most runs fail, the vote is worse than a single run. The total gain is E[theta (1 - theta)(1 - 2 theta)] (0.1 - 0.0571 = 0.0429 in the example).

Honest note on "fails". The formula counts the vote as wrong whenever 2 of 3 runs fail. If the two wrong runs give different wrong outputs, there is no majority, and a voter could detect that. So the formula is slightly pessimistic. In code, runs that fail on the same input can give the same wrong output (the shared-helper case), so I keep the simple version and say so. I could also count how often the wrong outputs match, since I record every output.

Say it.

"On one input, the vote fails if two or three of the three runs fail: 3 theta squared times 1 minus theta, plus theta cubed, which is 3 theta squared minus 2 theta cubed. Averaging gives E of 3 theta squared minus 2 theta cubed. With independence and p = 0.1 that is 0.028. With my example Beta it is 0.057."

D6. Majority of N runs

Formula. N = 2m + 1 (odd). The vote fails when J >= m + 1.

P_N = E[ sum_{j=m+1}^{N} C(N,j) theta^j (1 - theta)^(N-j) ]
    = sum_{j=m+1}^{N} C(N,j) B(j + a, N - j + b) / B(a, b)      (upper tail of a beta-binomial)

Table (Beta(0.5, 4.5) against independent p = 0.1).

N P_N with dependence P_N if independent
1 0.1000 0.1000
3 0.0571 0.0280
5 0.0424 0.00856
7 0.0352 0.00273
9 0.0309 0.00089
11 0.0281 0.00030
21 0.0219 0.0000014
101 0.0164 about 1e-24

The floor. As N grows, J / N tends to theta (law of large numbers). So a very large vote fails exactly on the inputs where theta > 1/2:

P_N  ->  P( theta(X) > 1/2 )      (= 0.0150 for Beta(0.5, 4.5))

Under independence P_N goes to 0. With dependence it cannot go below the share of inputs where most runs fail.

Say it.

"For N runs the vote fails when more than half fail, so P_N is the upper tail of the beta-binomial. As N grows it does not go to zero. It goes to the share of inputs where theta is above one half, which is about 1.5 percent in my example."

D7. Two settings a and b: P(both fail) = p_a p_b + Cov(theta_a, theta_b)

Derivation.

Run A from setting a, run B from setting b, same input x. They are independent given x, so
P(both fail | x) = theta_a(x) theta_b(x).
P(both fail) = E[theta_a(X) theta_b(X)] = E[theta_a] E[theta_b] + Cov(theta_a, theta_b)
             = p_a p_b + Cov(theta_a, theta_b).

This is the Littlewood and Miller (1989) extension of Eckhardt and Lee. With one setting, the covariance is Var theta, which is never negative. With two settings it is smaller when the settings find different inputs hard, and in principle it can be negative.

Example (same p, different hard inputs). 90% of inputs are easy (theta_a = theta_b = 0.02). 5% are hard for a only (theta_a = 0.6, theta_b = 0.1). 5% are hard for b only (theta_a = 0.1, theta_b = 0.6).

p_a = p_b = 0.9(0.02) + 0.05(0.6) + 0.05(0.1) = 0.053
E[theta_a^2]       = 0.9(0.0004) + 0.05(0.36) + 0.05(0.01) = 0.01886   (two runs from a)
E[theta_a theta_b] = 0.9(0.0004) + 0.05(0.06) + 0.05(0.06) = 0.00636   (one from a, one from b)
p^2 = 0.002809,  Var theta_a = 0.01605,  Cov(theta_a, theta_b) = 0.00355

Mixing settings cuts the joint failure from 0.0189 to 0.0064, though each run alone is just as good. Simulation: 0.0189 and 0.0063.

Votes over mixed runs. For three runs with theta_1, theta_2, theta_3 on one input:

P(at least 2 fail) = t1 t2 (1 - t3) + t1 t3 (1 - t2) + t2 t3 (1 - t1) + t1 t2 t3
                   = t1 t2 + t1 t3 + t2 t3 - 2 t1 t2 t3.
(With t1 = t2 = t3 = theta this gives 3 theta^2 - 2 theta^3, as in D5.)

In the example: vote over (a, a, a) fails with 0.0349; over (a, a, b) with 0.0274. The independence prediction 3p^2 - 2p^3 = 0.0081 is far too low for both.

In RQ1. For each change between runs (file version, agent, model, temperature) you estimate Cov(theta_a, theta_b) and ask which change lowers it most. A model-free estimate of E[theta_a theta_b] is the average over inputs of (J_a / k_a)(J_b / k_b), because runs in different settings are independent given the input.

Say it.

"For one run from each of two settings, both fail with p_a times p_b plus the covariance of their thetas. If the two settings find different inputs hard, the covariance is small, so diversity helps. RQ1 asks which change between runs lowers that covariance the most."

D8. Choosing odd N to minimise c_run N + c_fail P_N

Setup. c_run = cost of one run. c_fail = cost of shipping a wrong change. Cost C(N) = c_run N + c_fail P_N, for odd N only (odd N avoids ties).

Method. Compute P_N from the fitted (a, b) for N = 1, 3, 5, ..., say up to 21. Evaluate C(N). Take the smallest. The marginal rule: going from N to N + 2 is worth it only if c_fail (P_N - P_{N+2}) > 2 c_run.

Example (c_run = 1, so costs are in "runs").

N C(N), dependence, c_fail = 100 C(N), independent, c_fail = 100 C(N), dependence, c_fail = 1000 C(N), independent, c_fail = 1000
1 11.00 11.00 101.0 101.0
3 8.71 5.80 60.14 31.00
5 9.24 5.86 47.41 13.56
7 10.52 7.27 42.16 9.73
9 12.09 9.09 39.88 9.89
11 13.81 11.03 39.08 11.30
13 15.61 13.01 39.11 13.10

Reading it. With c_fail = 1000, the independence model says "use 7 runs, expected cost 9.73". With dependence, 7 runs really cost 42.16, more than four times as much, and the best choice is 11 runs. Dependence changes the best N and, more, the cost you should expect.

Say it.

"For each odd N I compute the vote failure from the fitted beta-binomial, multiply by the cost of a failure, add N times the cost of a run, and take the smallest. In my example, assuming independence picks 7 runs and expects a cost four times too low."

D9. Estimates that need no Beta assumption

The Beta is a model. You can estimate P(two fail) and the 2-of-3 vote directly from the counts.

Factorial moment of a binomial: E[J(J - 1) | theta] = E[J^2] - E[J]
                              = (k theta(1 - theta) + k^2 theta^2) - k theta = k(k - 1) theta^2.
So  mean over inputs of J(J - 1) / (k(k - 1))              estimates E[theta^2] without bias.
And mean over inputs of J(J - 1)(J - 2) / (k(k - 1)(k - 2)) estimates E[theta^3].
Vote 2-of-3: mean of 3 J(J-1)/(k(k-1)) - 2 J(J-1)(J-2)/(k(k-1)(k-2)).

This equals the vote failure averaged over all C(k, 3) triples of your k runs. Simulation (k = 10, Beta(0.5, 4.5)): 0.02497, 0.00889 and 0.05712, against true 0.025, 0.00893 and 0.05714.

You still need the Beta (or another model) to go beyond your data: P_N for N > k (N = 21 when you ran 10), and the floor P(theta > 1/2). Comparing the model-free numbers with the fitted model is also a check of fit.

Say it.

"I don't have to trust the Beta for the basic numbers. The average of J times J minus 1 over k times k minus 1 is an unbiased estimate of the chance that two runs both fail. I need the model only to predict votes larger than the number of runs I have."

D10. Maximum likelihood for the beta-binomial

What is maximised. Data: n inputs, J_i failing runs out of k on input i.

log L(a, b) = sum_{i=1}^{n} [ log C(k, J_i) + log B(J_i + a, k - J_i + b) - log B(a, b) ]

Maximise over a > 0 and b > 0 (or over p in (0, 1) and rho in (0, 1)).

Why numerical. The score equations involve the digamma function psi (the derivative of log Gamma):

d logL / da = sum_i [ psi(J_i + a) - psi(k + a + b) ] - n [ psi(a) - psi(a + b) ] = 0
d logL / db = sum_i [ psi(k - J_i + b) - psi(k + a + b) ] - n [ psi(b) - psi(a + b) ] = 0

They have no closed-form solution, so you solve them with Newton-Raphson, or maximise log L directly (for example Nelder-Mead on log a and log b, which keeps both positive).

Starting values from the method of moments.

p0   = sum J_i / (n k)
s^2  = sample variance of the J_i
rho0 = ( s^2 / (k p0 (1 - p0)) - 1 ) / (k - 1)      (from Var J = k p(1-p)[1 + (k-1) rho])

Simulation check. 400 inputs, k = 10, true a = 0.5, b = 4.5 (p = 0.1, rho = 0.167). MLE: a = 0.476, b = 4.551, so p = 0.095 and rho = 0.166. Method of moments: rho = 0.161.

Things to say if asked.

  • If the data show no overdispersion, rho goes to 0 and the fit goes to the edge (a + b tends to infinity): the binomial. A test of rho = 0 is then on the boundary (see 03_statistics.md S25).
  • Inputs with J = 0 still count. Most inputs may have J = 0. If there are more zeros than the Beta allows, a zero-inflated beta-binomial (a share pi of inputs that no run fails, plus a beta-binomial) may fit better.
  • The likelihood treats the J_i as independent across inputs. Over repeated experiments they are not, because the same k runs produce every row. So I use the MLE as the point estimate, but I do not trust the standard errors from its curvature. The real uncertainty comes from having only k runs, which is why the intervals come from a bootstrap over runs (D11).

Say it.

"I maximise the sum over inputs of log C(k, J_i) plus log B(J_i + a, k - J_i + b) minus log B(a, b). The score equations have digamma functions and no closed-form solution, so I maximise it numerically, starting from the method of moments."

D11. Why the bootstrap resamples runs, not inputs

The data. A matrix F with one row per input (10,000 or more) and one column per run (10). F = 1 if that run fails on that input.

The independent units are runs. Each run is an independent draw from the setting. The rows are independent only once you hold the 10 runs fixed. Over repeated experiments, one bug in one run makes it fail on a whole region of inputs, so many rows move together. If you resample rows, you treat the 10 runs as fixed and measure only the noise from sampling inputs, which is tiny with 10,000 inputs. You miss the bigger noise: you only saw 10 programs from the setting.

Run bootstrap. Draw 10 column numbers with replacement. Build F* from those columns. Recompute the statistic (p, rho, P_3, best N). Repeat B = 2,000 times. The 2.5% and 97.5% percentiles give a 95% percentile interval.

Simulation check (toy fault model). 40 possible faults, each with a failure region of inputs. Each run contains each fault with chance 0.15. 10 runs, 5,000 inputs, 400 repeated experiments:

Standard deviation of the estimate of p Value
True (over 400 repeated experiments) 0.0108
Bootstrap over runs (average of 30 data sets) 0.0101
Bootstrap over inputs (average of 30 data sets) 0.0018

Resampling inputs gives intervals about 6 times too narrow. Resampling runs is close to the truth.

Honest limits.

  • With 10 runs there are only 10 units, so the intervals are rough and may be a little too narrow (by about sqrt(9/10) for a mean).
  • If a run is drawn twice, the copy agrees with itself on every input, which inflates pair statistics such as rho. One fix is to compute pair statistics only over pairs of different original runs. [CHECK: my suggestion, to discuss with Prof. Zheng]
  • A two-way bootstrap that resamples both runs and inputs (Owen's "pigeonhole bootstrap", 2007) is another option for crossed data like this. [CHECK: reference from memory]
  • Nonparametric (resample observed runs) against parametric (simulate new data from the fitted model): the lab's NHPP papers use a parametric bootstrap. I resample runs because I do not want to trust the Beta model to describe how failures cluster across inputs.

Say it.

"The same ten runs meet every input, and one bug fails a whole region of inputs, so ten thousand rows are not ten thousand independent pieces of evidence. The runs are the independent units, so I resample runs. In a small simulation, resampling inputs gave intervals about six times too narrow."

D12. The Knight and Leveson z statistic (baseline, from Ron et al. [5])

Definitions. N versions, T test inputs, f_i = failures of version i, p_i = f_i / T. Under H0 (versions fail independently):

P0 = prod_i (1 - p_i)                              no version fails
P1 = sum_i p_i prod_{j != i} (1 - p_j)             exactly one fails
Pm = 1 - P0 - P1                                   two or more fail
K  = number of inputs on which two or more versions fail (observed)
Under H0, K ~ Binomial(T, Pm), approximately Normal with mu = T Pm and sigma^2 = T Pm (1 - Pm).
z  = (K - mu) / sigma.     Ron et al. reject at 99% when |z| > 2.576.

Small example (do this one on paper). Three versions with p = 0.01, 0.02, 0.01. T = 10,000.

P0 = 0.99 * 0.98 * 0.99 = 0.960498
P1 = 0.01(0.98)(0.99) + 0.02(0.99)(0.99) + 0.01(0.99)(0.98) = 0.009702 + 0.019602 + 0.009702 = 0.039006
Pm = 1 - 0.960498 - 0.039006 = 0.000496
mu = 4.96,  sigma = sqrt(4.96 * 0.999504) = 2.227
If K = 30:  z = (30 - 4.96) / 2.227 = 11.2   -> reject independence.

Ron et al.'s numbers. T = 1,000,000, mu = 115.36, K = 429: z = 313.64 / sqrt(115.36 * 0.99988) = 313.64 / 10.74 = 29.20. This matches their Table III.

Why it is only a baseline.

  • It is a yes or no test. It says whether there is dependence, not how much, and gives no model for votes or for N.
  • When mu is small (4.96 above), the normal approximation is rough. An exact binomial or Poisson tail is better.
  • It treats the estimated p_i as known.
  • It pools all versions, so it cannot say which change between runs lowers dependence.

Say it.

"Knight and Leveson compute, from each version's failure rate, how many inputs should make two or more versions fail if they were independent, and compare that with the observed count in a z statistic. It tells me whether there is dependence. rho tells me how much, and lets me predict votes, so I use the z only as a baseline."

D13. How precise is a failure probability from 10,000 inputs?

For one fixed program, the share of failing inputs p-hat has standard error sqrt(p (1 - p) / n).

  • p = 0.01, n = 10,000: SE = 0.000995. The 95% half-width is 0.00195, about plus or minus 20% of p.
  • For plus or minus 10% of p at 95%: n = 1.96^2 (1 - p) / (0.01 p) = 38,032 inputs.
  • p = 0.001, n = 10,000: only 10 failures expected, relative SE 32%.
  • Zero failures in n inputs: the 95% upper bound is 1 - 0.05^(1/n), about 3/n (the "rule of three"). For n = 10,000 that is 0.0003.

The bigger caveat is not n. Your inputs come from type hints and the PR's test values, not from real use. So the failure probability is relative to your input generator, and you should say so.

Say it.

"With 10,000 inputs and a failure probability of one percent, my estimate is good to about plus or minus 20 percent. If a run never fails, I can only say its failure probability is below about 3 in 10,000, and only for my input generator, not for real use."

D14. The field model m(t) = sum_j omega_j G(t - tau_j), and why it is an infinite-server queue

The model. Merged change j arrives at time tau_j with L_j added lines and covariates z_j. It brings a Poisson number of faults with mean omega_j = L_j exp(beta' z_j). Each fault is found after a random delay D with distribution G (G(u) = 0 for u < 0), independently of the others.

Derivation of m(t).

Step 1. Change j: N_j ~ Poisson(omega_j) faults.
Step 2. Each fault is found by time t with probability G(t - tau_j), independently.
        Thinning a Poisson count keeps it Poisson:
        (faults of change j found by t) ~ Poisson( omega_j G(t - tau_j) ).
Step 3. Changes are independent, and a sum of independent Poissons is Poisson:
        N(t) = faults found by t ~ Poisson( m(t) ),   m(t) = sum_j omega_j G(t - tau_j).
        The intensity is lambda(t) = m'(t) = sum_j omega_j g(t - tau_j), with g = G'.

Why it is an infinite-server queue. Think of each fault as a customer. It arrives when its change is merged. It stays "in service" (present but not yet found) for its delay D. Nobody waits for a server, because every fault is found on its own schedule: infinitely many servers. A detection is a departure. For a queue with Poisson arrivals and infinitely many servers (M/G/infinity), the departures form a Poisson process, here an NHPP with mean m(t).

  • If all faults arrive at time 0, m(t) = omega G(t). That is the finite-fault NHPP (Goel-Okumoto when G is exponential). It levels off at omega.
  • If arrivals continue forever, m(t) keeps growing: an infinite-fault model.
  • Dohi, Osaki and Trivedi [12] used this view to put finite and infinite fault NHPP models in one framework. [CHECK: the exact form of their arrival process; you have not read the full paper]

Why a finite-fault NHPP does not fit agent code. omega G(t) assumes one fixed code base with a fixed expected number of faults. Agent code keeps arriving, so the total number of faults keeps growing. In the sum, each change's own contribution levels off at omega_j, but the total grows as changes arrive.

Why exp(beta' z). It keeps omega_j positive for any beta, and each coefficient is a multiplicative effect: exp(beta_k) is the factor per unit of z_k. This is the proportional-intensity form used in the lab's covariate models.

Example. A 200-line agent change, baseline 0.01 faults per line (exp(beta_0) = 0.01), agent effect beta_1 = 0.4. omega = 200 * 0.01 * exp(0.4) = 2 * 1.492 = 2.98 expected faults. With G exponential with mean 30 days, the expected number found within 60 days is 2.98 (1 - e^(-2)) = 2.58.

Likelihood (my derivation). NHPP log-likelihood for fix times t_1, ..., t_n observed up to T:

log L = sum_i log lambda(t_i) - m(T),     lambda(t) = sum_j omega_j g(t - tau_j).
If each fix is linked to its change j (from the commit message), it splits by change:
log L = sum_j [ n_j log omega_j + sum_{i in j} log g(t_i - tau_j) - omega_j G(T - tau_j) ] + const.

So, for a known G, n_j ~ Poisson( L_j G(T - tau_j) exp(beta' z_j) ): a Poisson regression with offset log L_j + log G(T - tau_j). [CHECK: my derivation, to confirm with Prof. Zheng]

Say it.

"Each merged change brings a Poisson number of faults with mean omega_j, and each fault is found after a random delay with distribution G. Thinning keeps it Poisson, so the faults found by time t are Poisson with mean the sum of omega_j times G of t minus tau_j. That is an infinite-server queue: faults arrive with changes, stay hidden for their delay, and leave when found, without waiting for each other."

D15. Cohen's kappa, with a small example

Formula. kappa = (p_o - p_e) / (1 - p_e). p_o = observed share of agreement. p_e = agreement expected by chance = sum over labels of (checker's share) * (your share).

Example: checker against your hand labels on 20 examples.

You: follows rule You: does not
Checker: follows 12 1
Checker: does not 1 6 
p_o = (12 + 6) / 20 = 0.90
Checker says "follows" 13/20 = 0.65.  You say "follows" 13/20 = 0.65.
p_e = 0.65 * 0.65 + 0.35 * 0.35 = 0.4225 + 0.1225 = 0.545
kappa = (0.90 - 0.545) / (1 - 0.545) = 0.355 / 0.455 = 0.78

By the common Landis and Koch labels, 0.61 to 0.80 is "substantial" agreement.

Why you report kappa as well as your 90% rule. If almost every example has the same label, 90% agreement can be no better than chance. Example: 18 both "follows", 1 and 1 disagreements, 0 both "does not". p_o = 0.90, p_e = 0.95 * 0.95 + 0.05 * 0.05 = 0.905, kappa = -0.05. Also, 18 of 20 is a small sample: its Wilson 95% interval is 0.70 to 0.97.

Say it.

"Kappa is observed agreement minus chance agreement, divided by one minus chance agreement. In my example 90 percent agreement gives kappa 0.78. I report it because 90 percent can be pure chance when nearly every example has the same label."

D16. What "task as a random effect" means (RQ2)

Model, in words. Each task has its own baseline difficulty. You treat your 10 tasks as a sample from a larger population of tasks. You estimate the effect of the file version within each task, and you let the baseline vary between tasks.

y_tv = beta_0 + beta_1 * [v = rule replaced] + u_t + e_tv,   u_t ~ N(0, sigma_u^2),  e_tv ~ N(0, sigma_e^2)
y_tv: failure probability (or its logit) for task t and file version v.
beta_1: the effect of replacing the rule.  u_t: task t's own offset.
For pass/fail per run: logit P(pass) = beta_0 + beta_1 v + u_t   (a mixed logistic model).
In R (lme4): glmer(cbind(fail, pass) ~ version + (1 | task), family = binomial)

Why random and not fixed. You want a claim about tasks like these, not only these 10. Runs on the same task are correlated, and the random effect gives honest standard errors for that. The share of variance between tasks is sigma_u^2 / (sigma_u^2 + sigma_e^2), the same idea as rho in D4. For the logistic version it is sigma_u^2 / (sigma_u^2 + pi^2 / 3) on the latent scale.

Honest limit. With 10 tasks, sigma_u is estimated from 10 values. The result is close to a paired comparison of 10 task-level differences, which has little power for small effects (see 03_statistics.md S13).

Say it.

"Task as a random effect means each task gets its own baseline difficulty, drawn from a distribution, and I compare the two file versions within each task. I do it because I want to generalise to tasks like mine, and because runs on the same task are not independent. With ten tasks it is close to a paired comparison, so small effects will be hard to see."

20 likely committee questions about this math (short spoken answers)

Q1. Why is the chance that two runs both fail not p squared?

"Because the runs share the input. Given the input they are independent, so both fail with theta squared, but averaging over inputs gives p squared plus the variance of theta, which is bigger unless every input is equally hard."

Q2. What would Var theta = 0 mean in practice?

"That every input is exactly as hard as every other for this setting. For real code that's unlikely: some inputs hit an edge case that many runs get wrong."

Q3. Why a Beta distribution?

"theta is a probability, so it needs a distribution on 0 to 1, and the Beta has one parameter for the mean and one for the spread. It is conjugate to the binomial, so the count of failing runs has a closed form. If it fits badly, I'd try a zero-inflated version or a mixture."

Q4. What is rho, and what values do you expect?

"rho is the correlation between two runs' failures on the same input, 1 over a plus b plus 1. I don't know the value yet. The Nogueira result that voting got only 0.43 of the independent gain suggests it's clearly above zero, and the pilot will tell me."

Q5. Derive the 2-out-of-3 vote failure.

"On one input the vote fails if two or three runs fail: 3 theta squared times 1 minus theta plus theta cubed, which is 3 theta squared minus 2 theta cubed. Averaging over inputs gives E of that. With p = 0.1 and independence it's 0.028."

Q6. When does voting make things worse?

"On an input where theta is above one half, because then most runs fail and the vote picks the wrong answer more often than one run would. The gain on one input is theta times 1 minus theta times 1 minus 2 theta."

Q7. Can you always fix dependence by adding more runs?

"No. As N grows, the vote fails exactly on the inputs where theta is above one half, so the failure probability goes to that share, not to zero."

Q8. How do you fit the model? Why not a closed form?

"By maximum likelihood on the counts of failing runs per input. The score equations contain digamma functions and have no closed-form solution, so I maximise numerically, starting from method-of-moments values."

Q9. Why bootstrap runs and not inputs?

"Because the same runs meet every input. One bug in one run fails a whole region of inputs, so the rows are not independent pieces of evidence about the setting; the runs are. In a small simulation, resampling inputs gave intervals about six times too narrow."

Q10. How do you check that the beta-binomial fits?

"I compare the observed number of inputs with 0, 1, up to k failing runs with what the fitted model expects, and I compare the model's P(two fail) with the model-free estimate from J times J minus 1. I'd also compare AIC with the binomial and a zero-inflated version."

Q11. How is your rho different from the Knight and Leveson z?

"The z only tests whether failures are independent. rho measures how dependent they are, and with p it gives me the vote failure for any N, so I can choose N. I keep the z as a baseline so I can compare with Ron et al."

Q12. How do you measure what a change between runs does?

"For runs from two settings I estimate the covariance of their thetas, using the average over inputs of the product of their failure shares minus the product of their means. The change that gives the smallest covariance at the same p is the most useful one for voting."

Q13. How do you choose N, and where do c_run and c_fail come from?

"I compute N times c_run plus c_fail times the vote failure for each odd N and take the smallest. c_run is the measured cost of one run. c_fail is a choice the team makes, so I'd show the answer for a range of values."

Q14. Are 10 runs per setting enough?

"For p, roughly yes. For rho and for the bootstrap it's tight, because the runs are the units, so the intervals will be wide. The pilot will show the interval width, and I'd add runs if needed."

Q15. Is it fair to count every 2-of-3 failure as a vote failure?

"It's slightly pessimistic, because two different wrong outputs give no majority, and a voter could notice that. Runs with a shared bug can give the same wrong output, so I use the simple count, say so, and can check how often the wrong outputs match."

Q16. How precise is a failure probability from 10,000 inputs?

"At one percent, about plus or minus 20 percent of the value. With zero failures I can only say it's below about 3 in 10,000, and only for my input generator."

Q17. Why is your field model an infinite-server queue?

"Each fault arrives with its change and stays hidden for a random delay, independently of the others, like customers with their own server. Detections are the departures, so their count by time t is Poisson with mean the sum of omega_j times G of t minus tau_j."

Q18. Why exp(beta' z) for omega_j?

"It keeps the expected number of faults positive, and each coefficient becomes a multiplying factor. For example, beta = 0.4 for an agent means about 1.5 times as many faults per line."

Q19. What does "task as a random effect" mean?

"Each task gets its own baseline difficulty drawn from a distribution, and I compare file versions within tasks. It lets me generalise beyond my ten tasks and keeps the standard errors honest, because runs on the same task are correlated."

Q20. Why report kappa if you already require 90% agreement?

"Because 90 percent can be chance level when nearly every example has the same label. Kappa removes the chance part. In my example 90 percent gives kappa 0.78, but with very unbalanced labels 90 percent can give kappa near zero."
