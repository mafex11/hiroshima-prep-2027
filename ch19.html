1. The problem and why it matters

Q1. Why would anyone run a coding agent several times on the same task?

In Gloaguen et al.'s numbers one run costs at most about one and a half US dollars, and each run can give a different patch. So it is natural to run a few and pick one, like the versions in N-version programming. My question is when that really buys reliability, and when the runs only repeat the same bug.

If he pushes ("Do teams really do this?"): "I don't have numbers on how often teams do it. At work we once sent the same tutorial video, as an uploaded file, through our Gemini pipeline that turns videos into guides, which isn't a coding agent, twice with the same prompts, and both times it wrote no step for about the first 80 seconds. Only two runs, but the same miss twice. My point is that it's cheap, so a team needs to know when it helps."

Follow-ups (each builds on your last answer)

  1. Prof: "You say each run can give a different patch. But Gloaguen et al. set the temperature to 0. Do repeated runs really differ?"
    You: "Yes, in practice. Temperature 0 removes the random sampling, but hosted models still aren't fully deterministic, and an agent run has many steps, so one small difference early can change everything after it. Gloaguen et al. ran each agent only once, but Zhang et al. ran Claude Code three times on each of 500 SWE-bench Verified tasks, and 58 tasks were solved in only one or two of the three runs."
  2. Prof: "Solved or not is only pass or fail. How would you tell whether two passing patches really differ?"
    You: "By behaviour, not by text. I run both on the same generated inputs and count the inputs where their outputs differ. Two patches can look different and still behave the same, and for a vote only the behaviour matters."
  3. Prof: "So if the runs behave very differently, voting will help?"
    You: "Not necessarily: it helps only if their failures fall on different inputs. Your lab's N-version paper found that more diversity did not always mean higher reliability, and versions can differ a lot yet still fail on the same hard inputs. So I measure joint failures directly, not just how different the runs are."

Q2. Why do you call the context file "part of the specification"?

Besides the code itself, the agent learns what to build from the task text and the context file. In Ron et al., who reused the Knight and Leveson specification, many shared failures traced back to parts of it that are hard or ambiguous. Every run in a repository reads the same file, so a rule in it can play the same role.

If he pushes ("Most rules are about commands, like how to run the tests."): "Yes, and I don't use those. I pick only rules that change what code is written, like which helper to use, because only those can change how the code behaves."

Follow-ups (each builds on your last answer)

  1. Prof: "Which parts of the Knight and Leveson specification were hard or ambiguous in Ron et al.?"
    You: "The failures were concentrated in two of the fifteen launch conditions, numbers 9 and 14. There many agents used the circle through the three points instead of the smallest circle that contains them, and for an obtuse triangle those differ. Conditions 3 and 10 had an angle that can be written two ways, equal in exact maths but not under the benchmark's float comparison."
  2. Prof: "But that is a trap in the problem itself. A rule in the context file is an explicit instruction. Why expect the same effect?"
    You: "I'd expect it to be stronger, because in Ron et al. many agents fell into the trap on their own but not all of them, while a rule tells every run to make the same choice. If that choice is wrong on some inputs, more runs share the failure. That's my hypothesis, and RQ1 tests it by comparing how often runs fail together with the rule and with neutral text in its place."
  3. Prof: "In your data, how would you tell a failure caused by the rule from a trap in the task itself, like their circle?"
    You: "I compare the two file versions on the same task and the same inputs. If the shared failures sit in code that uses what the rule names, and they drop with the neutral file, they come from the rule. If they stay with the neutral file, they come from the task itself, and I'd report them as that."

Q3. Is this really a reliability question, or a software engineering question?

The main quantity is a probability: how often two or three runs fail on the same input, and what that does to a vote. That is the Eckhardt and Lee question, and it needs a probability model with intervals. Whether agents follow a rule is the software engineering part, and I keep it only as a manipulation check.

Why he asks: this is a reliability lab. He wants to see that the core of the plan is the probability model, not rule compliance.

Follow-ups (each builds on your last answer)

  1. Prof: "You say the main quantity is how often runs fail together. Why isn't the failure probability of one run enough?"
    You: "Because the vote depends on E[θ²] and E[θ³], so on how the failures are spread over the inputs, not only on their average p. Two settings with the same p can give very different votes."
  2. Prof: "Show me that with numbers."
    You: "Imagine p = 0.02 in two cases. If every input has θ = 0.02, a 2-out-of-3 vote fails with 3p² - 2p³, about 0.0012. If instead 2.5% of inputs have θ = 0.8 and the rest have 0, p is still 0.02, but on those inputs 3θ² - 2θ³ = 0.896, so the vote fails with about 0.022. That is worse than a single run."
  3. Prof: "In your second case the vote is worse than one run. What would you tell a team?"
    You: "Not to pay for more runs of the same setting. They should either use one run and spend the money on testing beyond the task's tests, or change something between runs, like the agent, so that different runs find different inputs hard. Which change does that best is exactly my RQ1."

Q4. Give me a concrete example of one rule making every run fail together.

For example, imagine the file says "round money with round_cents()", and that old helper turns any negative value into 0.0. A task asks for a discount function, and its tests use only positive prices. Most runs follow the rule and pass the tests, but on a refund, which has a negative price, they all return 0.0. So they fail on the same inputs with the same wrong answer.

If he pushes ("So voting can't fix it?"): "Right. If 7 of 9 versions share the bug, the majority is wrong on those inputs, so the vote is wrong too."

Follow-ups (each builds on your last answer)

  1. Prof: "That example is imaginary. Do real context files have rules like 'use this helper'?"
    You: "I haven't picked my rules yet, but real files do have rules like that. In fastmcp's current AGENTS.md one rule says never use a bare except and be specific with exception types, and another says prefer item.key over ad-hoc name or URI fallbacks. Both change the code the agent writes and a script can check them, though I still need the version of the file each task used. What I do know is that agents follow the tools a file names: in Gloaguen et al., uv, a Python package tool, was used 1.6 times per task when the file mentioned it and fewer than 0.01 times when it didn't."
  2. Prof: "Following a tool is not the same as inheriting a bug. If a helper were buggy, wouldn't the developers have fixed it?"
    You: "Often yes, so I can't count on finding a real buggy helper. But a helper can be right for its old use and wrong for a new one, like a rounding helper written for shelf prices and then used for refunds. Its old tests still pass, so nobody notices until a new task sends every run to it."
  3. Prof: "And if the developer's merged code also calls that helper, would you even see the failure?"
    You: "Mostly not: runs that follow the rule agree with the merged code and look correct, which is the limit I state in my plan. The only hint comes from runs that skip the helper, for example with the neutral file, because they'd disagree with the merged code on refunds, and my hand check would show the merged code is the one that's wrong. I'd drop those inputs as planned, but I'd report the case, since it's exactly the shared bug my method can't count."

2. Eckhardt and Lee

Q5. In your study, what is the "development process", and what is a "version"?

A process is one setting on one task: one agent, one model and one file version, and in my harness one temperature. A version is one run of that setting that passes the task's tests. Drawing a version at random means starting one more run in a clean container.

If he pushes ("Are your runs really independent draws?"): "Given the setting, I treat them as exchangeable: same container image, no shared state, no git history. A provider quietly changing the model would break that, so I pin the CLI and model versions, record them for every run, and would run all settings of a task over the same few days."

Follow-ups (each builds on your last answer)

  1. Prof: "Why is the process one setting on one task? In Eckhardt and Lee the process produces a whole program."
    You: "Because θ(x) has to be defined on one input space, and each task is a different function with its own inputs. In Eckhardt and Lee the whole program has one specification; here each task is its own small specification, with its own tests and the context file of its time."
  2. Prof: "Then how do you get one answer per setting across your 10 tasks?"
    You: "First I compare settings within each task, since every task has all seven settings, so the task's difficulty cancels out. For one number per setting across tasks, I'd need a model that lets ρ vary by task, a hierarchical model, and that's something I want to learn here."
  3. Prof: "What would that hierarchical model look like?"
    You: "Each task gets its own p and ρ, and those come from one shared distribution across tasks, for example a normal distribution on the logit scale, the log of the odds. Then a task with few failures is pulled toward the other tasks instead of standing alone. I haven't fitted one yet; I'd first simulate data from it to see whether 10 tasks are enough to estimate the spread."

Q6. Please show why two runs both fail with probability p² + Var θ.

Draw an input X. Given X, the two runs fail independently, each with chance θ(X), so both fail with θ(X)². Averaged over inputs that is E[θ(X)²], and by the definition of variance E[θ²] = (E[θ])² + Var θ = p² + Var θ. So joint failure equals p² only when θ is the same on every input.

If he pushes ("Is Var θ = 0 ever realistic?"): "Only if every input is equally hard, and I don't expect that for real code. An empty list or a negative value is usually harder than a typical input. Imagine half the inputs have θ = 0 and half have θ = 0.4: then p = 0.2 and p² = 0.04, but the real joint failure is 0.5 x 0.16 = 0.08."

Follow-ups (each builds on your last answer)

  1. Prof: "You said that given X the two runs fail independently. Isn't that exactly the independence you're testing?"
    You: "No, they are two different things. Given the input, two runs are independent because each is a separate draw from the setting in a fresh container, the same assumption Eckhardt and Lee make for independently developed versions. Over random inputs they are still dependent, because both are more likely to fail on the same hard inputs, and that dependence is exactly Var θ."
  2. Prof: "Then how big is that dependence in your helper example?"
    You: "Imagine θ = 7/9 on 2% of the inputs and 0 on the rest. Then p = 0.02 times 7/9, about 0.016, so p² is about 0.00024. But E[θ²] = 0.02 times 49/81, about 0.012, so two runs both fail about 50 times more often than independence predicts."
  3. Prof: "Why exactly 50?"
    You: "If all failures sit on a share q of the inputs with the same θ, then E[θ²] = qθ² and p² = q²θ², so the ratio is 1/q. Here q is 0.02, so the ratio is 50. The rarer the hard inputs, the further joint failure is from independence, even when p is small."

Q7. Eckhardt and Lee also showed that more versions can be worse than one. When does that happen?

It needs θ(x) above 0.5 on a set of inputs with positive probability. There most versions are wrong, so as N grows the system failure tends to the probability of the inputs where θ is above 0.5. If that is bigger than p, many versions are worse than one. A strong rule that sends every run to a buggy helper is exactly that case.

Why he asks: to see if you know the theory beyond one formula. The report version also says system failure probability does not always fall as N grows.

Follow-ups (each builds on your last answer)

  1. Prof: "Why does the system failure tend to the probability of those inputs? Show me."
    You: "Take one input with θ above 0.5. As N grows, the share of failing versions tends to θ by the law of large numbers, so the majority fails with probability tending to 1, and where θ is below 0.5 it tends to 0. Averaging over inputs, the limit is the probability of the set where θ is above 0.5, plus half of any set where θ is exactly 0.5."
  2. Prof: "So can adding versions help at first and then hurt? Give me a case."
    You: "Imagine 10% of inputs have θ = 0.1, 3% have θ = 0.6, and the rest 0, so one version fails with p = 0.028. Three versions fail with about 0.022, and five with about 0.021, which is the best. After that it climbs, passes a single version at about 55 versions, and heads for 0.03. Eckhardt and Lee show a case like this in their report."
  3. Prof: "How would you know from your data which case you're in?"
    You: "From the fitted Beta I get the share of inputs with θ above 0.5, and I compute P(majority of N fails) for each N instead of assuming it falls. Eckhardt and Lee's Theorem 3 also gives a quick check: if the distribution of θ puts at least as much weight on every interval below 0.5 as on its mirror image above 0.5, voting is on average no worse than one version."

3. RQ1 and RQ2

Q8. In RQ1, how do you compare the four changes: file version, agent, model and temperature?

For two settings a and b, both fail with p_a p_b + Cov(θ_a, θ_b), so I estimate that covariance on the same inputs. I compare four changes this way: file version, agent, model and temperature. The change that lowers it most is the best way to get diversity.

If he pushes ("Which settings exactly?"): "Agent: Claude Code against Codex, which also changes the model. Model: the main Codex model against the smaller one; in my cost estimate those are GPT-5.2 and GPT-5.1 mini, as in Gloaguen et al. Temperature: my harness at its two temperatures. File: the original against the neutral file, within one agent. The plan compares covariances. Because the failure rates differ between settings, I'd also show each one scaled to a correlation, so a setting doesn't look better only because it fails less often."

If he pushes ("How do you estimate the covariance?"): "On each input, setting a has Y_a failing runs out of k_a, and b has Y_b out of k_b. Runs from different settings are independent given the input, so the average of Y_a Y_b / (k_a k_b) over inputs estimates E[θ_a θ_b]. Then I subtract p_a p_b."

If he pushes ("Eckhardt and Lee is about one process. What covers two?"): "That is Littlewood and Miller's idea of forced diversity, where versions come from different methods. I know it from its abstract and from how Ron et al. describe it, not from the full paper, so I didn't cite it. In my formula the covariance can even be below zero, which would mean two settings fail together less often than independence predicts."

Follow-ups (each builds on your last answer)

  1. Prof: "You say the change that lowers the covariance most is best. Lowers it compared with what?"
    You: "Compared with two runs of the same setting, where the covariance is just Var θ_a. If pairing a Claude Code run with a Codex run gives a covariance well below each agent's own variance, then changing the agent buys diversity."
  2. Prof: "Can the covariance between two settings ever be larger than both variances?"
    You: "No. By the Cauchy-Schwarz inequality a covariance is at most the square root of Var θ_a times Var θ_b, and that lies between the two variances, so it can't be above the larger one. It reaches that bound only when one setting's θ is an exact straight-line function of the other's, so the less the two settings agree on which inputs are hard, the lower it gets."
  3. Prof: "But the smaller model fails more often. How do you weigh a lower covariance against a higher p?"
    You: "I'd compare the end number, the joint failure p_a p_b + Cov(θ_a, θ_b) or the vote failure, not the covariance alone. A weaker model can lower the covariance and still raise the joint failure through its higher p. That might be one reason your lab's paper found voting helped little with weaker models, but I've only read the abstract, so it's a guess."

Q9. Your design is not fully crossed. Temperature changes only in your harness, and the second model runs only in Codex on the original file. Isn't that confounded?

Yes, partly. The temperature result holds only for Qwen3-30B-Coder in my harness, and the model result only inside Codex on the original file. I don't vary temperature in the CLIs: Prof. Zheng told me on 2 Nov that newer models often don't let you set it, so I keep that comparison in my own harness, where I set it directly. Adding the neutral file to the smaller model and my harness would add 300 runs, about 42 to 52 dollars, so I could add it if the pilot cost is fine.

If he pushes ("And Claude Code against Codex?"): "That changes the harness and the model together; in my cost estimate that is Sonnet 4.5 against GPT-5.2. Only the two Codex models separate the model from the agent. So I report each comparison with its own baseline and don't claim one general ranking."

Why he asks: to check that you limit your claims honestly.

Follow-ups (each builds on your last answer)

  1. Prof: "You said 300 more runs for about 42 to 52 dollars. Walk me through that."
    You: "The smaller Codex model on the neutral file is 10 tasks times 10 runs, so 100 runs at 18 to 22 cents, which is 18 to 22 dollars. My harness on the neutral file is 10 tasks, 2 temperatures and 10 runs, so 200 runs at 12 to 15 cents, which is 24 to 30 dollars. Together that's 300 runs and 42 to 52 dollars at Gloaguen et al.'s per-task prices."
  2. Prof: "Would those 300 runs remove the confounding?"
    You: "Only part of it. I'd see whether a rule's effect holds for both Codex models and in my harness, so the file result wouldn't rest on two agents alone. But temperature would still change only in my harness, and Claude Code against Codex would still change the harness and the model together."
  3. Prof: "Could you separate the agent from the model at all?"
    You: "Partly. Gloaguen et al. ran the same Qwen3-30B-Coder in Qwen Code, an existing agent that also reads AGENTS.md, so if I ran it there as well as in my harness, only the agent would change. At their prices that's about 12 to 15 dollars per 100 runs; it isn't in my plan yet, and I'd add it if the pilot budget allows."

Q10. In RQ2, why replace the rule with neutral text instead of deleting it?

Deleting also makes the file shorter. Zhang et al. found that random rules raised the pass rate about as much as curated ones, so just having rules in the file seems to matter. Neutral text of about the same length keeps that fixed, so the difference I measure is the rule's content.

If he pushes ("What is neutral text?"): "A sentence of about the same length with no instruction in it, for example a line about the project's history. The checker then shows whether the agents stopped following the rule."

If he pushes ("Was that significant?"): "Not on its own. Every rule set beat no rules by about 7 to 14 points, but no single comparison reached p < 0.05. The closest, random rules against no rules, had p = 0.077."

Follow-ups (each builds on your last answer)

  1. Prof: "Why would just having rules in the file matter? What's the mechanism?"
    You: "Zhang et al. read it as priming: on-topic instructions nudge the agent into a more careful mode, almost whatever they say. Their evidence is that random, shuffled and wrong-domain rule files did about as well as curated ones. I don't need that explanation to be right; my design only has to hold the length and the presence of rules fixed."
  2. Prof: "Then couldn't your neutral line prime the agent too?"
    You: "Maybe a little. Then what I measure is the rule against a line of the same length that tells the agent nothing, and that is the comparison I want. To check that the choice of line doesn't matter, I could try a second neutral line on one task in the pilot."
  3. Prof: "With 10 runs per line, could you even see a difference?"
    You: "Only a big one. With a Fisher exact test on how many runs pass the task's tests, 9 out of 10 against 3 out of 10 would show, but 9 against 7 would not. So it's only a sanity check, about 20 extra runs or roughly 15 to 21 dollars, and if the two neutral lines give very different results, I'd rethink my control."

Q11. Which direction do you expect in RQ2?

I don't assume one. In Zhang et al., prohibitions such as "do not refactor unrelated code" helped the pass rate, so a rule can protect. In my helper example the rule makes things worse beyond the tests. That's why RQ2 measures both the test pass rate and the failure probability beyond the tests.

If he pushes ("So prohibitions clearly help?"): "Not clearly. In Zhang et al. only that one rule was significant on its own, and they say it would not survive a strict correction for many comparisons."

Follow-ups (each builds on your last answer)

  1. Prof: "Your rules say 'use this helper'. That's a 'do' rule, not a prohibition. What did Zhang et al. find for 'do' rules?"
    You: "Four 'do' rules went the other way: removing them raised the pass rate by more than 5 points, for example 'follow code style' and 'handle edge cases'. None of the four was significant on its own, so I take it as a hint, not a finding."
  2. Prof: "Why would a 'do' rule hurt?"
    You: "Their reading is that a 'do' rule adds work that competes with the real task for the agent's attention, while a 'don't' rule acts only when the agent is about to go wrong. They also warn that such well-meant rules may bring regressions that standard testing doesn't show, and testing beyond the task's tests is exactly what RQ2 adds."
  3. Prof: "What result would show that worry is wrong for your rules?"
    You: "If, for rules the checker shows the agents really followed, the failure probability beyond the tests is no higher with the rule, and the interval rules out a large rise. Then I'd report that these rules changed the code without hurting reliability, which is still useful for teams who write these files."

Q12. How will you analyse RQ2, and can about 10 tasks detect anything?

I compare the two file versions in a mixed model with task as a random effect, so one hard task doesn't drive the result. With about 10 tasks it can only detect a large effect. So I'll report the estimate with its interval, plus the result per rule, and call it an estimate on 10 tasks, not a general law.

If he pushes ("Inputs inside one run are not independent."): "That's right. Failures inside one run are linked, so I should add run as a random effect inside task, or first summarise each run by one failure probability. I'd like your advice on which is better."

If he pushes ("Why not more tasks?"): "Each task needs a checked rule, an input generator and 20 hand-checked disagreements, plus the run costs. If the pilot is cheaper than I expect, more tasks is the first thing I'd add."

Follow-ups (each builds on your last answer)

  1. Prof: "You say about 10 tasks can only detect a large effect. How large is large?"
    You: "If I treat each task as one pair, original file against neutral file, then at the usual 5% level 10 pairs give an 80% chance of detecting the effect only when the average change is about as big as its spread from task to task, an effect size of about 1. At half that size the chance drops to about 30%."
  2. Prof: "How would you know that spread before the main runs?"
    You: "Only roughly. I'd take a first value from the pilot and then simulate: generate many fake studies with that spread and a chosen effect, fit the same mixed model to each, and count how often the interval excludes zero. Because the pilot value is rough, I'd repeat it for a range of spreads."
  3. Prof: "And if the simulation says you need 30 tasks?"
    You: "Each extra task needs 40 main runs, about 29 to 42 dollars at Gloaguen et al.'s prices, plus my time for its checker and inputs. So 20 more tasks would add about 590 to 830 dollars, more than the whole current estimate. Then I'd keep RQ2 as an estimate with an honest interval rather than a test, and ask your advice on whether more tasks are worth it."

4. The beta-binomial model and ρ

Q13. What exactly is random in your model?

Two things. The input X is drawn from the distribution I declare, and given X, each run of setting s fails with chance θ_s(X). The Beta distribution describes how θ spreads across inputs. The runs are a sample from the setting, which is why the bootstrap resamples runs.

Follow-ups (each builds on your last answer)

  1. Prof: "A beta-binomial usually gives each unit its own random θ. What is the unit in your model?"
    You: "The input. Each input x has its own θ_s(x), and because X is random, θ_s(X) is a random number between 0 and 1; the Beta is my model for its distribution, what Eckhardt and Lee call the intensity distribution. Given θ, the number of failing runs on that input is binomial, so overall it's beta-binomial."
  2. Prof: "But the same 10 runs meet all the inputs, so the counts on different inputs are not independent. Doesn't that break your likelihood?"
    You: "It hurts the intervals more than the estimates. If I multiply the per-input likelihoods as if the inputs were independent, the estimates of a and b are still roughly right, but the likelihood acts as if I had 10,000 independent observations, so its intervals are far too narrow. So I take the estimates from it and the intervals from the bootstrap over runs."
  3. Prof: "So what limits your precision, the 10,000 inputs or the 10 runs?"

Q14. Write down the beta-binomial quantities you use.

If θ follows Beta(a, b), the mean failure probability is p = a/(a + b) and ρ = 1/(a + b + 1). Then Var θ = ρ p(1 - p), so two runs both fail with p² + ρ p(1 - p). The number of failing runs out of k has variance k p(1 - p)[1 + (k - 1)ρ], which is larger than the binomial k p(1 - p) when ρ > 0.

Follow-ups (each builds on your last answer)

  1. Prof: "Derive ρ = 1/(a + b + 1) for me."
    You: "The Beta variance is ab divided by (a + b)² times (a + b + 1). Since p(1 - p) = ab/(a + b)², that variance is p(1 - p)/(a + b + 1). Writing it as ρ p(1 - p) gives ρ = 1/(a + b + 1)."
  2. Prof: "You call ρ a correlation. A correlation between what? Show it."
    You: "Let U and V say whether run 1 and run 2 fail on the same random input. Each has mean p and variance p(1 - p), and E[UV] = E[θ²], so their covariance is E[θ²] - p² = Var θ. Dividing by p(1 - p) gives the correlation Var θ / p(1 - p), which is ρ."
  3. Prof: "Then where does the factor 1 + (k - 1)ρ in the count's variance come from?"
    You: "The count is the sum of k such indicators. Each has variance p(1 - p), and each of the k(k - 1) ordered pairs has covariance ρ p(1 - p), so the variance is k p(1 - p) + k(k - 1)ρ p(1 - p) = k p(1 - p)[1 + (k - 1)ρ]. With 10 runs and ρ = 0.3, that is 3.7 times the binomial variance."

Q15. In plain words, what does ρ mean, and why use it instead of the Knight and Leveson z?

ρ is the correlation between "run 1 fails" and "run 2 fails" on the same random input. Zero means one run failing tells you nothing about another, and one means they always fail together. z is a test statistic that grows with the number of inputs and depends on each version's failure rate. ρ is a number between 0 and 1 that measures how strong the dependence is, and it goes straight into the vote formula.

If he pushes ("So what is z for?"): "It's my baseline, so I can compare with Ron et al. ρ is my main measure."

Follow-ups (each builds on your last answer)

  1. Prof: "You say z grows with the number of inputs. Show me why."
    You: "z takes K, the number of inputs where two or more versions fail, subtracts the number expected under independence, and divides by the standard deviation, which is about the square root of that expected number. If the excess per input stays the same, the top grows like the number of inputs T and the bottom like the square root of T, so z grows like the square root of T. Ron et al.'s 429 against 115.36 on a million inputs gives z = 29.2, but the same pattern on 10,000 inputs would give only about 2.9."
  2. Prof: "So z mostly tells you how much evidence you have. What would ρ be for Ron et al.'s data?"
    You: "I can't get it from their summary numbers, because K counts inputs where two or more of 48 different programs fail, and those programs have very different failure rates: 27 of them never failed at all. But they released their code and all the generated versions on GitHub, so I could rerun them and fit it myself, which would be a good first exercise."
  3. Prof: "Those 48 programs come from five harnesses and three languages. Would one ρ even make sense there?"
    You: "Not really, because ρ assumes the versions are exchangeable, meaning they behave like repeated draws from one process, so swapping their labels changes nothing. Theirs come from many processes. That's why one setting in my design is one agent, one model, one file version and one temperature, and across settings I use the covariance instead, a bit like Ron et al. comparing same-agent pairs with cross-agent pairs."

Q16. Why a Beta distribution? What if it fits badly?

But I expect most inputs to have θ = 0 and a few to be hard, and one Beta may not fit that well. Then I'd try a zero-inflated beta-binomial or a mix of two Betas, and compare them by AIC and by how well they predict the observed vote failures.

If he pushes ("You fit per task? That's a lot of fits."): "Yes, one per task and setting. Each task has 7 settings, so about 70 fits for 10 tasks. If the intervals are too wide, a hierarchical model that shares information across tasks is the next step."

If he pushes ("Settings will have different numbers of admitted runs."): "The beta-binomial allows a different k per setting, so a setting with 7 admitted runs just has k = 7. Fewer runs means less information, and admission says something by itself, so I report the test pass rate next to ρ."

  1. Prof: "What does a zero-inflated beta-binomial mean here, in terms of inputs?"

  2. Prof: "With 10 runs, how can you tell θ = 0 from a small θ on one input?"

  3. Prof: "If they're hard to tell apart, how do you choose between the models? By AIC, as you said?"

Q17. Do you even need the Beta assumption to estimate the vote failure?

Not for small N. If Y of k runs fail on an input, the average of Y(Y - 1)/(k(k - 1)) over inputs estimates E[θ²] with no assumption, and Y(Y - 1)(Y - 2)/(k(k - 1)(k - 2)) estimates E[θ³]. So I can estimate E[3θ² - 2θ³] directly and use it to check the Beta fit.

If he pushes ("Then what does the model add?"): "One ρ per setting to compare, smoothing when few runs are admitted, and answers for N larger than the number of runs I have."

Why he asks: to see whether you know what the model adds over plain counting. It is also a reason for 10 runs: with 3 runs you could check only the 2-out-of-3 vote directly, and with 10 you can check larger votes too, up to the number of admitted runs.

Follow-ups (each builds on your last answer)

  1. Prof: "Why Y(Y - 1) over k(k - 1), and not simply (Y/k) squared?"
    You: "Because (Y/k) squared is biased upward: its expected value is θ² plus θ(1 - θ)/k, the extra coming from binomial noise. Y(Y - 1) counts ordered pairs of different runs that both fail, there are k(k - 1) such pairs, and each pair fails together with probability θ², so the ratio has expected value exactly θ²."
  2. Prof: "Give me a number: 10 runs, and 3 fail on one input."
    You: "Then Y(Y - 1)/(k(k - 1)) is 6 over 90, about 0.067, while (3/10) squared would give 0.09. The third-order term is 6 over 720, which is 1/120. So for this input the vote term is 3 times 0.067 minus 2 times 1/120, about 0.18, and the estimate averages that over all inputs."
  3. Prof: "Is that 0.18 just a formula, or does it mean something?"
    You: "It means something simple. Of the 120 ways to choose 3 of my 10 runs, 22 have at least two runs failing on that input, and 22 over 120 is also about 0.18. So the estimate is the vote of three averaged over every group of three runs I have, which is why it needs no Beta assumption."

Q18. Why does the bootstrap resample runs and not inputs?

The same runs meet all 10,000 or more inputs. If one run has a bug, it fails on many inputs at once, so the inputs are not independent information about the setting. Resampling runs keeps that structure, and resampling inputs would make the intervals much too narrow.

If he pushes ("With about 10 runs, that bootstrap is rough."): "Yes, it is. A hierarchical or Bayesian model across tasks may give better intervals, and I'd like your advice. Your lab's page mentions interval estimation by parametric bootstrap, and that is one of the things I want to learn here."

  2. Prof: "If the same run is drawn twice, those two copies fail on exactly the same inputs. Doesn't that make ρ look bigger?"

5. 2-out-of-3 voting

Q19. Is a vote over dependent runs always worse than a vote over independent ones?

The vote fails with 3E[θ²] - 2E[θ³], against 3p² - 2p³ under independence. If θ stays below 0.5 on every input, 3θ² - 2θ³ is convex there, so by Jensen's inequality the vote fails at least as often as the independent formula says. If θ is above 0.5 on some inputs, Jensen doesn't apply directly, so I compute both numbers from the fitted model.

If he pushes ("Derive 3θ² - 2θ³."): "The vote fails if two or three of the three runs fail: 3θ²(1 - θ) + θ³ = 3θ² - 2θ³."

Follow-ups (each builds on your last answer)

  1. Prof: "Why is 3θ² - 2θ³ convex below one half?"
    You: "Its second derivative is 6 - 12θ, which is positive below one half and negative above it. So below one half the curve bends upward, and Jensen's inequality says the average of such a curve is at least the curve at the average, so E[3θ² - 2θ³] is at least 3p² - 2p³."
  2. Prof: "And above one half, where it bends down, can dependence make the vote better than independence?"
    You: "Yes, but only when runs fail a lot. Imagine half the inputs have θ = 0.4 and half have θ = 1, so p = 0.7. Independence predicts a vote failure of 0.784, but the true value is half of 0.352 plus half of 1, which is 0.676."
  3. Prof: "How much is 'a lot'? Can you give a bound?"
    You: "Yes. The largest convex curve that stays under 3θ² - 2θ³ equals it up to θ = 1/4 and then runs straight from there to the point (1, 1). Jensen works for that curve, so whenever p is at most 1/4, the dependent vote can never beat the independence formula, whatever the inputs look like. I expect p for admitted versions to be far below 1/4, so in my data dependence can't make the vote better."

Q20. Classic N-version programming votes on every input at run time. A team merges one patch. So what does voting mean here?

A team wouldn't run three patches in production. It would run all the patches on generated inputs and pick the one whose outputs agree with most of the others. If most runs share a bug, the picked patch has it. The model predicts how often the majority is wrong, and I can also measure directly how often the picked patch fails against the merged code.

If he pushes ("Are those the same number?"): "No. The per-input vote is the classic N-version number. The picked patch is one fixed program, so it can be right where the majority is wrong, and the other way round. I'd report both."

If he pushes ("Two wrong outputs may differ. Is that still a vote failure?"): "In my formula, yes, so it is on the safe side. A real voter could notice two different wrong answers. I can count separately the inputs where the wrong outputs are identical, because that is the dangerous case."

Follow-ups (each builds on your last answer)

  1. Prof: "A real team has no merged code to compare with. How would it pick a patch?"
    You: "It doesn't need the merged code. Picking uses only the agreement between the patches: on each generated input I see which patches give the same output, and I pick the patch that agrees with the others on the most inputs. The merged code is only for my own measurement, to check afterwards whether the picked patch fails."
  2. Prof: "Then isn't the picked patch just the majority? How can it be right where the majority is wrong?"
    You: "Imagine five patches. Three share one rare bug on 0.1% of the inputs, and each of those three also has its own bug on a different 5%, while the other two are clean. The clean ones disagree with the rest least, so I pick a clean one, and on the rare bug's inputs it is right while the vote of five is wrong."
  3. Prof: "Your clean patch won because the shared bug was rare. When would it lose?"
    You: "Call the shared bug's share of inputs X and each own bug's share Y. Adding up its disagreements with the other four, a clean patch gets 3X + 3Y and a buggy one 2X + 6Y, so the clean patch wins only while X is below 3Y. With 5% own bugs, a shared bug on more than 15% of the inputs makes me pick a buggy patch."

Q21. How do you find the best number of runs N?

I minimise c_run N + c_fail P(majority of N fails) over odd N. P(majority of N fails) is the binomial tail with θ(X), averaged over inputs with the fitted model. When ρ is near zero, extra runs lower it quickly. When ρ is near one, extra runs only repeat the same bug, and the best N can be 1.

If he pushes ("Where do the costs come from?"): "c_run I can measure: it's the cost of one run. c_fail depends on the team, so I'd show the best N for a range of ratios c_fail / c_run, not one number."

    You: "Then I have a real trade-off: ρ in RQ1 needs more runs per task, while RQ2 needs more tasks. One option is 20 runs on a few tasks for RQ1 and 10 runs on all tasks for RQ2, and I'd decide that once the pilot shows the real cost per run."

7. Failures beyond the tests: inputs, oracle and checks

Q29. How will you generate the inputs in practice?

A property-based testing library such as Hypothesis can build values from Python type hints, and I'd mix those with the values used in the task's tests. For each entry point I write the distribution down before the runs: types, ranges and the share of test values. At least 10,000 inputs per entry point.

If he pushes ("Is 10,000 enough?"): "If a version fails on 1 in 1,000 inputs, I see about 10 failures. If it fails on none, its failure probability is likely below about 3 in 10,000, by the rule of three. Running a function is cheap, so I can add more where needed."

If he pushes ("Why only the functions the tests call? Bugs can be in helpers."): "Every admitted version must implement the functions the tests call, so I can compare all versions there. A helper one run invents may not exist in another run. A helper bug that matters still shows up through the entry point that uses it."

If he pushes ("What about objects, files or network calls?"): "Those I can't generate this way, so I skip them and report how many I skipped. That's the limit in my proposal: only functions whose inputs can be generated."

Follow-ups (each builds on your last answer)

  1. Prof: "Hypothesis is built to find bugs, not to sample from a fixed distribution. Can a failure probability come from it?"
    You: "Not directly. Hypothesis lets you control which values can appear, but on purpose not how often each one appears, and its maintainers change that whenever they improve the tool. So I'd use it to see what each type hint allows, and draw the actual values myself from a distribution I write down, with a fixed random seed."
  2. Prof: "Then write one down for me. Say the function is discount(price: float, percent: int)."
    You: "Imagine the tests use prices between 1 and 500 and percents of 0, 10 and 50. I might take 20% of the inputs straight from those test values, and the other 80% with the price uniform between -1,000 and 1,000 and the percent a whole number from -10 to 110, so wider than the tests on both sides. Those numbers are my choice, and I'd fix them before any run."
  3. Prof: "With a uniform price, what's the chance you ever draw a price of exactly zero?"
    You: "In theory zero, since a continuous distribution puts no weight on a single value. With Python's random numbers it's 1 in 2 to the 53 per draw, about 1 in 10 to the 16, so in practice never. So a bug that shows only at a price of 0 has failure probability 0 under my distribution, which is honest but no help to a team. That's why the boundary inputs from your lab's BCD method sit next to the random ones: they hit exact values like 0 wherever the code compares a parameter with them."

Q30. How do you tell a real failure from an input that is simply illegal?

Some disagreements come from inputs the project never allows, like a negative quantity. I read 20 disagreements per task, check the docstring, the tests and how the function is called in the code base, and drop inputs that are outside the real domain or where the merged code itself is wrong. If many inputs get dropped, I narrow the declared distribution and say so.

If he pushes ("What if the code uses time or randomness?"): "I'd fix the random seeds and run the merged code twice on each input. If it disagrees with itself, I drop that input or entry point. For flaky tests at admission, I re-run them and drop flaky tasks."

Follow-ups (each builds on your last answer)

  1. Prof: "You read only 20 disagreements per task, but there may be thousands. How do 20 decide about the rest?"
    You: "The 20 show me patterns, and I turn each pattern into a written limit on the input domain that applies to every input. If most of the 20 come from negative quantities that the docstring and the callers never allow, I write down 'quantity at least 0' and drop every input that breaks it, not only the ones I read."
  2. Prof: "And if a rare kind of disagreement never shows up among your 20?"
    You: "That can easily happen: if one kind makes up 1% of the disagreements, 20 random picks miss it about 82% of the time, since 0.99 to the power 20 is about 0.82. So I wouldn't pick the 20 at random. I'd first group the disagreements by a simple pattern, like which argument is unusual and what each side returned, and read at least one from every group."
  3. Prof: "When you read a group and call its inputs illegal, that's your own judgement. Couldn't that bias RQ2?"
    You: "It could, so I'd decide blind: when I read a disagreement, I wouldn't see which file version or agent produced it, and I'd base the domain limits only on the merged code, its docs and its callers. A dropped input is dropped for every setting, so both file versions are still compared on exactly the same inputs."

Q31. Admission requires passing the tests. Doesn't that bias your failure probability?

It makes it conditional on passing, and that's on purpose: a run that fails the task's tests is not a working version, as in Knight and Leveson's acceptance test. But a file version that lets more runs pass could also admit weaker versions. That's why RQ2 reports the pass rate and the failure probability beyond the tests side by side.

Follow-ups (each builds on your last answer)

  1. Prof: "Give me an example where more runs pass but the admitted code gets less reliable."
    You: "Imagine that with the neutral file 5 of 10 runs pass, each failing on 1% of my inputs. With the rule 9 pass: 5 like before plus 4 weaker ones that fail on 5%. The pass rate rises from 50% to 90%, but the average failure probability of an admitted version rises from 1% to about 2.8%."
  2. Prof: "So which file version would you tell a team to use?"
    You: "It depends on how they use the runs. A team that reruns until the tests pass needs on average one over the pass rate runs per working version: 2 with the neutral file and about 1.1 with the rule. But with the rule the code it merges fails on 2.8% of inputs on average instead of 1%, so the rule saves runs and costs reliability, and I'd report both numbers rather than pick one."
  3. Prof: "Can you put both into one number?"
    You: "Yes, with the same two costs I use for choosing N. The cost per working version is the cost of a run divided by the pass rate, plus the cost of a failure times p. Here the rule saves about 0.89 runs but adds about 0.018 to p, so it wins only while one failure costs less than 50 runs. Above that, the neutral file is the better choice despite its lower pass rate."

8. The lab's methods: boundary values, NHPP and pysrat

Q32. (Prof. Okamura) Our BCD paper found boundary points by hand. How do you get them automatically?

I take branch conditions in the merged code that compare a parameter with a constant, like if percent > 100, and use 100 and its neighbours one minimal step away as boundary points. Your paper's Remark 2 says that boundaries from execution paths differ from boundaries defined by outputs, so I say clearly that mine are path-based. The pilot will report how many functions even have such conditions.

Follow-ups (each builds on your last answer)

  1. Prof: "How would you find those branch conditions in Python code, concretely?"
    You: "With Python's ast module, which turns source code into a tree. I walk the tree of each entry point, find the comparisons in if and while statements, and keep those where one side is a parameter and the other a number, like percent > 100."
  2. Prof: "Often the parameter is changed first, like p = percent / 100 and then if p > 1. Does your rule see that?"
    You: "Not my simple rule, because p isn't a parameter. For easy cases I can follow the assignment back, so p > 1 becomes percent > 100, but harder ones need a constraint solver such as Z3, a tool that finds inputs that make a condition true. The pilot would tell me how many conditions are of that harder kind."
  3. Prof: "After you invert it, which step do you take, one step in p or one step in percent?"
    You: "In percent, because that's what a caller actually sends: for an integer the step is 1, so the boundary points are 100 and 101, one on each side. For a float parameter I'd use the next float Python can represent, which math.nextafter gives, about 1.4 times 10 to the minus 14 above 100. Your paper's discussion suggests a Gaussian to find neighbouring points of continuous inputs, so I could compare the two."

Q33. Why use BCD only as a stress test, and how will you judge it?

30 to 50 chosen inputs are not a random sample from the declared distribution, so they can't give a failure probability. I use them to find boundary bugs the random inputs miss, and I compare the input sets with mutants of the merged code. A mutant is killed when its execution path differs, as in your paper, here from coverage.py branch data, and I also report kills by different outputs.

If he pushes ("What about strings and lists?"): "Your paper leaves non-numeric inputs as future work. I'd try one-element edits, adding, removing or changing one element, as the minimal operations, and see whether the distance still makes sense."

Follow-ups (each builds on your last answer)

  1. Prof: "Why add kills by output? Isn't a different path enough?"
    You: "They catch different things. An arithmetic mutant with no branch after it changes the output but not the path, and a mutant can change the path but still return the same output. The path rule lets me compare with your paper's kill rates, and the output rule matches my definition of a failure, a wrong output."
  2. Prof: "Which mutation operators would you use in Python?"
    You: "The five from your paper: off-by-one, and replacing a relational, arithmetic or logical operator or a scalar variable. All of them exist in Python, so I'd write them myself as small edits to the code's syntax tree with the ast module. Keeping the same five keeps my kill rates comparable with yours."
  3. Prof: "Some mutants never change the output at all. How do you handle them?"
    You: "Those are equivalent mutants, and in general no program can decide whether a mutant is one. Under the output rule they can never be killed, so they pull every method's kill rate down. I'd mark the mutants that no input from any method kills, check a sample of them by hand, and report kill rates with and without the ones I judge equivalent."

Q34. Why doesn't a finite-fault NHPP fit agent code, and what do you use instead?

In a finite-fault model like Goel-Okumoto, m(t) = ω(1 - e^(-bt)): one fixed code base holds ω faults on average, and testing finds them over time. Where agents keep merging changes, new faults keep arriving, so ω is not fixed. Instead, each merged change brings its own faults, and each fault is found after a delay.

If he pushes ("Write it down."): "Change j brings ω_j = L_j exp(β'z_j) faults on average, each found after a delay with distribution G, so m(t) = Σ_j ω_j G(t - τ_j). With one change at time 0 and an exponential G, this reduces to Goel-Okumoto."

Follow-ups (each builds on your last answer)

  1. Prof: "What does your m(t) do in the long run? Is it a finite or an infinite failure model?"
    You: "It depends on the merges. While agent changes keep arriving, m(t) keeps growing without limit, like an infinite failure model, and if merges stop, it levels off at the sum of the ω_j, like a finite failure model. So one model can look like either kind."
  2. Prof: "Suppose changes arrive at a steady rate. How fast does m(t) grow?"
    You: "If changes arrive at rate r and each brings ω faults on average, m(t) is r ω times the integral of G from 0 to t. For large t that integral is t minus the mean delay, so m(t) becomes a straight line: r ω times the difference between t and the mean delay. Faults are found at the rate they arrive, just one average delay later."
  3. Prof: "Then how many faults sit unfound in the code at any time?"
    You: "In the long run, the rate faults arrive times the mean delay, so r ω times the mean delay, which is Little's law. Imagine 5 agent changes a week, 0.2 faults each and a mean delay of 10 weeks: about 10 faults are in the code and not yet found at any moment."

Q35. Why do you call that an infinite-server queue?

Faults "arrive" with each merged change and "leave" when they are found, and they don't wait for each other. So it is like an M/G/∞ queue where each fault's stay has distribution G, and if each change brings a Poisson number of faults, the number found by time t is Poisson with mean m(t). Dohi, Osaki and Trivedi used this view to unify finite and infinite fault NHPP models.

If he pushes ("Have you read that 2004 paper?"): "Only the abstract so far. It describes debugging as an infinite-server queue that covers NHPP models with both a finite and an infinite number of faults, gives Bayesian and non-Bayesian ways to estimate it, and compares it with an earlier queueing model on real fault data."

Follow-ups (each builds on your last answer)

  1. Prof: "Why is the number found by time t Poisson? Show me."
    You: "Take one change merged at τ with a Poisson number of faults, mean ω. Each fault is found by t independently with probability G(t - τ), and keeping each point of a Poisson count independently with the same probability, called thinning, gives again a Poisson count, with mean ω G(t - τ). Changes are independent, and a sum of independent Poisson counts is Poisson, so the total found is Poisson with mean m(t)."
  2. Prof: "Is it realistic that faults are found independently of each other?"
    You: "Probably not fully. Qiu et al. point out that finding one fault can lead testers to related modules, so detections come in clusters, and that's why they use a self-exciting Hawkes process, where each detection raises the chance of more soon after. In my data I'd compare the weekly fix counts with what the fitted model expects each week: if they spread much more than a Poisson count would, plain Poisson is wrong."
  3. Prof: "And if it is wrong, how would you change your model?"
    You: "The simplest step is to let each change's fault rate be random, ω_j times a gamma-distributed factor with mean 1, so the count per change becomes negative binomial instead of Poisson. That's the same idea as my beta-binomial in RQ1, a random rate on top of a count. If the clusters really follow each detection in time, a Hawkes model like Qiu et al.'s fits better, and that's something I'd learn here."

Q36. How would you fit it, and where does pysrat come in?

I'd treat the fix times as an NHPP with intensity Σ_j ω_j g(t - τ_j) and maximise the usual log-likelihood: the sum of the log intensities at the fix times, minus m(T). pysrat gives the families for G, such as exponential, gamma and log-normal.

If he pushes ("Have you used pysrat?"): "Yes. I ran pysrat 0.2.8: the README quick start, then all 12 models on the Musa SS1A data that comes with it, and the log-logistic model fitted best by AIC. I'd ask Prof. Okamura whether its metrics-based or PR-NHPP models can already handle changes that each start at their own merge time."

Follow-ups (each builds on your last answer)

  1. Prof: "Your likelihood uses only the fix times. But you also know which change each fix belongs to. Why not use that?"
    You: "I should. Then each change j is its own small NHPP on the time since its merge, and the log-likelihood is a sum over changes: for each change, add the log of ω_j g(d) for every fix delay d, and subtract ω_j G(T - τ_j). Knowing which change each fix came from gives me each delay directly, which pins down G and β better."
  2. Prof: "What does the term ω_j G(T - τ_j) do for a change merged just before T?"
    You: "It says how many of that change's faults I should have seen by the end of the data. A change merged a week before T has had only one week, so few fixes from it are expected, and the model doesn't read its quiet week as a sign that it was clean."
  3. Prof: "Put a number on it: exponential delays with a mean of 10 weeks, one week after the merge."
    You: "G(1) = 1 - e^(-1/10), about 0.095, so on average less than a tenth of its faults have been found after one week. So recent changes tell me little about how many faults each change brings, and most of that comes from older ones, which is one more reason to pool repositories."

Q37. Where does the fix data come from, and is there enough?

From about 20 AIDev repositories. I'd find fix commits from their messages and link them to agent-written lines, the way Qiu et al. built datasets from GitHub issue histories. Counts per repository will be far below theirs: 104 to 397 faults per dataset, and 183 to 290 in their four GitHub datasets. So I'd pool repositories and share β across them. That's why this part is "if time permits".

If he pushes ("AIDev stops in 2025."): "Yes, its dataset cutoff is 1 August 2025. So I'd use it to choose repositories and then collect their newer commits myself."

If he pushes ("How is this different from Xia and Miller?"): "They model the hazard that one line is touched by a bug-fixing commit, with Fine-Gray competing risks. My model gives the expected number of faults not yet found, which is what a reliability growth model is for."

Follow-ups (each builds on your last answer)

  1. Prof: "How exactly do you decide from its message that a commit is a fix?"
    You: "I'd follow Xia and Miller: first conventional prefixes like 'fix:', then keyword patterns on the commit subject, and an LLM for commits that stay unclear. They checked a random sample of 100 commits labelled by hand and got a Cohen's kappa of 0.94, and I'd do the same check on my repositories."
  2. Prof: "And how do you link a fix to the agent-written line it repairs?"
    You: "Through the lines the fix changes or deletes: git blame tells me which commit last wrote each of them, and if that's an agent's merged change, the fault belongs to it, which is the idea of the SZZ method. It fails when a fix only adds a missing check, so there's no old line to blame, or when the line was reformatted in between. So I'd report how many fixes I couldn't link."
  3. Prof: "Your model needs the time a fault was found. Is the fix commit's time that time?"
    You: "Not exactly: a fault is usually found first and fixed later, so the commit time adds a repair delay on top of the detection delay. Where a fix links to an issue, I'd use the time the issue was opened, which is closer to detection, and Qiu et al. also built their GitHub datasets from issue histories. Otherwise I'd say clearly that my G is the delay until the fix, not until detection."

9. Threats to validity

Q38. What is the biggest threat to your results?

The oracle. The merged code is my reference, so if the human made the same mistake, for example used the same buggy helper, my testing can't see it. That is exactly the shared-helper case my study is about, so I may undercount the failures I care about most. The hand check catches the opposite case, where the merged code is wrong and the runs are right.

Follow-ups (each builds on your last answer)

  1. Prof: "Is there any way to catch a bug that the merged code shares?"
    You: "Partly, with checks that need no reference, called metamorphic relations: relations between the outputs of related inputs. In my discount example, discounting a negated price should give the negated result, so discount(-100, 10) should be -90. The round_cents helper returns 0.0 there, which breaks the relation even if the merged code does the same."
  2. Prof: "Who says that relation is true? Maybe refunds are meant to give zero."
    You: "Right, a relation is a claim about the specification, so it can be wrong too. I'd only use relations that the docstring, the tests or the code base support, and treat a broken one like a disagreement: something I check by hand, not an automatic failure."
  3. Prof: "Then what would you report from these checks?"
    You: "A separate count, kept out of p: the inputs where the merged code itself breaks a checked relation, and how many runs agree with it there. Those are shared failures my main measure can't see, so if the count is large for a task, I'd flag that task's p and ρ as probably too low. It isn't in my submitted plan, but it's how I'd partly cover this threat."

Q39. Couldn't the models have seen these pull requests in training?

Yes, some may be in the training data. I add newer pull requests merged after the training cutoff where possible, and I report old and new tasks separately. Gloaguen et al. checked this on their tasks: 12% to 40% of tasks came before the cutoff, depending on the model, and success did not differ significantly.

Follow-ups (each builds on your last answer)

  1. Prof: "If a model has seen the merged change, what does that do to your measures, not just to success?"
    You: "It pushes p down, because runs that reproduce the merged change agree with my reference. Its effect on ρ could go either way. Runs that copy the change become more alike, which pushes ρ up, but runs that reproduce it exactly never fail, and mixing never-failing runs with the others pulls ρ down, so I'd look at the data rather than guess."
  2. Prof: "How would you see memorisation in your data?"
    You: "One sign is runs whose diff is almost the same text as the merged diff. I'd measure that similarity for every run and compare old and new tasks. If near-copies show up mainly on old tasks, that's a warning that memory, not the task text, shaped those runs."
  3. Prof: "How many of your tasks will actually be after the cutoff?"
    You: "It depends on the models I pin. For the models Gloaguen et al. used, including Qwen3-30B-Coder in my harness, only 12% to 40% of the 138 came before the cutoff, so most are already after it. If I pin newer Claude or GPT models in 2027, probably none are, since the newest of the 138 was merged in January 2026, so for those the after-cutoff tasks have to be the newer pull requests I add."

Q40. Why only Python, and how far do the results generalise?

  1. Prof: "You say the method carries over. What would you change to run it on TypeScript?"
    You: "Mainly the input generator and the output comparison. TypeScript's types disappear when the code runs, so I'd read them from the source and generate values with fast-check, its property-based testing library. The statistics, ρ and the vote, don't depend on the language at all."
  2. Prof: "Agents change every few months. Is a ρ measured on 2027 agents still useful in 2028?"
    You: "The exact number probably not.   3. Prof: "With one round of agents, how would you know the pattern isn't specific to them?"

Q41. Real users don't send random inputs. Isn't your input distribution arbitrary?

Partly, yes. A failure probability only means something for a stated input distribution, and p and ρ both depend on it. Follow-ups (each builds on your last answer)

  1. Prof: "Why would the ranking stay the same when p changes? Give me a case where it flips."

  2. Prof: "If it flips, which distribution do you believe?"
    You: "Neither alone: I'd report both and say the ranking depends on which inputs matter.   3. Prof: "Could you get closer to real use without any user data?"
    You: "Partly. I could run the repository's own test suite, log the arguments each entry point actually receives, and build a third distribution from those.   1. Prof: "Why do you think voting helped little with the weaker models?"
    You: "I haven't read your results, so this is only my guess from Eckhardt and Lee. On an input where a version fails with chance θ, a vote of three fails with 3θ² - 2θ³, and that's below θ only when θ is below one half. A weak model has more inputs where most of its versions are wrong, and there the vote makes things worse."
  2. Prof: "Show me that it's below θ only when θ is below one half."
    You: "Take θ minus the vote failure: θ - 3θ² + 2θ³, which factors as θ(1 - θ)(1 - 2θ). Between 0 and 1 the first two factors are positive, so the sign is the sign of 1 - 2θ: positive below one half, zero at one half, negative above. For example, θ = 0.3 gives a vote failure of 0.216, but θ = 0.7 gives 0.784."
  3. Prof: "And with five versions instead of three?"
    You: "It pushes further both ways. At θ = 0.3 a vote of five fails with about 0.163, lower than 0.216, and at θ = 0.7 with about 0.837, higher than 0.784. So adding versions helps only on inputs where most versions are right, which would fit weak models gaining little."

Q46. Ron et al. already asked whether changing the agent, model or language removes shared failures. What's new in your RQ1?

Three things. They used one specification, the Knight and Leveson one, and I use real repository tasks with a developer's own context file. They had one version per configuration, and they say themselves that they measure diversity across configurations, not variation within one; I have 10 runs per setting. And I estimate the size of the dependence, ρ and the vote failure, not only test independence with z.

If he pushes ("What did they find?"): "That changing the harness, model and language did not make the failure correlation go away. But voting over three programs still cut the mean failure count from 387 to 131."

Follow-ups (each builds on your last answer)

  1. Prof: "Ron et al. say rerunning would likely change their exact failure counts. Why is that variation worth studying, and not just noise?"
    You: "Because rerunning the same agent with the same file is the cheapest redundancy a team has, and it's where I'd expect the most sharing: same model, same prompt, same file. Nogueira et al. point that way: three versions from one model got only 0.27 of the gain independence allows, against 0.44 when the models differed."
  2. Prof: "But 0.27 of the gain is still a gain. Ron et al. had shared failures too, and their votes still cut the mean failure count from 387 to 131. How?"
    You: "Because the mean hides the shape. The median was 0 for single versions and for triples alike, and voting mainly removed the very bad versions: the worst single version failed on 10,469 of a million inputs, but the worst triple only on 419. Voting removes failures a version has alone, not the ones several versions share."
  3. Prof: "Then what is that 419?"
    You: "Most likely the failures the versions share. In their Table III, 419 is also the number of inputs where two or more programs fail together within each language, and the Rust programs fail only on conditions 9 and 14, where many programs used the wrong circle. So I'd guess the worst triples hold two versions with that same mistake, but I'd check their released data before saying so."

Q47. And compared with Nogueira et al.?

They used 224 contest problems, with no repository and no context file, and five samples per setting at temperature 0.6. Their pairwise score assumes that, under independence, every test is equally likely to fail, and they name that as a limitation because tests differ in difficulty. That is exactly the Eckhardt and Lee point, and the Beta distribution over θ is how my model handles differences in input difficulty.

If he pushes ("Anything else from them?"): "No combination of models beat the strongest single model, and three versions from one model captured only 0.27 of the possible gain. That's why I compare changes of agent and model."

Follow-ups (each builds on your last answer)

  1. Prof: "What exactly does their pairwise measure compare?"
    You: "For two versions that fail F_i and F_j of the T tests, it compares how many tests both fail with F_i times F_j over T, the overlap you'd expect if each version's failed tests were a random pick from all T. It divides the difference by its standard deviation, so it's like a z for one pair."
  2. Prof: "If some tests are harder than others, which way does that push it?"
    You: "Up. Hard tests attract failures from both versions, so two versions share more than F_i F_j over T even if they were written independently, and part of what the measure calls correlation is just difficulty. They reduce that by treating standard tests and edge-case tests separately, and they say difficulty can still vary inside each group."
  3. Prof: "But in Eckhardt and Lee's model, varying difficulty is the dependence. So what is left to separate?"
    You: "Nothing, in their model: versions from one process fail together exactly because inputs differ in difficulty. So I don't try to remove it, and ρ measures all of it. What my design adds is a cause I can change: on the same inputs I compare ρ with the rule and with neutral text, which shows how much of the shared difficulty the rule creates."

Q48. Gloaguen et al. and Zhang et al. already test context files. Why isn't that enough?

Both measure whether the task's tests pass. Gloaguen et al. ran each agent once per task and name aspects beyond task success as future work, and Zhang et al. used one agent with one model. I run each setting 10 times and test beyond the tests, so I can see failures that pass the tests and whether the runs share them. As far as I know, nobody has combined those on real tasks with a developer's own file.

Follow-ups (each builds on your last answer)

  1. Prof: "How do you know there are failures beyond the tests to find?"
    You: "For my tasks I don't yet; the pilot will show it. There are two hints: Gloaguen et al.'s tests cover 75% of the changed code on average, and Xia and Miller found that within 180 days of merge, bug-fixing commits changed 4.0% of agent-written lines against 2.7% of human-written ones."
  2. Prof: "Couldn't that gap just mean agents work in buggier parts of the code?"
    You: "They took some care: they adjusted for the role of each file and compared lines within each repository. But they also say a changed line isn't always a defect, and they found that almost half of the later changes to agent-written lines came from agent commits themselves."
  3. Prof: "Why does that last point matter?"
    You: "They read it as agents working on their own code, in a different part of the code base than humans, so 4.0% against 2.7% partly compares different code, not only different authors. That's why I prefer a controlled comparison: every run gets the same task, the same code and the same inputs, and only the setting changes."

12. If the results are null

Q49. If ρ comes out close to zero, has the study failed?

No. It would mean that on these tasks the runs fail almost independently, so the simple vote formula works and extra runs are worth paying for. That would differ from Ron et al. and Nogueira et al., so it's worth reporting with intervals. I'd first check that ρ is not near zero only because almost nothing fails.

Follow-ups (each builds on your last answer)

  1. Prof: "How could ρ come out near zero only because almost nothing fails?"
    You: "If failures are rare, most inputs have no failing run and the rest have just one, and a count of one can't show sharing. Then the fit puts ρ near zero, but that only means I never saw two runs share a bug. So I'd report the bootstrap interval and the number of inputs with any failure, and call that setting inconclusive, not independent."
  2. Prof: "Give me an example."
    You: "Imagine each run has a one-in-ten chance of a bug that fails on the same ten inputs. Then θ is 0.1 on those inputs, which gives a ρ of about 0.1. But with 10 runs, about 74% of the time that bug shows up in at most one run, so no input ever has two failing runs, and the fit says ρ is zero or has nothing to fit."
  3. Prof: "So would you add inputs or runs?"
    You: "Runs. More inputs only add more inputs where that single run fails, while with 20 runs the chance of seeing the bug in at least two runs rises from about 26% to about 61%. Runs are the expensive part, so I'd add them only for settings where the pilot shows this problem."

Q50. What if no version fails on any generated input?

Then I report an upper bound: 0 failures in 10,000 inputs means the failure probability is likely below about 0.0003. ρ can't be estimated there, and I'd say so. I can't promise failures; the pilot will show whether there are enough, and if not, I'd choose other tasks.

Follow-ups (each builds on your last answer)

  1. Prof: "Where does 'below about 0.0003' come from?"
    You: "From the rule of three. If the failure probability were p, the chance of no failure in n independent inputs is (1 - p) to the power n, about e to the minus np. Setting that equal to 0.05 gives np = ln 20, which is about 3, so the 95% upper bound is about 3 over n, here 3 in 10,000."
  2. Prof: "Is 3 in 10,000 good enough for a team?"
    You: "It depends on how often the function runs. If it's called a million times a day with inputs like mine, 3 in 10,000 still allows up to about 300 failures a day, so for busy code 10,000 inputs can't promise much."
  3. Prof: "How many inputs would you need to show one in a million?"
    You: "By the same rule, about 3 million inputs with no failure. For a small function without side effects that's cheap to run, so the count isn't the hard part. The hard part is that the bound holds only for my declared distribution, and at one in a million, whether that distribution matches real use matters far more than the number of inputs."

Q51. What if replacing the rule changes nothing in reliability?

If the checker shows the agents did write different code, then "no change in reliability" is a real result: the rule changed the code but not how often it fails. If the checker shows no change, the manipulation failed for that rule, so I'd replace the rule instead of reporting a null.

Follow-ups (each builds on your last answer)

  1. Prof: "If you swap a rule whenever the manipulation fails, aren't you searching until you find an effect?"
    You: "It would be, if I decided after seeing reliability. I decide only from the checker, whether the code changed, before I look at any failure probability, and I'd report every rule I tried, including the ones I dropped."
  2. Prof: "How do you make sure you decide before looking?"
    You: "The checker reads only the code, so I can run it on every run's change before I generate a single input. I'd write down the condition for dropping a rule first, for example how big a gap in compliance I need between the two file versions, and only then run the inputs."
  3. Prof: "With 10 runs per file version, how big a gap can the checker even show?"
    You: "Only a big one: even 8 of 10 runs following the rule against 3 of 10 gives a two-sided Fisher exact p of about 0.07. But a rule has 2 tasks and 2 agents, so 40 runs per file version, and the same rates, 32 of 40 against 12 of 40, give p below 0.0001. So I'd judge each rule on all its runs, not on one task."

Follow-ups (each builds on your last answer)

  1. Prof: "Which parts of BCS301 would you actually use?"
    You: "The binomial distribution, mean and variance, and covariance and correlation from the part on joint distributions. ρ is the correlation between two runs failing on the same input, and Var θ is just E[θ²] minus p². What the course didn't cover is fitting a model like mine by maximum likelihood, and that's the Year 1 part."
  2. Prof: "What would maximum likelihood maximise in your model?"
    You: "The probability of the counts I observe. For each input I take the beta-binomial probability of its number of failing runs, multiply over all inputs, and choose a and b to make that product as large as possible, in practice its logarithm, with a numerical optimiser."
  3. Prof: "Write that probability for one input."
    You: "If y of k runs fail, it's k choose y, times B(y + a, k - y + b), divided by B(a, b), where B is the beta function. It comes from averaging the binomial probability, θ to the y times (1 - θ) to the k - y, over the Beta distribution of θ."

Q54. How does your BrandMemory work connect to this proposal?

It taught me that a rule can be written down and still never reach the model: the brand voice section had the lowest priority and was the first cut by a 3,200-character limit. After the fix, one A/B comparison showed contractions falling from 6 to 0. One comparison is not a study, but it's why my design has a manipulation check: I don't assume a rule was followed, I check it.

Follow-ups (each builds on your last answer)

  1. Prof: "How did you find out the rule never reached the model?"
    You: "Projects with BrandMemory on logged that the guidance was applied, but the output showed no trace of the brand voice, and pairs with it on and off looked almost the same. So I traced what the model actually received, and the brand voice section was the first thing cut at the 3,200-character limit."
  2. Prof: "What did you change?"
    You: "I removed the 3,200-character limits per feature and raised the overall limit from 6,000 to 30,000 characters. I also turned off our default house style when a brand voice is active, because its rules were winning over the brand's rules that did arrive."
  3. Prof: "Why was the house style winning?"
    You: "It used strong words like 'MANDATORY' and came with six fixed examples, and the model followed those over the brand's rules. It taught me that how a rule is worded and where it sits can matter as much as what it says, which is one reason my neutral text has about the same length as the rule and sits in the same place."
