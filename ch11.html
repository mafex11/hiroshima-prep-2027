Chapter 11 of 28

Questions on your proposal

When and how long: Sunday: sections 1 to 5 and 11 out loud. The rest before the oral exam.

These are the questions Prof. Zheng (Monday 2 Nov) or the oral exam panel could ask about your research proposal, section by section, each with a short model answer in your voice. It goes deeper than the 15-question bank in 03_Research_Plan_Defense/05_question_bank_with_model_answers.md and repeats only a few of its questions, with more detail. Anything marked [FILL] or [CONFIRM] is yours to complete or check before you say it.

How to use it

  • Say the first sentence of an answer, then stop and let him ask more. The "If he pushes" lines are for the follow-up.
  • Every number about your plan matches the proposal you sent. Paper facts come from the paper texts in paper_text/. For the lab's N-version paper [1] you have read only the abstract, so never quote anything else from it.
  • The official guideline says the oral exam (online, between 24 Nov and 2 Dec 2026) evaluates "knowledge in the specialized field, application capability, and problem-solving abilities" (https://www.hiroshima-u.ac.jp/system/files/302259/M%E5%A4%96%E5%9B%BD%E4%BA%BA%EF%BC%88%E5%9B%BD%E5%A4%96%EF%BC%89%E5%8B%9F%E9%9B%86%E8%A6%81%E9%A0%85%EF%BC%88%E8%8B%B1%E8%AA%9E%E7%89%88%EF%BC%89202704.pdf). So expect the maths in sections 2, 4, 5 and 8 at the exam too, not only on Monday.
  • Examples that start with "imagine" use made-up numbers. They are not results.

1. The problem and why it matters

Q1. Why would anyone run a coding agent several times on the same task?

In Gloaguen et al.'s numbers one run costs at most about one and a half US dollars, and each run can give a different patch. So it is natural to run a few and pick one, like the versions in N-version programming. My question is when that really buys reliability, and when the runs only repeat the same bug.

If he pushes ("Do teams really do this?"): "I don't have numbers on how often teams do it. [CONFIRM: add "I sometimes rerun an agent at work and compare the results" only if true.] My point is that it's cheap, so a team needs to know when it helps."

Q2. Why do you call the context file "part of the specification"?

Besides the code itself, the agent learns what to build from the task text and the context file. In Ron et al., who reused the Knight and Leveson specification, many shared failures traced back to parts of it that are hard or ambiguous. Every run in a repository reads the same file, so a rule in it can play the same role.

If he pushes ("Most rules are about commands, like how to run the tests."): "Yes, and I don't use those. I pick only rules that change what code is written, like which helper to use, because only those can change how the code behaves."

Q3. Is this really a reliability question, or a software engineering question?

The main quantity is a probability: how often two or three runs fail on the same input, and what that does to a vote. That is the Eckhardt and Lee question, and it needs a probability model with intervals. Whether agents follow a rule is the software engineering part, and I keep it only as a manipulation check.

Why he asks: this is a reliability lab. He wants to see that the core of the plan is the probability model, not rule compliance.

Q4. Give me a concrete example of one rule making every run fail together.

For example, imagine the file says "round money with round_cents()", and that old helper turns any negative value into 0.0. A task asks for a discount function, and its tests use only positive prices. Most runs follow the rule and pass the tests, but on a refund, which has a negative price, they all return 0.0. So they fail on the same inputs with the same wrong answer.

If he pushes ("So voting can't fix it?"): "Right. If 7 of 9 versions share the bug, the majority is wrong on those inputs, so the vote is wrong too."

2. Eckhardt and Lee

Q5. In your study, what is the "development process", and what is a "version"?

A process is one setting on one task: one agent, one model and one file version, and in my harness one temperature. A version is one run of that setting that passes the task's tests. Drawing a version at random means starting one more run in a clean container.

If he pushes ("Are your runs really independent draws?"): "Given the setting, I treat them as exchangeable: same container image, no shared state, no git history. A provider quietly changing the model would break that, so I pin the CLI and model versions, record them for every run, and would run all settings of a task over the same few days."

Q6. Please show why two runs both fail with probability p² + Var θ.

Draw an input X. Given X, the two runs fail independently, each with chance θ(X), so both fail with θ(X)². Averaged over inputs that is E[θ(X)²], and by the definition of variance E[θ²] = (E[θ])² + Var θ = p² + Var θ. So joint failure equals p² only when θ is the same on every input.

If he pushes ("Is Var θ = 0 ever realistic?"): "Only if every input is equally hard, and I don't expect that for real code. An empty list or a negative value is usually harder than a typical input. Imagine half the inputs have θ = 0 and half have θ = 0.4: then p = 0.2 and p² = 0.04, but the real joint failure is 0.5 x 0.16 = 0.08."

Q7. Eckhardt and Lee also showed that more versions can be worse than one. When does that happen?

It needs θ(x) above 0.5 on a set of inputs with positive probability. There most versions are wrong, so as N grows the system failure tends to the probability of the inputs where θ is above 0.5. If that is bigger than p, many versions are worse than one. A strong rule that sends every run to a buggy helper is exactly that case.

Why he asks: to see if you know the theory beyond one formula. The report version also says system failure probability does not always fall as N grows.

3. RQ1 and RQ2

Q8. In RQ1, how do you compare the four changes: file version, agent, model and temperature?

For two settings a and b, both fail with p_a p_b + Cov(θ_a, θ_b), so I estimate that covariance on the same inputs. I compare four changes this way: file version, agent, model and temperature. The change with the lowest correlation is the best way to get diversity.

If he pushes ("Which settings exactly?"): "Agent: Claude Code against Codex, which also changes the model. Model: GPT-5.2 against the smaller Codex model. Temperature: my harness at its two temperatures. File: the original against the neutral file, within one agent. I compare correlations, not covariances, because the failure rates differ."

If he pushes ("How do you estimate the covariance?"): "On each input, setting a has Y_a failing runs out of k_a, and b has Y_b out of k_b. Runs from different settings are independent given the input, so the average of Y_a Y_b / (k_a k_b) over inputs estimates E[θ_a θ_b]. Then I subtract p_a p_b."

If he pushes ("Eckhardt and Lee is about one process. What covers two?"): "That is Littlewood and Miller's idea of forced diversity, where versions come from different methods. I know it from how Ron et al. describe it [CONFIRM: add "and from its abstract" only if you read it], so I didn't cite it. In my formula the covariance can even be below zero, which would mean two settings fail together less often than independence predicts."

Q9. Your design is not fully crossed. Temperature changes only in your harness, and the second model runs only in Codex on the original file. Isn't that confounded?

Yes, partly. The temperature result holds only for Qwen3-30B-Coder in my harness, and the model result only inside Codex on the original file. I don't vary temperature in the CLIs, since as far as I know neither documents a temperature setting. Adding the neutral file to the smaller model and my harness would add 300 runs, about 42 to 52 dollars, so I could add it if the pilot cost is fine.

If he pushes ("And Claude Code against Codex?"): "That changes the harness and the model together, Sonnet 4.5 against GPT-5.2. Only the two Codex models separate the model from the agent. So I report each comparison with its own baseline and don't claim one general ranking."

Why he asks: to check that you limit your claims honestly.

Q10. In RQ2, why replace the rule with neutral text instead of deleting it?

Deleting also makes the file shorter. Zhang et al. found that random rules raised the pass rate about as much as curated ones, so just having rules in the file seems to matter. Neutral text of about the same length keeps that fixed, so the difference I measure is the rule's content.

If he pushes ("What is neutral text?"): "A sentence of about the same length with no instruction in it, for example a line about the project's history. The checker then shows whether the agents stopped following the rule."

If he pushes ("Was that significant?"): "Not on its own. Every rule set beat no rules by 7 to 14 points, but the closest comparison with no rules had p = 0.077."

Q11. Which direction do you expect in RQ2?

I don't assume one. In Zhang et al., prohibitions such as "do not refactor unrelated code" helped the pass rate, so a rule can protect. In my helper example the rule makes things worse beyond the tests. That's why RQ2 measures both the test pass rate and the failure probability beyond the tests.

If he pushes ("So prohibitions clearly help?"): "Not clearly. In Zhang et al. only that one rule was significant on its own, and they say it would not survive a strict correction for many comparisons."

Q12. How will you analyse RQ2, and can about 10 tasks detect anything?

I compare the two file versions in a mixed model with task as a random effect, so one hard task doesn't drive the result. With about 10 tasks it can only detect a large effect. So I'll report the estimate with its interval, plus the result per rule, and call it an estimate on 10 tasks, not a general law.

If he pushes ("Inputs inside one run are not independent."): "That's right. Failures inside one run are linked, so I should add run as a random effect inside task, or first summarise each run by one failure probability. I'd like your advice on which is better."

If he pushes ("Why not more tasks?"): "Each task needs a checked rule, an input generator and 20 hand-checked disagreements, plus the run costs. If the pilot is cheaper than I expect, more tasks is the first thing I'd add."

4. The beta-binomial model and ρ

Q13. What exactly is random in your model?

Two things. The input X is drawn from the distribution I declare, and given X, each run of setting s fails with chance θ_s(X). The Beta distribution describes how θ spreads across inputs. The runs are a sample from the setting, which is why the bootstrap resamples runs.

Q14. Write down the beta-binomial quantities you use.

If θ follows Beta(a, b), the mean failure probability is p = a/(a + b) and ρ = 1/(a + b + 1). Then Var θ = ρ p(1 - p), so two runs both fail with p² + ρ p(1 - p). The number of failing runs out of k has variance k p(1 - p)[1 + (k - 1)ρ], which is larger than the binomial k p(1 - p) when ρ > 0.

Q15. In plain words, what does ρ mean, and why use it instead of the Knight and Leveson z?

ρ is the correlation between "run 1 fails" and "run 2 fails" on the same random input. Zero means one run failing tells you nothing about another, and one means they always fail together. z is a test statistic that grows with the number of inputs and depends on each version's failure rate. ρ is a number between 0 and 1 that measures how strong the dependence is, and it goes straight into the vote formula.

If he pushes ("So what is z for?"): "It's my baseline, so I can compare with Ron et al. ρ is my main measure."

Q16. Why a Beta distribution? What if it fits badly?

θ lies between 0 and 1, and the Beta is a simple two-parameter family there with a closed-form likelihood. But I expect most inputs to have θ = 0 and a few to be hard, and one Beta may not fit that well. Then I'd try a zero-inflated beta-binomial or a mix of two Betas, and compare them by AIC and by how well they predict the observed vote failures.

If he pushes ("You fit per task? That's a lot of fits."): "Yes, one per task and setting. Each task has 7 settings, so about 70 fits for 10 tasks. If the intervals are too wide, a hierarchical model that shares information across tasks is the next step."

If he pushes ("Settings will have different numbers of admitted runs."): "The beta-binomial allows a different k per setting, so a setting with 7 admitted runs just has k = 7. Fewer runs means less information, and admission says something by itself, so I report the test pass rate next to ρ."

Q17. Do you even need the Beta assumption to estimate the vote failure?

Not for small N. If Y of k runs fail on an input, the average of Y(Y - 1)/(k(k - 1)) over inputs estimates E[θ²] with no assumption, and Y(Y - 1)(Y - 2)/(k(k - 1)(k - 2)) estimates E[θ³]. So I can estimate E[3θ² - 2θ³] directly and use it to check the Beta fit.

If he pushes ("Then what does the model add?"): "One ρ per setting to compare, smoothing when few runs are admitted, and answers for N larger than the number of runs I have."

Why he asks: to see whether you know what the model adds over plain counting. It is also a reason for 10 runs: with 3 runs you could check only the 2-out-of-3 vote directly, and with 10 you can check larger votes too, up to the number of admitted runs.

Q18. Why does the bootstrap resample runs and not inputs?

The same runs meet all 10,000 or more inputs. If one run has a bug, it fails on many inputs at once, so the inputs are not independent information about the setting. Resampling runs keeps that structure, and resampling inputs would make the intervals much too narrow.

If he pushes ("With about 10 runs, that bootstrap is rough."): "Yes, it is. A hierarchical or Bayesian model across tasks may give better intervals, and I'd like your advice. Your lab's page mentions interval estimation by parametric bootstrap, and that is one of the things I want to learn here."

5. 2-out-of-3 voting

Q19. Is a vote over dependent runs always worse than a vote over independent ones?

The vote fails with 3E[θ²] - 2E[θ³], against 3p² - 2p³ under independence. If θ stays below 0.5 on every input, 3θ² - 2θ³ is convex there, so by Jensen's inequality the vote fails at least as often as the independent formula says. If θ is above 0.5 on some inputs, Jensen doesn't apply directly, so I compute both numbers from the fitted model.

If he pushes ("Derive 3θ² - 2θ³."): "The vote fails if two or three of the three runs fail: 3θ²(1 - θ) + θ³ = 3θ² - 2θ³."

Q20. Classic N-version programming votes on every input at run time. A team merges one patch. So what does voting mean here?

A team wouldn't run three patches in production. It would run all the patches on generated inputs and pick the one whose outputs agree with most of the others. If most runs share a bug, the picked patch has it. The model predicts how often the majority is wrong, and I can also measure directly how often the picked patch fails against the merged code.

If he pushes ("Are those the same number?"): "No. The per-input vote is the classic N-version number. The picked patch is one fixed program, so it can be right where the majority is wrong, and the other way round. I'd report both."

If he pushes ("Two wrong outputs may differ. Is that still a vote failure?"): "In my formula, yes, so it is on the safe side. A real voter could notice two different wrong answers. I can count separately the inputs where the wrong outputs are identical, because that is the dangerous case."

Q21. How do you find the best number of runs N?

I minimise c_run N + c_fail P(majority of N fails) over odd N. P(majority of N fails) is the binomial tail with θ(X), averaged over inputs with the fitted model. When ρ is near zero, extra runs lower it quickly. When ρ is near one, extra runs only repeat the same bug, and the best N can be 1.

If he pushes ("Where do the costs come from?"): "c_run I can measure: it's the cost of one run. c_fail depends on the team, so I'd show the best N for a range of ratios c_fail / c_run, not one number."

If he pushes ("Does the failure probability always fall with N?"): "No, Eckhardt and Lee showed it may not. That's why I compute it from the fitted θ distribution for each N instead of assuming it falls."

Why he asks: it is a "best value" trade-off, the same kind of question as finding the best rejuvenation time in his own work. You can say that in one line, but don't go into his papers' details.

6. Design: tasks, rules, agents, runs and costs

Q22. In Gloaguen et al.'s tasks, are those really the pull requests' own tests?

Mostly not. Gloaguen et al. say most of these pull requests didn't add or change tests, so an LLM agent wrote new tests from the task text and the merged change. They checked that those fail before and pass after, reviewed them by hand, and added the existing repository tests that pass on the merged code. On average the tests cover 75% of the modified code, which leaves room for failures beyond them.

If he pushes ("So what do you mean by the pull request's tests?"): "In my proposal it means the task's test set."

If he pushes ("Does the agent see these tests?"): "In my setup, no. I add the task's tests only after the run ends, so the agent can't fit its code to them."

If he pushes ("And the newer pull requests you add?"): "I'd use the PR's own tests where it has them. Otherwise I'd write tests the same way and check by hand that they fail before and pass after."

Q23. Their task texts are written by an LLM too. Couldn't a task text mention the rule?

It could. Their task texts are written from the PR description, the issue and the merged change, with an instruction not to leak the solution. I'll read every task text I use, and if it names the helper or pattern the rule names, I'll remove that sentence or drop the task, so I test the file and not the prompt.

Q24. How will you choose the rules?

I'll read the developer-written files of the 12 repositories and keep rules that a script can check in the diff and that change what code is written, like which helper, library or error type to use. I want about 5 rules, each with 2 tasks where it matters, meaning the merged change touches code where the rule applies. I haven't picked them yet; that's part of the pilot.

If he pushes ("Which rules would you not pick?"): "Rules like 'put tests in tests/' or 'run pytest -q'. They change where files go or how to run things, not how the code behaves. [CONFIRM: optional own example: "At work I added a rule to always write a migration file instead of changing the shared database directly. It's a good rule, but it's about process, so it wouldn't fit RQ2."]"

If he pushes ("Why Cohen's kappa? Isn't 90% agreement enough?"): "Kappa corrects for chance. If 90% of runs follow a rule, a checker that always says 'yes' already gets 90% agreement but a kappa of zero. So I need both."

Q25. Why screen tasks first, and why keep tasks an agent always solves?

A task no run can solve gives no admitted versions, so I drop it, as Zhang et al. did; in their pilot 27% of tasks were never solved. They also dropped always-solved tasks, because they measured only the pass rate. I keep them, because a run that always passes the tests can still fail on generated inputs, and those tasks give the most versions.

If he pushes ("How much screening?"): "About 20 candidate tasks, 3 runs per agent, two agents: 120 runs."

Q26. Why Claude Code and Codex, and why your own harness as well?

They are the agents I use every day, and they read the two common file names, CLAUDE.md and AGENTS.md. Gloaguen et al. also give per-task costs for these agents, on these tasks and on SWE-bench Lite. Codex also runs a second, smaller model, so the agent stays fixed while the model changes. My own harness, written in plain Python as I built Yuki 2.0, shows me the exact prompt and lets me set the temperature, which, as far as I know, neither CLI documents.

If he pushes ("Gloaguen et al. say they set temperature 0 in both CLIs."): "Yes, they report that. As far as I know, neither CLI documents a temperature setting, so I'd rather not depend on it. In my harness I control it directly."

If he pushes ("Isn't your harness much weaker than the commercial agents?"): "Probably, and it runs a smaller open-weight model. So I treat it as a third agent, not a copy of the others, and the temperature comparison holds only inside it."

Q27. Which two temperatures, and how will you run Qwen3-30B-Coder?

I haven't fixed them yet. Gloaguen et al. used 0.7 with top-p 0.8 for this model, so 0.7 is a natural first value, with a low value as the second [CONFIRM: your choice, for example 0.2]. They ran the model locally with vLLM and estimated its cost from OpenRouter prices. I'd do the same if I have a GPU, or else use a hosted API.

Q28. Walk me through the 820 runs and the cost.

Main runs: 10 tasks x 2 file versions x 2 agents x 10 runs = 400. On the original file only: the second Codex model, 10 tasks x 10 runs = 100, and my harness, 10 tasks x 2 temperatures x 10 runs = 200. Screening: about 20 tasks x 3 runs x 2 agents = 120. At the per-task costs in Gloaguen et al., that's about 420 to 590 US dollars.

If he pushes ("Break the cost down."): "Claude Code is most of it: 260 runs at 1.15 to 1.51 dollars, about 299 to 393. Codex with GPT-5.2: 260 runs at 0.32 to 0.57, about 83 to 148. The smaller model: 100 runs, about 18 to 22. Qwen: 200 runs, about 24 to 30."

If he pushes ("Are those costs from these tasks?"): "The ranges cover both benchmarks in their Table 2. On their 138 tasks alone, Claude Code was 1.15 to 1.33 dollars and Codex with GPT-5.2 0.38 to 0.57."

If he pushes ("Newer models cost more. Who pays?"): "Yes, Zhang et al. report about 5 dollars per task and condition with Claude Opus 4.6. In my proposal I wrote that I'd ask whether it fits a lab budget. If it doesn't, I'd move more runs to the open-weight model, which costs about a tenth of Claude Code per task. [CONFIRM: add "but I don't expect the lab to pay" or "I can pay for a small pilot myself" only if you really mean it.]"

Why he asks: to see that you know your own numbers. Never say or hint that the lab must pay.

7. Failures beyond the tests: inputs, oracle and checks

Q29. How will you generate the inputs in practice?

A property-based testing library such as Hypothesis can build values from Python type hints, and I'd mix those with the values used in the task's tests. For each entry point I write the distribution down before the runs: types, ranges and the share of test values. At least 10,000 inputs per entry point.

If he pushes ("Is 10,000 enough?"): "If a version fails on 1 in 1,000 inputs, I see about 10 failures. If it fails on none, its failure probability is likely below about 3 in 10,000, by the rule of three. Running a function is cheap, so I can add more where needed."

If he pushes ("Why only the functions the tests call? Bugs can be in helpers."): "Every admitted version must implement the functions the tests call, so I can compare all versions there. A helper one run invents may not exist in another run. A helper bug that matters still shows up through the entry point that uses it."

If he pushes ("What about objects, files or network calls?"): "Those I can't generate this way, so I skip them and report how many I skipped. That's the limit in my proposal: only functions whose inputs can be generated."

Q30. How do you tell a real failure from an input that is simply illegal?

Some disagreements come from inputs the project never allows, like a negative quantity. I read 20 disagreements per task, check the docstring, the tests and how the function is called in the code base, and drop inputs that are outside the real domain or where the merged code itself is wrong. If many inputs get dropped, I narrow the declared distribution and say so.

If he pushes ("What if the code uses time or randomness?"): "I'd fix the random seeds and run the merged code twice on each input. If it disagrees with itself, I drop that input or entry point. For flaky tests at admission, I re-run them and drop flaky tasks."

Q31. Admission requires passing the tests. Doesn't that bias your failure probability?

It makes it conditional on passing, and that's on purpose: a run that fails the task's tests is not a working version, as in Knight and Leveson's acceptance test. But a file version that lets more runs pass could also admit weaker versions. That's why RQ2 reports the pass rate and the failure probability beyond the tests side by side.

8. The lab's methods: boundary values, NHPP and pysrat

Q32. (Prof. Okamura) Our BCD paper found boundary points by hand. How do you get them automatically?

I take branch conditions in the merged code that compare a parameter with a constant, like if percent > 100, and use 100 and its neighbours one minimal step away as boundary points. Your paper's Remark 2 says that boundaries from execution paths differ from boundaries defined by outputs, so I say clearly that mine are path-based. The pilot will report how many functions even have such conditions.

Q33. Why use BCD only as a stress test, and how will you judge it?

30 to 50 chosen inputs are not a random sample from the declared distribution, so they can't give a failure probability. I use them to find boundary bugs the random inputs miss, and I compare the input sets with mutants of the merged code. A mutant is killed when its execution path differs, as in your paper, here from coverage.py branch data, and I also report kills by different outputs.

If he pushes ("What about strings and lists?"): "Your paper leaves non-numeric inputs as future work. I'd try one-element edits, adding, removing or changing one element, as the minimal operations, and see whether the distance still makes sense."

Q34. Why doesn't a finite-fault NHPP fit agent code, and what do you use instead?

In a finite-fault model like Goel-Okumoto, m(t) = ω(1 - e^(-bt)): one fixed code base holds ω faults on average, and testing finds them over time. Where agents keep merging changes, new faults keep arriving, so ω is not fixed. Instead, each merged change brings its own faults, and each fault is found after a delay.

If he pushes ("Write it down."): "Change j brings ω_j = L_j exp(β'z_j) faults on average, each found after a delay with distribution G, so m(t) = Σ_j ω_j G(t - τ_j). With one change at time 0 and an exponential G, this reduces to Goel-Okumoto."

Q35. Why do you call that an infinite-server queue?

Faults "arrive" with each merged change and "leave" when they are found, and they don't wait for each other. So it is like an M/G/∞ queue where each fault's stay has distribution G, and if each change brings a Poisson number of faults, the number found by time t is Poisson with mean m(t). Dohi, Osaki and Trivedi used this view to unify finite and infinite fault NHPP models.

If he pushes ("Have you read that 2004 paper?"): "Only the title and abstract so far. [CONFIRM: change this if you read it before you speak.]"

Q36. How would you fit it, and where does pysrat come in?

I'd treat the fix times as an NHPP with intensity Σ_j ω_j g(t - τ_j) and maximise the usual log-likelihood: the sum of the log intensities at the fix times, minus m(T). pysrat gives the families for G, such as exponential, gamma and log-normal.

If he pushes ("Have you used pysrat?"): "Not yet. [CONFIRM: change this if you install it and run an example.] I'd ask Prof. Okamura whether its metrics-based or PR-NHPP models can already handle changes that each start at their own merge time."

Q37. Where does the fix data come from, and is there enough?

From about 20 AIDev repositories. I'd find fix commits from their messages and link them to agent-written lines, the way Qiu et al. built datasets from GitHub issue histories. Counts per repository will be far below theirs: 104 to 397 faults per dataset, and 183 to 290 in their four GitHub datasets. So I'd pool repositories and share β across them. That's why this part is "if time permits".

If he pushes ("AIDev stops in 2025."): "Yes, its dataset cutoff is 1 August 2025. So I'd use it to choose repositories and then collect their newer commits myself."

If he pushes ("How is this different from Xia and Miller?"): "They model the hazard that one line is touched by a bug-fixing commit, with Fine-Gray competing risks. My model gives the expected number of faults not yet found, which is what a reliability growth model is for."

9. Threats to validity

Q38. What is the biggest threat to your results?

The oracle. The merged code is my reference, so if the human made the same mistake, for example used the same buggy helper, my testing can't see it. That is exactly the shared-helper case my study is about, so I may undercount the failures I care about most. The hand check catches the opposite case, where the merged code is wrong and the runs are right.

Q39. Couldn't the models have seen these pull requests in training?

Yes, some may be in the training data. I add newer pull requests merged after the training cutoff where possible, and I report old and new tasks separately. Gloaguen et al. checked this on their tasks: 12% to 40% of tasks came before the cutoff, depending on the model, and success did not differ significantly.

Q40. Why only Python, and how far do the results generalise?

The benchmark is Python, and type hints make input generation possible; Gloaguen et al. also name Python-only as a limit. It's about 10 tasks, two commercial agents at fixed versions and one open-weight model, and agents change every few months. What should carry over is the method, so I'll release all tasks, code and data for others to rerun on new agents.

Q41. Real users don't send random inputs. Isn't your input distribution arbitrary?

Partly, yes. A failure probability only means something for a stated input distribution, and p and ρ both depend on it. I have no real usage data for these functions, so I declare the distribution before the runs and mix in the values the tests use. I can also check whether the ranking of settings stays the same under a second, narrower distribution, for example only values near the test values.

11. What is new

Q45. What did you take from our N-version paper's abstract, and what do you add?

I've read only the abstract. Two points shaped my plan: voting helped with strong models, but the benefit was limited with weaker ones, and more diversity did not always mean more reliability. What I add is real repository tasks, the shared context file as a possible cause, and a fitted coincident-failure model for the vote and the best number of runs.

If he pushes ("How did those points shape it?"): "I don't assume a change between runs helps. RQ1 measures which change lowers shared failures."

Q46. Ron et al. already asked whether changing the agent, model or language removes shared failures. What's new in your RQ1?

Three things. They used one specification, the Knight and Leveson one, and I use real repository tasks with a developer's own context file. They had one version per configuration, and they say themselves that they measure diversity across configurations, not variation within one; I have 10 runs per setting. And I estimate the size of the dependence, ρ and the vote failure, not only test independence with z.

If he pushes ("What did they find?"): "That changing the harness, model and language did not make the failure correlation go away. But voting over three programs still cut the mean failure count from 387 to 131."

Q47. And compared with Nogueira et al.?

They used 224 contest problems, with no repository and no context file, and five samples per setting at temperature 0.6. Their pairwise score assumes that, under independence, every test is equally likely to fail, and they name that as a limitation because tests differ in difficulty. That is exactly the Eckhardt and Lee point, and the Beta distribution over θ is how my model handles differences in input difficulty.

If he pushes ("Anything else from them?"): "No combination of models beat the strongest single model, and three versions from one model captured only 0.27 of the possible gain. That's why I compare changes of agent and model."

Q48. Gloaguen et al. and Zhang et al. already test context files. Why isn't that enough?

Both measure whether the task's tests pass. Gloaguen et al. ran each agent once per task and name aspects beyond task success as future work, and Zhang et al. used one agent with one model. I run each setting 10 times and test beyond the tests, so I can see failures that pass the tests and whether the runs share them. As far as I know, nobody has combined those on real tasks with a developer's own file.

12. If the results are null

Q49. If ρ comes out close to zero, has the study failed?

No. It would mean that on these tasks the runs fail almost independently, so the simple vote formula works and extra runs are worth paying for. That would differ from Ron et al. and Nogueira et al., so it's worth reporting with intervals. I'd first check that ρ is not near zero only because almost nothing fails.

Q50. What if no version fails on any generated input?

Then I report an upper bound: 0 failures in 10,000 inputs means the failure probability is likely below about 0.0003. ρ can't be estimated there, and I'd say so. I can't promise failures; the pilot will show whether there are enough, and if not, I'd choose other tasks.

Q51. What if replacing the rule changes nothing in reliability?

If the checker shows the agents did write different code, then "no change in reliability" is a real result: the rule changed the code but not how often it fails. If the checker shows no change, the manipulation failed for that rule, so I'd replace the rule instead of reporting a null.
