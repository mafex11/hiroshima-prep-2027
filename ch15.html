Chapter 15 of 62

Questions on your slides

When and how long: After each run-through: a friend asks 5 at random.

Use this after each run-through of the talk. Ask a friend to pick 5 questions at random from anywhere in this file and read them to you one at a time. Answer each one out loud, without looking, then have them read the three follow-ups in order, because each one pushes on your last answer, the way a professor would. Afterwards, compare what you said with the answer here and fix any number you got wrong. Numbers that come after "say", "imagine", "for example" or "in a toy model" are made-up examples for working out a calculation, not results, so call them examples when you use them.

66 questions on 14 slides, each with a short answer and 3 follow-ups (198 follow-ups in all).

Slide 1: Does a shared AGENTS.md make coding-agent runs fail together? (title)

S1.1. What is an AGENTS.md file, and why is the date rule highlighted in your picture?

AGENTS.md is a plain text file in the repository that Codex reads at the start of every run; Claude Code reads the same kind of file as CLAUDE.md. It lists rules, like how to run the tests or which helper to use. I highlighted the date rule because if that helper mishandles some dates, every run that follows the rule inherits the same bug and fails on the same inputs.

Follow-ups (each builds on your last answer)

  1. Prof: "Is that date rule from a real repository?"
    You: "No, the rules on the slide are an illustration I made. But real files do have rules like that. In fastmcp's current AGENTS.md, for example, one rule says never use a bare except, and another says prefer item.key over ad-hoc name or URI fallbacks. I haven't picked my study's rules yet."
  2. Prof: "You haven't picked them yet. How will you choose them?"
    You: "I'll pick about five rules that change what code is written, like which helper to use, and that a script can check, each with two tasks. Rules about commands, like how to run the tests, can't change how the code behaves, so I leave them out. And the task text must not mention the rule, so any effect comes from the file."
  3. Prof: "Why must a script be able to check the rule?"
    You: "Because I have to show that changing the file really changed what the agent wrote, and with hundreds of runs I can't read every diff by hand. If the agent ignored the rule anyway, a null result would mean nothing, just as BrandMemory's rules couldn't change anything while they were never sent. So I report compliance, but only as a check that the change worked, not as a research question."

S1.2. Your title asks whether runs "fail together". Together compared with what, and what would count as a yes?

Compared with independence. If each run fails with probability p, two independent runs would both fail with probability p squared. It's a yes if runs with the same file fail on the same inputs clearly more often than that, and the word "make" needs a comparison: changing the file should change how often.

Follow-ups (each builds on your last answer)

  1. Prof: "You said 'more often than p squared'. Why does that matter in practice?"
    You: "Because of voting. If three runs each fail with probability 0.1 and fail independently, a 2-out-of-3 vote fails only when two or more fail: 3 times 0.01 times 0.9, plus 0.001, which is 0.028. If they always fail on the same inputs, the vote fails 0.1 of the time, the same as one run, so the extra runs buy nothing."
  2. Prof: "Is there evidence that language-model versions really fail together like that?"
    You: "Yes, two 2026 studies. In Ron et al., two or more of 48 agent-written programs failed together on 429 of a million inputs, against about 115 expected under independence. In Nogueira et al., voting over three versions captured only 0.43 of the gain independence would allow, and 0.27 when all three came from one model. Neither study used a context file."
  3. Prof: "Ron et al. report a z of about 29. Doesn't that settle how strong the dependence is?"
    You: "No. The z says how sure we are that there is some dependence, not how big it is: 429 minus 115.36, over the square root of 115.36, is about 29.2, and ten times the inputs with the same pattern would give about 92. The ratio, about 3.7, is closer to a size but still depends on how many versions are pooled, so in my study the size is rho, from 0 to 1, with a bootstrap interval."

S1.3. Your picture shows three runs failing on the same input. Have you actually seen that happen?

Not with coding agents yet; that's what I want to measure. I've seen a hint of it with a model pipeline at work: in September we ran our video-to-guide pipeline on Gemini twice, with the same video and the same prompts, and both runs of the local-file version made the same mistake, no step for roughly the first 80 seconds. But two runs are a hint, not a measurement.

Follow-ups (each builds on your last answer)

  1. Prof: "Two runs are a hint. What would turn it into a measurement?"
    You: "Many runs on many inputs: for example, 10 runs on each of several videos, counting on each video how many runs make the mistake. If the runs were independent, those counts would look binomial; if they pile up at 0 and at 10, the runs fail together, and the rho of a beta-binomial model says how much. That's my plan's design, with code inputs instead of videos."
  2. Prof: "Make it concrete. One video in ten makes every run fail, and the other nine never do. What is rho?"
    You: "The mean failure chance p is 0.1, so two independent runs would both fail with probability 0.01. Here both fail whenever the video is the bad one, so 0.1, ten times as often. The variance of theta is 0.1 minus 0.01, which is 0.09, and rho is 0.09 over 0.1 times 0.9, which is 1, the top of the scale."
  3. Prof: "A rho of 1 from ten videos. How much would you trust it?"
    You: "Not much, because it rests on one video. If one video in ten is truly bad, a new sample of ten has no bad video at all about a third of the time, since 0.9 to the power 10 is about 0.35. So I'd want many more inputs and an interval; in my plan each entry point gets at least 10,000 generated inputs, and the interval comes from a bootstrap that resamples runs."

Slide 2: AI engineer now, student from April 2027

S2.1. Your 2023 paper is a review. What was your own part in it?

I was second of four authors, and I researched and wrote the paper myself: I read the papers, compared the methods and wrote the text, and my co-authors reviewed it. It was a review and concept paper, with no dataset or model of our own. It taught me how to read and summarise research; my own experiments start with this plan.

Follow-ups (each builds on your last answer)

  1. Prof: "You compared the methods. Explain one of them."
    You: "Region growing. You start from a seed pixel inside the tumour and keep adding neighbouring pixels whose intensity is close to the region's, until no neighbour is close enough. It's simple, but the result depends on the seed and the threshold, and it can leak into healthy tissue where the edge is weak."
  2. Prof: "It leaks where the edge is weak. How would you catch that automatically?"
    You: "One way is to run two different methods, say region growing and a CNN, and flag the regions where they disagree, so a doctor looks there first. If each method fails on 10% of scans and they fail independently, both fail on only 1%, so 9 in 10 of the first method's failures fall on scans where the second one is right, and those show up as a disagreement."
  3. Prof: "Would the two methods really fail independently?"
    You: "Probably not. A weak edge is hard for both, so they tend to go wrong on the same scans, and where both go wrong the same way they agree and nothing is flagged. That's Eckhardt and Lee's point and the question in my plan: two versions help only if they rarely fail on the same inputs. So I'd first measure how often they fail together on labelled scans."

S2.2. It says first position at ICRCCT 2023. Who gave that, the journal or the conference?

The conference. My certificate, a Certificate of Appreciation, says the paper secured first position at ICRCCT 2023, on 23 and 24 June 2023, organised by the Computer Science department of my college. The paper itself appeared in IJIRAE, in a June 2023 special issue.

Follow-ups (each builds on your last answer)

  1. Prof: "Your CV says 'Best Research Paper, IJIRAE'. Which is right?"
    You: "The certificate and my form. The award came from the conference, not the journal, and the certificate never says 'Best Research Paper'. My CV worded it wrongly, and I'm correcting it."
  2. Prof: "Then what did the journal do? Was the paper peer-reviewed?"
    You: "The journal lists it as double-blind peer-reviewed. It was received on 2 June 2023 and accepted on 20 June. I didn't receive any reviewer comments from the journal; the feedback came from my co-authors."
  3. Prof: "Eighteen days, no comments, and your own department ran the conference. How much weight should we give it?"
    You: "Not much on its own, and I don't know who the judges were. I'm glad of it as a first step that got me reading research, but I'd want my research judged by independent review and by results others can check. That's why my plan releases all tasks, code and data, and pins the agents to fixed versions in clean containers."

S2.3. "Founding team" at Layerpath: are you a founder, and how big is the company?

No, I'm not a founder. I joined the founding team as an engineer, I'm paid a salary only, with no shares or stock options, and it's a small team of about 7 people.

Follow-ups (each builds on your last answer)

  1. Prof: "With only seven people, can you really leave before April?"
    You: "Yes. I'll leave as soon as I'm accepted, before I enrol, and hand over my work properly; other engineers at Layerpath will take over Magic Editor and BrandMemory. My CEO knows I'm applying; he wrote one of my recommendation letters."
  2. Prof: "Until then you work full time. How are you preparing?"
    You: "In the evenings and at weekends, about 8 to 10 hours a week, through Ross's Introduction to Probability Models and Wasserman's All of Statistics, Poisson processes and maximum likelihood first. I've also installed pysrat and run it on the Musa SS1A data that comes with it, 151 days and 112 faults, fitting all twelve models."
  3. Prof: "What did that pysrat run teach you?"
    You: "That the model choice changes the answer a lot. The S-shaped log-logistic model fitted best by AIC, about 354.7, but the expected total number of faults ranged from about 119 to 672 across the twelve models. So one number hides a lot, and I'd report a bootstrap interval and show the top few models side by side."

S2.4. Your slide says 2022 to 2026. Your CV says May 2026 and your form says July 2026. Which is right?

Both, for different things. My final-semester results were announced on 22 May 2026, and my official grade card, with my final CGPA of 8.04, is dated 22 July 2026. So May is when the results came out, and July is the date on the grade card, which my form uses.

Follow-ups (each builds on your last answer)

  1. Prof: "And the proposal you sent us in October said a CGPA of 8.0, not 8.04."
    You: "8.04 is the exact figure on my final grade card; the proposal rounded it. I should have written it the same way everywhere."
  2. Prof: "Two dates and two CGPAs. Why should we trust the numbers in your research?"
    You: "That's fair. In research I'd keep each number in one place: a script computes every number and table from the data, so nothing is typed twice and nothing can drift between the paper and the slides."
  3. Prof: "If that script has a bug, every number is consistently wrong. How would you catch that?"
    You: "By running the whole analysis on simulated data where I know the answer. I'd generate failures from a beta-binomial with a known rho, and check that the analysis gets it back and that its 95% intervals contain the true value about 95% of the time. A bug that shifts every number shows up there, because I know what the numbers should be."

S2.5. Before Layerpath you were Software Engineer 1 at BusinessRoom. What did you do there, and why only four months?

I worked on page load speed, moved services to Docker on AWS ECS with CI/CD, set up monitoring, and built an AI assistant on AWS Lambda. The company ran out of funding and the team wound down, and I joined Layerpath the next month.

Follow-ups (each builds on your last answer)

  1. Prof: "You worked on page speed. What did you actually change?"
    You: "Mostly front-end work, caching, and SVGs in place of heavy images, so the browser had less to download. I didn't do any database work, so the 'query optimisation' on my CV is wrong, and I'm fixing it."
  2. Prof: "Your CV says 7 seconds down to 1.5. How was that measured?"
    You: "That's a product number from work, and I don't have the method in front of me, like which pages or how many loads, so I won't defend the exact figure. A load time is a distribution, so properly I'd report the median and the 95th percentile before and after, on the same pages and network, with cold and cached loads separately."
  3. Prof: "Why separate cold and cached loads? Put numbers on it."
    You: "Say a cold load takes 4 seconds, a cached one half a second, and 80% of loads hit the cache: the average is 0.8 times 0.5 plus 0.2 times 4, which is 1.2 seconds. But one load in five still takes 4 seconds, and if the hit rate falls to 50%, the average becomes 2.25 seconds with no change to the code."

Slide 3: Magic Editor: the user approves every edit

S3.1. In your "Check" box, what exactly does the code check, and what can it not check?

The model can't send free text; it must return a structured action, like "change the text of element X to Y", and the code checks it against a schema, written with Zod, before anything happens. A malformed or impossible edit is rejected. What the schema can't check is whether the new text is right, and that's what the user's approval is for.

Follow-ups (each builds on your last answer)

  1. Prof: "A schema checks the shape. How does it know element X even exists?"
    You: "The schema alone doesn't. That's a check against the demo's current state, so the server checks each action against a copy of the live demo before writing anything, refuses it with a message like 'element X was not found on step Y', and reads the change back afterwards to confirm it landed."
  2. Prof: "Between that check and the moment the user approves, the demo may change. What then?"
    You: "Then the check is out of date; it's a time-of-check to time-of-use problem. So each batch carries the demo version it was planned against and is refused if the demo has changed since, unless the changes were on other steps, and every action is checked again against the live demo just before it's written."
  3. Prof: "So one action can be refused. Would you refuse the whole plan? Say it has 5 actions, and each fails its check independently with probability 0.05."
    You: "If I refused the whole plan, it would pass only if all five pass: 0.95 to the power 5, about 0.77. So about 23% of plans would be refused, and about 9 in 10 of those had only one bad action. That's why Magic Editor now checks each action on its own: a bad one is dropped and reported back to the agent, and the rest apply."

S3.2. The user approves every edit. Isn't that admitting the AI is unreliable?

Yes, in a way, and that's on purpose. The approval works like an acceptance test done by a person: nothing is applied until the user approves it, so a bad edit is caught before it changes anything, and the user stays in control.

Follow-ups (each builds on your last answer)

  1. Prof: "An acceptance test. Which fault-tolerance idea is that?"
    You: "It's closer to a recovery block than to N-version programming: one version, an acceptance test, and a fallback. Here the acceptance test is the format check plus the user, and the fallback is that nothing changes if the user rejects."
  2. Prof: "But a person is not a perfect acceptance test. What if users approve without reading?"
    You: "That's a real risk, called automation bias: people tend to accept what a system proposes, especially when it's usually right, so the approval rate makes quality look better than it is. One sign is an edit that's approved and then undone soon after; since September Magic Editor logs approvals, rejections and undos of the AI's changes, though not later manual edits."
  3. Prof: "So there are two checks. If the format check misses 10% of bad edits and the user misses 30%, how many get through?"
    You: "If they miss independently, a bad edit gets through only when both miss it: 0.1 times 0.3, so 3%. But they probably aren't independent: a well-formed edit with subtly wrong text passes the schema and is also the kind a user misses. So the real figure is likely above 3%, the same coincident-failure problem as in N-version programming."

S3.3. Your subtitle says the text is "based on what is on screen". What if it describes something that isn't on the screen?

That's a hallucination, and the schema can't catch it, because the action is well formed; only the text inside it is wrong. Since October a separate fast model call compares the new line with the step's screenshot and sources, and keeps the old words if the new line names something not on screen. After that, the user is the last check.

Follow-ups (each builds on your last answer)

  1. Prof: "A model checking a model. Couldn't the checker be wrong in the same way?"
    You: "Yes, especially if it's the same model. A screen that's hard for the writer, like a tiny or unclear label, tends to be hard for the checker too, so their mistakes fall on the same screens. That's Eckhardt and Lee's point: if difficulty varies from input to input, two versions from one process fail together more often than independence predicts."
  2. Prof: "Is there evidence for that with language models?"
    You: "In code, yes. Nogueira et al. found that voting over three versions got 0.44 of the possible gain when the three models differed, but only 0.27 when all three came from one model. So a checker from a different model might miss fewer of the writer's mistakes, but I'd have to measure that."
  3. Prof: "How would you measure it in Magic Editor?"
    You: "I'd take a random sample of edits and have a person label each new line right or wrong against the screen, without seeing what the checker said. Then I'd run the same sample through a same-model checker and a different-model checker, and compare how many of the wrong lines each one lets through, with an interval, and whether the misses pile up on the same hard screens."

S3.4. Your band says the same idea is in your plan: a run counts only if it passes the task's tests. Are user approval and passing tests really the same thing?

Not the same check, but the same idea: a model's answer is only a proposal until it passes a check. In Magic Editor the check is the format and the user; in my plan it's the pull request's tests, like the acceptance test in Knight and Leveson's experiment. Both checks see only what they look at.

Follow-ups (each builds on your last answer)

  1. Prof: "Only what they look at. So what do the tests miss?"
    You: "Every input the developer didn't write a test for. So after a run passes the tests, I give its code at least 10,000 random inputs per entry point, built from the type hints and the values in the tests, and compare each answer with the merged code's answer. The share of inputs where it disagrees is its failure probability beyond the tests."
  2. Prof: "If you admit only runs that pass the same tests, doesn't that push all their failures into the same untested places?"
    You: "Yes, I think it does. If every admitted version passes the same tests, the failures left must sit where the tests don't look, so they cluster there and rho goes up. I can't remove that, but both file versions face the same tests, so the comparison stays fair, and I report rho as 'given admission'."
  3. Prof: "And if a version fails on none of its 10,000 inputs, what can you say?"
    You: "Not that it's perfect. With zero failures in 10,000 independent inputs, the one-sided 95% upper bound on the failure probability is about 3 in 10,000, the rule of three; exactly, 1 minus 0.05 to the power one over 10,000, about 0.0003. And it holds only for my input distribution, not for real use."

S3.5. Do real customers use Magic Editor, and how do you know its edits are good?

It's part of Layerpath's product, but I don't have a formal quality study. Since every edit is approved or rejected by a user, the approval rate per suggestion would be a natural first measure.

Follow-ups (each builds on your last answer)

  1. Prof: "Is the approval rate really a measure of quality? What could distort it?"
    You: "A few things. Users may approve without reading, which pushes it up, and some reject good edits because they changed their mind, which pushes it down. And a few heavy users may make most of the suggestions, so one overall rate would mostly reflect them."
  2. Prof: "A few heavy users. How many workspaces would you even have? Your CV says 35+."
    You: "I'm not sure how that number was measured, so I won't defend it. The only log I have covers 14 days up to an audit on 30 September: 31 workspaces, with our own staff not counted separately. So I'd take staff out first, and then treat workspace as a random effect."
  3. Prof: "With about 30 workspaces, how much does that cost you? Give me a number."
    You: "Say each workspace makes 20 suggestions and the correlation inside a workspace is 0.1. The design effect is 1 plus 19 times 0.1, which is 2.9, so 600 suggestions count like about 207 independent ones, and the interval is about 1.7 times wider. It's the same intraclass correlation that measures shared failures in my plan."

Slide 4: BrandMemory: rules the model never saw

S4.1. How did you find that the brand rules never reached the model?

The logs said the brand guidance was applied, but with BrandMemory on and off the texts looked almost the same. So I followed the saved brand profile through the code that builds the prompt, up to the text sent to the model. The sections are ranked by priority, the lowest are cut first when the text is too long, and brand voice was ranked last.

Follow-ups (each builds on your last answer)

  1. Prof: "Then why did the log say the guidance was applied?"
    You: "Because the flag only recorded that brand guidance had been produced, in a separate step with a 6,000-character limit. It never saw the 3,200-character cut each feature made later, so it stayed true even when the voice section was gone. It checked the intent, not what was actually sent."
  2. Prof: "In our Markov models we use a coverage factor, the chance that a fault is detected and handled when it happens. What was the coverage of that log for this error?"
    You: "Zero. The flag stayed true whether or not the voice section was cut, so it could never catch this error, and the log looked fine for every affected demo."
  3. Prof: "So where should the check be, and is it there now?"
    You: "On the final prompt, just before the model call, recording any section that was cut, and ideally on the output too. Honestly, the cut sections still aren't logged today; my fix went after the cause instead, by raising the limit and making the cuts follow priority strictly. A log of what was cut is the obvious next step."

S4.2. What exactly did you change to fix it?

I removed the per-feature 3,200-character limits and raised the overall limit from 6,000 to 30,000 characters. I also turned off our default house style when a brand voice is active, used the brand's verified examples as examples, and moved the brand rules before the output requirements in the video prompt.

Follow-ups (each builds on your last answer)

  1. Prof: "You went from a 3,200-character limit to 30,000. Why was there a limit at all?"
    You: "I don't know of a written reason for the 3,200 figure, so before I claimed one I'd check the code history where it was set. Limits like that usually keep prompts short and cheap. A higher cap doesn't make every prompt that long; it just leaves room, and after the fix I checked the final prompt for my test pair and no section was cut."
  2. Prof: "So nothing was cut any more. Was the limit the only cause?"
    You: "No. Some brand rules did arrive even before, but our default house style used strong words like 'MANDATORY' and came with six fixed examples, and the model followed it over the brand's rules. So how a rule is worded and where it sits mattered as much as whether it arrived."
  3. Prof: "So several causes and five changes at once. How would you tell which change mattered?"
    You: "Not from my one pair, which ran after all the changes. Leave-one-out, as Zhang et al. did for agent rules, misses changes that cover for each other, so I'd use a factorial design: all 32 on-off combinations of the five changes, and with 3 brands and 5 runs each, 480 runs. A well-chosen half, 16 settings, still separates the five main effects and all ten two-way interactions, if the higher interactions are small."

S4.3. Contractions went from 6 to 0, and "you" and "your" from 15 to 1. Couldn't that happen by chance?

It could. The model writes different text on every run, and with one output on each side I can't see how much the count moves by itself. That's why the slide says one pair, not a study.

Follow-ups (each builds on your last answer)

  1. Prof: "Suppose the count with BrandMemory off is Poisson with mean 6. How likely is a 0?"
    You: "The Poisson chance of 0 is e to the minus 6, about 0.0025, so about 1 in 400. Under that model a 0 would be strong evidence. But the mean of 6 comes from a single run, and the Poisson model is itself an assumption."
  2. Prof: "And if the Poisson model is wrong?"
    You: "Runs of a language model probably vary more than a Poisson allows, because some runs are longer or more casual. So I'd use a negative binomial, a Poisson whose mean itself varies from run to run, which does for counts what the beta-binomial does in my plan. I'd add the word count as an offset and report the ratio of the on and off rates with an interval."
  3. Prof: "Apart from chance, what else is weak about that one pair?"
    You: "I counted the words myself. The brand memory in that workspace came from one company's website while the demo was about another company's product, and the request went to the product walkthrough profile, not the marketing one. A real test would use many pairs on several brands, each side run several times, with measures and a counting script fixed in advance."

S4.4. Why did you count contractions and "you" and "your"? Does that really show the brand voice?

Because the brand's rules said "avoid contractions" and "write in the third person", so those are counts the rules should change, and they're easy to count. It shows that those rules reached the model and changed the text. It doesn't show the whole voice, like tone.

Follow-ups (each builds on your last answer)

  1. Prof: "Then how would you measure tone?"
    You: "With people: show raters two texts for the same demo, one with BrandMemory on and one off, in random order and without saying which is which, and ask which sounds more like the brand's own site. I could use a model as the judge instead, but only after measuring how well it agrees with the human raters."
  2. Prof: "How would you measure that agreement?"
    You: "With Cohen's kappa, which compares the raters' agreement with what they'd reach by chance, given how often each one picks the BrandMemory text. If both pick it most of the time, they agree a lot just from that habit, and kappa takes that part out."
  3. Prof: "Compute it. Twenty pairs, the two agree on 18, and each picks the BrandMemory text in 15."
    You: "Observed agreement is 18 of 20, so 0.9. By chance it would be 0.75 times 0.75 plus 0.25 times 0.25, which is 0.625. So kappa is 0.9 minus 0.625, over 1 minus 0.625, which is 0.275 over 0.375, about 0.73: good, but lower than the raw 90% suggests."

  1. Prof: "Only 9 unasked actions. What can 9 out of 9 really tell you about the catch rate?"

S7.1. User approval, replay tests and a task's tests are very different things. What do they really share?

Each one checks only cases someone picked. The user checks the edit in front of them, my replays check the 45 calls I recorded, and a task's tests check the inputs the developer wrote. Outside those cases, none of them tells me anything.

  1. Prof: "That's an old point: testing can show bugs, not their absence. What's new here?"

Slide 8: Voting needs versions that fail differently

S8.1. Your first box is about our N-version paper. Have you read it, and what did you take from it?

  1. Prof: "Why do you think voting helped little with the weaker models?"
    You: "I haven't seen your results, so this is only a guess from Eckhardt and Lee.   2. Prof: "Can you show me that it's below θ only when θ is below one half?"

  3. Prof: "And with five versions instead of three?"

Slide 9: Two questions: shared failures and one rule

S9.1. RQ1 asks "how much more often than independence predicts". What number answers that?

ρ, the intraclass correlation of a beta-binomial model: 0 means independent, and 1 means the runs always fail together. With the mean failure probability p, two runs both fail with p² plus ρ p(1 - p), so "how much more often" is that divided by p²: 1 plus ρ times (1 - p) over p.

  2. Prof: "So with rare failures any small ρ looks dramatic. Why not make that ratio your main number?"
    You: "Because the ratio mixes ρ with p: the same ρ of 0.1 gives about 1.9 at p = 0.1 and 10.9 at p = 0.01. ρ separates the dependence from how often runs fail, and the vote failure depends on both. So I report ρ, p and the 2-out-of-3 vote failure together."
  3. Prof: "Then how precisely can ten runs per setting pin down ρ?"
    You: "Not very. More inputs don't help much, because one buggy run fails the whole region at once. So with ten runs I can tell ρ near zero from ρ near a half, and I'd pool tasks when I compare settings."

Slide 11: One number for "fail together"

S11.1. In your picture, both cases have p = 0.2. Where does the 0.08 on the right come from?

  1. Prof: "So the variance of θ is 0.04. What is ρ for that right-hand picture?"

  2. Prof: "And at the other end, ρ = 1. How large can the chance that both fail get, with the same p = 0.2?"

S11.2. Each run is a fresh, separate run. Why would two runs not fail independently?

Given the input, they do: on input x both fail with θ(x) squared. But averaged over random inputs that is E of θ squared, which is p squared plus the variance of θ. So the runs share the hard inputs, and that shared difficulty is the dependence, which is Eckhardt and Lee's result.

  1. Prof: "What exactly did Eckhardt and Lee prove? Have you read the paper?"

I've read the NASA report version, TM-86369 from January 1985: the model, independent errors, the effects of coincident errors and the conclusions.   2. Prof: "Probability zero under which distribution? What is that in your study?"

S11.3. Why a Beta distribution for θ?

θ is a probability, so it needs a distribution on 0 to 1, and the Beta has one parameter for the mean and one for the spread. It is conjugate to the binomial, so the number of failing runs on one input is beta-binomial, with a closed form. Its ρ is 1 over a plus b plus 1.

Follow-ups (each builds on your last answer)

  1. Prof: "Derive that ρ. And your slide says ρ = 1 means 'always fail together'. What exactly does that mean?"
    You: "The Beta variance is a b over (a plus b) squared times (a plus b plus 1), which is p times 1 minus p, divided by a plus b plus 1. ρ is that variance divided by p times 1 minus p, so 1 over a plus b plus 1. ρ = 1 means θ is only 0 or 1, so on each input either all runs fail or none do; 'always fail together' is my short way of saying that."
  2. Prof: "In practice I'd expect most inputs to have θ exactly 0. Can a Beta represent that?"
    You: "Not exactly. With a below 1 it piles mass near zero, but it never puts a share of inputs at exactly zero, and it can't hold a separate lump of hard inputs. So I'd also fit a zero-inflated beta-binomial, where a share of inputs can't fail, and let the pilot show which one fits."
  3. Prof: "Does that kind of misfit change any conclusion, or only the fit?"
    You: "It can change the conclusion. Take my right-hand picture: p = 0.2 and ρ = 0.25, and a 2-out-of-3 vote there fails with 0.176. A Beta with the same p and ρ predicts about 0.157, so it makes voting look better than it is. That's why I also estimate the vote straight from the counts of failing runs, with no Beta, and check that the model reproduces it."
