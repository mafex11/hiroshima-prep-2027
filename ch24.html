Question bank with model answers (for the meeting with the professors)

When and how long: Optional, 20 minutes.

These are guesses, not a script the professors will follow. Say the answers in your own words. Short is better. If you don't know something, say "I don't know yet" and how you would find out. That is always better than guessing.

Anything marked [CONFIRM] must be true before you say it. Anything marked [FILL] is yours to fill. Funding is confirmed: you fund your studies yourself.

About the research

Q1. Can you explain your research in a few sentences? I treat repeated coding-agent runs on one real task as N versions of a program. RQ1 measures how much more often they fail on the same inputs than independence predicts, and which change between runs lowers that most: the context file, the agent, the model or the temperature. RQ2 checks whether replacing one real rule in the context file with neutral text changes reliability beyond the task's own tests. The main result is a fitted model that tells a team how many runs to vote over at a given cost.

Follow-ups (each builds on your last answer)

  1. Prof: "You list four changes between runs: the context file, the agent, the model and the temperature. Which one do you expect to lower joint failures most?"
    You: "My guess is changing the model or the agent. On contest problems, Nogueira et al. found that a vote of three versions from one model captured only 0.27 of the gain that independent failures would allow, against 0.44 when the models differed. But that study had no context file, and in Ron et al. the shared failures crossed agents and languages, so it's only a guess that RQ1 has to check."
  2. Prof: "If mixing models helps, why not simply tell teams to mix them? What does your fitted model add?"
    You: "A ranking says which change helps, but not whether it's worth paying for. Agents differ in cost and in how often they pass the tests. My model takes each setting's failure probability p and the covariance between settings, meaning how much their failures land on the same inputs, and turns them into the vote's failure chance and the cheapest number of runs."
  3. Prof: "Show me with numbers. Two agents both have p = 0.05. Two runs of the same agent have a covariance of 0.02, and one run of each has 0.01. How often do two runs both fail?"
    You: "Two runs both fail with p_a times p_b plus the covariance, so independence alone would give 0.0025. Two runs of the same agent give 0.0025 plus 0.02, which is 0.0225, and one run of each gives 0.0125. So mixing the agents cuts joint failures by more than 40 percent, though they still fail together five times as often as independence predicts."

Q2. Why reliability? You are an engineer. Why research, and why now? At work I review and test agent changes every day, but tests only cover the cases someone thought of. I have also seen an instruction to a model have no effect at all, while our logs said it was applied. So "the tests passed" doesn't feel like the full answer to me. I want real numbers for how often this code fails and how much voting helps, and that needs probability models I can't build yet.

Follow-ups (each builds on your last answer)

  1. Prof: "Everyone knows tests only cover the cases someone thought of. What would you do differently, apart from writing more tests?"
    You: "I'd measure failure as a probability instead of a pass or fail. I write down an input distribution, draw many random inputs from it, compare each version's output with a reference, and report the share that fail with an interval. My plan uses at least 10,000 inputs per entry point, meaning each function the task's tests call."
  2. Prof: "And if none of those 10,000 inputs fails, what do you report? Zero?"
    You: "Not zero. With no failures in n random inputs, the rule of three gives a 95% upper bound of about 3 over n, so about 3 in 10,000. And it only speaks for inputs drawn from my distribution, so it isn't a proof that the code is correct."
  3. Prof: "Where does that 3 come from?"
    You: "If the true failure probability is p, the chance of seeing no failure in n inputs is (1 - p) to the power n, which is about e to the minus n p. The upper bound is the p where that chance falls to 5%, so n p equals minus the log of 0.05, which is about 3.0, and p is about 3 over n."

Q3. Have you read our N-version paper? How is your work different? I've only read the abstract, because the full text is behind the Springer paywall. [CONFIRM: change this if you get the paper and read it before the meeting.] From it, you compared strong and weak models and two ways to add diversity, temperature and conversation history reuse. My plan takes that question to real repository tasks with coding agents, and adds the shared context file as a possible cause of common failures. Could I ask you for a copy?

Follow-ups (each builds on your last answer)

  1. Prof: "From the abstract: voting helped our strong models but helped little with the weaker ones. Why do you think that is?"
    You: "My guess comes from Eckhardt and Lee's model: a vote helps on inputs where fewer than half of the versions fail, and hurts where more than half fail. A strong model fails on few inputs, so the vote fixes its occasional slips, while a weak model may be wrong on many inputs for most of its versions. I've only read the abstract, though, so I'd want to check that against your data."
  2. Prof: "Show me that with three versions."
    You: "On an input where each version fails with chance θ, a vote of three fails with 3θ² - 2θ³, and one version fails with θ. One version's chance minus the vote's is θ times (1 - θ) times (1 - 2θ), which is positive below one half and negative above it. So at θ = 0.1 the vote fails with 0.028 instead of 0.1, but at θ = 0.7 it fails with 0.784 instead of 0.7."
  3. Prof: "So for a weak model, can voting make things worse overall, not only on one input?"
    You: "Yes, if its failures sit on inputs that are hard for most versions. Imagine 40% of inputs have θ = 0.7 and the rest have θ = 0: one version fails with p = 0.28, but a vote of three fails with 0.4 times 0.784, about 0.31, which is worse. So how the failures spread over the inputs decides it, not p alone, and that spread is what my model measures."

Q4. Why can't you just assume the runs fail independently? Eckhardt and Lee showed that two versions from the same process fail independently only if every input is equally hard. Real inputs are not equally hard: some edge cases trip up almost every run. If θ(x) is the chance that a run fails on input x, two runs both fail with probability p^2 + Var θ(X). So any spread in difficulty makes joint failures more likely than p^2.

Follow-ups (each builds on your last answer)

  1. Prof: "You say some edge cases trip up almost every run. Is there evidence for that with coding agents, or is it intuition?"
    You: "There is evidence. Ron et al. repeated Knight and Leveson's 1986 experiment with coding agents, and the main failures were concentrated in two of the fifteen launch conditions, where many agents used the circle through three points instead of the smallest circle that contains them. Overall, 429 inputs had two or more of the 48 programs failing, against about 115 expected under independence."
  2. Prof: "How do you get 'about 115 expected'? Those 48 programs all have different failure rates."
    You: "Under independence each program keeps its own rate. For one input, the chance that none fails is the product of 1 minus each rate, and the chance that exactly one fails is a sum of similar products, so 1 minus those two is the chance that two or more fail. Times a million inputs, that gives 115.36, and the excess over it, divided by the square root of 115.36, gives their z of about 29."
  3. Prof: "Do a small one by hand. Three programs fail independently with probabilities 0.01, 0.02 and 0.03. What's the chance that two or more fail on one input?"
    You: "Add the three pairwise products, 0.0002, 0.0003 and 0.0006, which makes 0.0011. Then subtract twice the product of all three, 2 times 0.000006, because the pairwise sum counts the case where all three fail three times instead of once. That leaves about 0.00109, roughly one input in a thousand."

Q5. How would voting even work with code patches? Each run gives a patch. In practice a team would run all the patches on generated inputs and pick the one whose outputs agree with most of the others. My model predicts how often the majority is wrong on an input, and I can also measure directly how often the picked patch fails against the merged code. On an input where a run fails with chance θ, a 2-out-of-3 vote fails with chance 3θ^2 - 2θ^3, and averaged over inputs that is E[3θ^2 - 2θ^3]. I compare that with 3p^2 - 2p^3, what you'd get if runs were independent, and I also find the odd number of runs N that minimises run cost plus expected failure cost.

Follow-ups (each builds on your last answer)

  1. Prof: "Why only an odd number of runs?"
    You: "With an even number the vote can tie, for example two runs right and two wrong, and then the majority doesn't say which output to pick. An odd number avoids ties, while an even number would need a tie rule, like flipping a coin."
  2. Prof: "Suppose you do flip a coin on ties. Is a fourth run worth anything?"
    You: "No, it changes nothing. With four runs and a coin flip, the vote fails if three or four runs fail, plus half the time when exactly two fail, and that adds up to exactly 3θ² - 2θ³, the same as three runs. So the fourth run is pure cost."
  3. Prof: "Then how would you choose between three and five runs?"
    You: "Five beat three when the cost of a failure times the drop in the vote's failure chance is more than the cost of two runs. With independent runs and p = 0.02, three fail with about 0.0012 and five with about 0.00008, so five win only if one failure costs more than about 1,800 runs. Dependence can move that either way: in a Beta model with the same p, ρ = 0.1 lowers the bar to about 650 runs and ρ = 0.8 raises it to about 17,600, so I'd compute it from the fitted model."

Q6. Why a beta-binomial model? How will you fit it? θ is a chance between 0 and 1 that changes from input to input, and the Beta distribution is a flexible model for that, so the number of failing runs out of k on one input is beta-binomial. Its intraclass correlation, ρ = 1/(a + b + 1), is zero under independence, so it measures directly how much runs fail together. I fit it per task and setting by maximum likelihood, with intervals from a bootstrap that resamples runs, because the same runs meet every input. If almost every input has zero failures, a zero-inflated version may fit better, and the pilot will show that.

Follow-ups (each builds on your last answer)

  1. Prof: "Maximum likelihood needs a starting point, and it can fail to converge. How would you start it?"
    You: "From the moments of the counts. The average share of failing runs gives p, and how much the counts spread beyond a binomial gives ρ, because the variance of the number of failing runs out of k is k p(1 - p) times (1 + (k - 1)ρ). Those simple estimates are my starting values, and they're also a check on the final fit."
  2. Prof: "Do it. Ten runs per input, the counts average 0.5 failing runs, and their variance is 1.0."
    You: "p is 0.5 over 10, so 0.05, and a binomial variance would be 10 times 0.05 times 0.95, which is 0.475. The observed variance is about 2.1 times that, so 1 + 9ρ = 2.1 and ρ is about 0.123. Then a + b = 1/ρ - 1, about 7.1, and a is p times that, about 0.36, so b is about 6.8."
  3. Prof: "And if the variance had come out at 0.4, below the binomial 0.475?"
    You: "Then the moment estimate of ρ is negative, about minus 0.02. Within one setting the true value can't be below zero, because two runs both fail with p squared plus Var θ, and a variance is never negative. So I'd read it as chance: my ten runs happened to fail on different inputs. The Beta fit agrees, since it stops at the edge, ρ = 0, the plain binomial, and I'd say that the usual intervals are unreliable at that edge."

Q7. How will you find failures that the tests miss? A run's change only counts as a version if it passes the pull request's own tests. Then I generate at least 10,000 random inputs per entry point, from the type hints and the values in the PR's tests, and compare each version with the merged code under a fixed rule: a float tolerance, the same exception class, and order ignored for unordered collections. I check 20 disagreements per task by hand and drop inputs where the merged code itself is wrong. The honest limit is that if the merged code has the same bug, this kind of testing can't see it.

Follow-ups (each builds on your last answer)

  1. Prof: "You compare outputs with a float tolerance. Which tolerance, and why does it matter?"
    You: "I'd fix it before any run, for example a relative tolerance of one in a billion, the default of Python's math.isclose, plus a small absolute tolerance for values near zero, where a relative one breaks down. Too tight, and harmless rounding differences count as failures; too loose, and real bugs hide inside the tolerance."
  2. Prof: "Give me a case where a loose tolerance hides a real bug."
    You: "Money. Python's round of 72.195 to two decimals gives 72.19, because 72.195 is stored as a binary float just below it, while code that uses the Decimal type and rounds half up gives 72.20. That one-cent difference is about 1.4 in 10,000 relative, so a tolerance of one in a thousand would hide it, while one in a billion would flag it."
  3. Prof: "So is that one cent a failure or not?"
    You: "It depends on the specification, so the tolerance has to come from the domain, not be one number for everything. If the merged code rounds money with Decimal, I'd compare money outputs exactly to the cent, and for scientific floats I'd use a relative tolerance. I'd write that down per entry point before any run, so I can't tune it after seeing the results."

Q8. What do you know about probability, statistics and reliability models like NHPP? My only statistics course so far is BCS301 in my third semester. It covered probability distributions, Markov chains, hypothesis tests and ANOVA. I can explain the models in my plan, and the basic NHPP idea that the expected number of faults found by time t follows a mean value function, like ω(1 - e^(-bt)) in the Goel-Okumoto model. I haven't fit an NHPP to real data myself yet [CONFIRM: unless you install pysrat and run its example before the meeting], which is why statistics and reliability courses come first in my plan.

Follow-ups (each builds on your last answer)

  1. Prof: "In ω(1 - e^(-bt)), what do ω and b mean, and how many faults are left at time t?"
    You: "ω is the expected total number of faults, and b is the rate at which each remaining fault is found, so each fault's detection time is exponential with mean 1 over b. By time t we expect ω(1 - e^(-bt)) found, so ω e^(-bt) are still left, and that number falls exponentially."
  2. Prof: "How would you estimate ω and b from failure times?"
    You: "By maximum likelihood. For failure times up to T, the log-likelihood is the sum of the log intensity at each failure time minus m(T), where the intensity is ω b e^(-bt). Setting the derivative in ω to zero gives ω = n divided by (1 - e^(-bT)), and b has to be found numerically; pysrat fits both with the EM algorithm, but I haven't run it myself yet. [CONFIRM: change this if you run pysrat before the meeting.]"
  3. Prof: "Put in numbers: 20 failures by day 30, and b is 0.05 per day. How many faults remain?"
    You: "1 - e^(-1.5) is about 0.78, so ω is 20 over 0.78, about 25.7. So about 26 faults in total, and about 6 still to be found. It's only as good as the model, though: if the data don't follow this exponential shape, that 6 can be far off, which is why pysrat offers twelve NHPP models to compare."

Q9. Is this realistic in two years, in time and money? My schedule puts courses, the models, the harness and a pilot in the first half of Year 1, the main runs and RQ2 in the second half, the shared-failure model and a first paper in the first half of Year 2, and the thesis last. RQ1 is the core, and the field data part is only if time permits, so it can be dropped. The 820 runs cost about 420 to 590 US dollars at the per-task prices in Gloaguen et al., and newer models may cost more. Follow-ups (each builds on your last answer)

  1. Prof: "You said newer models may cost more. How much more?"
    You: "I don't know yet. The only newer number I have is Zhang et al.'s rough figure of about 5 dollars per task and condition with Claude Opus 4.6, but their whole study of over 5,000 runs cost about 2,000 dollars, which is about 40 cents a run.   3. Prof: "Then the file version itself changes your cost. Does that matter for RQ2?"

Harder follow-ups, if he digs

  • "Why 10 runs per setting?" It balances cost against seeing how many runs fail on each input. The pilot will show whether 10 gives a useful interval for ρ. If not, I'd change it then.
  • "What if every run passes every input?" Then that task's failure probability is close to zero and ρ can't be estimated there. I report that, because it is a result too. But passing the PR tests every time doesn't mean passing every generated input. That's why I keep tasks the agents always solve.
  • "Why not conversation history reuse, like in our paper?" It's not in the plan now. My own harness controls the whole prompt, so I could add it as another setting if you think it's worth it.
  • "How do you know removing the rule changed what the agent did?" A checker script confirms it. I keep a checker only if it agrees with my hand labels on at least 90% of 20 or more examples, and I report Cohen's kappa. Compliance is a check on the setup, not a research question.
  • "Can't you set the temperature in Claude Code or Codex?" Gloaguen et al. report setting it to 0 in both. As far as I know, neither CLI documents a temperature setting, so I'd rather not depend on it. I treat each setting as a distribution of runs, and I vary temperature in my own harness, where I control it directly.
  • "How unsure are your estimates?" The bootstrap over runs gives intervals for ρ and for the vote failure chance, so I report a range, not one number.
  • "Tell me about the infinite-server queue model." In my field-data part, each merged agent change adds some expected faults that are found after a delay, so m(t) = Σ ω_j G(t - τ_j). Prof. Dohi used the same infinite-server queue idea in 2004 to unify finite and infinite fault NHPP models. [CONFIRM: so far only the abstract of that paper has been read.
