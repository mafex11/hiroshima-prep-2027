  1. Prof: "Suppose we kept your question but used the setting of our N-version paper, programming problems given to several models, instead of real repository tasks. What would you lose?"

  2. Prof: "Why do you expect a shared file to matter more than a shared model?"
    You: "I don't know that it does; that's part of what RQ1 measures. A shared model is already a known common cause: in Nogueira et al., a three-version vote captured only 0.27 of the possible gain when all three versions came from one model, against 0.44 with mixed models. My guess is that the file adds a second common cause on top, because a rule can push every run toward the same design, like the same helper."
  3. Prof: "How would you separate the two in your design?"
    You: "Through the covariance between pairs of runs: for runs from two settings, the chance both fail on a random input is the product of their failure probabilities plus the covariance of their per-input failure chances. I compare pairs that differ in one thing only, the model, the agent or the file version, and the change that lowers the covariance most points to the strongest common cause. Some covariance always remains, because some inputs are simply hard for any version."

Q2. Your background cites Xia and Miller: bug-fixing commits changed 4.0% of agent-written lines within 180 days, against 2.7% of human-written ones. Does that show agent code is less reliable? What could confound it?

Not directly. It shows that in 182 open-source repositories, agent-written lines were more often changed by a bug-fixing commit within 180 days, which is more corrective maintenance, not a measured failure probability. The authors adjust for the file's role and for the repository, and they list their own limits: authorship is guessed from commit authors and lines like "Co-authored-by", human commits may have hidden AI help, the bug-fix labels come from a rule-based and LLM-assisted classifier, and not every changed line is a defect.

Why he asks: the number is in your plan's Background, and professors like to check cited numbers. If he pushes ("What else could confound it?"): "I would also worry about the kind of tasks people give to agents, and whether reviewers look harder at agent code, so its bugs are found sooner." If he pushes ("So why cite it?"): "Because it is a field signal that merged agent code gets more bug-fix changes later, so some bugs likely got past the checks at merge time. My plan looks for that kind of failure before merge, with inputs beyond the tests." If he pushes ("Which way would hidden AI help bias it?"): "Towards no difference, as the authors say. So the real gap could be larger, not smaller." Note for you: everything above is in the paper text (/Users/mafex/code/personal/masters-research/2027-refresh/hiroshima-application/qbank-2026-11-01/paper_text/REF10_Xia_Miller_2026_post_merge_fate_arXiv2607.09902.txt: method section, "Modeling Considerations" and "Limitations"). Follow-ups (each builds on your last answer)

  1. Prof: "You said it's corrective maintenance, not a failure probability. What's the difference?"
    You: "A failure probability is the chance that the code gives a wrong result on an input drawn from some input distribution. A bug-fix change rate counts lines that a later fix touched, so it also depends on whether anyone used that code, noticed the bug and labelled the commit as a fix. A buggy line nobody runs is never fixed, and a fix can touch lines that weren't wrong."
  2. Prof: "You said it counts lines that a later fix touched. A line merged a month before their data ends has had little time to be touched. How can they still give a 180-day figure?"
    You: "As I read their method, each line is watched from its merge until a later commit changes it or their data ends. A line still untouched at the end is right-censored, so it counts only for the time it was watched. Since a line can be ended by a bug fix or by other kinds of change, they use competing-risks methods, the Fine-Gray model, and the 4.0% and 2.7% are cumulative incidences of a bug-fix change at 180 days."
  3. Prof: "Why not simply take one minus Kaplan-Meier for bug-fix changes, treating the other changes as censored?"
    You: "Because a line already rewritten by, say, a refactor can never later be changed by a bug fix. Treating it as censored pretends it still could be, so one minus Kaplan-Meier overstates the bug-fix share. The cumulative incidence function counts those other changes as competing events instead."

Follow-ups (each builds on your last answer)

  1. Prof: "You said a team can choose how many runs to vote over. Does anyone actually run a coding agent several times on one task?"
    You: "A few tools already can. As far as I know, Codex's cloud version can run up to four attempts on one task, but a person then picks one by hand, so nothing is voted on. Voting over agent-written programs is so far mostly in research, like Ron et al. with five agent harnesses."
  2. Prof: "How would a team vote over code at all? Programs aren't numbers."
    You: "You vote on outputs, not on the code: run every version on the same input and return the output most of them agree on, as in N-version programming. A team could also use it before merging: inputs where the versions disagree point to likely bugs, and a person looks at those."
  3. Prof: "But running every version on every input costs three times as much. When is that worth it?"
    You: "If each version fails independently with probability 0.1, one version fails 10% of the time and a 2-out-of-3 vote fails 2.8% of the time, so the two extra runs save 0.072 failures. That pays off when a failure costs more than 2 over 0.072, about 28 times the cost of one run. If the versions tend to fail together, the saving shrinks and that break-even goes up, which is why my plan measures the dependence first."

Q15. What does temperature do mathematically, and why can two runs at temperature 0 still differ?

The model gives a score z_i to every possible next token and turns the scores into probabilities with a softmax, p_i = exp(z_i/T) / Σ_j exp(z_j/T). A low T makes the top token more likely, a high T flattens the choice, and as T goes to 0 the choice becomes the single most likely token.

Q23. A two-state up/down system has failure rate λ and repair rate μ. Write the generator matrix, solve πQ = 0 and derive the availability. Also find the stationary distribution of a 2x2 discrete-time chain as an eigenvector.

Q24. Define the reliability function R(t), the density f(t), the hazard h(t) and MTTF = ∫R(t)dt. Show that the exponential has constant hazard and is memoryless. For the exponential, R(t) = e^(−λt) and f(t) = λe^(−λt), so h(t) = λ is constant. It is memoryless because P(T > s + t | T > s) = e^(−λ(s + t)) / e^(−λs) = e^(−λt) = P(T > t).
