2. Key papers (read for the proposal)

P1. Zheng, Okamura, Dohi: Can Generative AI Enhance the Effectiveness of N-Version Programming? [ABSTRACT ONLY]

  • Venue: SFPVV 2025 (2nd Int. Symposium on Software Fault Prevention, Verification, and Validation, Shanghai, 8 to 9 Nov 2025), LNCS 16356, pp. 1-16, Springer, 2026. DOI 10.1007/978-981-95-6032-5_1. DBLP key conf/sfpvv/ZhengOD25.
  • Access: closed. Springer served a JavaScript challenge to curl; Unpaywall and Semantic Scholar list no open copy; no preprint on arXiv; nothing in the HU repository. I read the abstract (via WebFetch of the Springer page) and the 19-item reference list (Crossref).
  • What the abstract says (quotes): it evaluates LLM-generated code on "correctness and diversity"; it compares "high-performing (e.g., GPT-4o) and lower-performing LLMs"; the two diversity strategies are "temperature tuning and conversation history reuse"; generative AI can improve NVP "when using high-quality models, enabling more reliable outcomes through majority voting", but "the benefits are limited with lower-accuracy models"; diversity measures "do not always translate into improved reliability". It also says NVP "has seen limited adoption in practice due to its high development cost".
  • Second source: Nogueira et al. 2026 (R2 below, read in full) describe it as: "Zheng et al. [29] measured performance improvement from an N-version ensemble using AST-based similarity between solutions." Its reference list includes "Comparing Python programs using abstract syntax trees" (Salazar Paredes 2020), L2CEval, Galapagos, LLaMA and a Claude governance paper. (my note) So it probably used Python, an AST-based diversity measure and several model families, but I cannot confirm any of that, and the proposal does not claim it.
  • Limitations / future work: unknown (not readable).
  • How the proposal builds on it (v2): RQ1 treats the 10 runs of each setting as versions and asks whether a shared context file makes them fail together, and which change between runs (file version, agent, model, temperature) lowers that most. The self-built harness varies temperature on an open-weight model, one of the settings [1] varied. Text in the proposal is limited to the abstract's claims.
  • Action for Sudhanshu: get the PDF before the interview (ask Prof. Zheng politely in a later email, or through a library). Do not quote numbers from it until then.

P2. Guo, Okamura, Dohi: Optimal test case generation for boundary value analysis (read in full)

  • Venue: Software Quality Journal 32(2), pp. 543-566, 2024 (published online 13 Feb 2024). Open access, CC BY 4.0. DOI 10.1007/s11219-023-09659-9. Funded in part by JST.
  • Idea: define boundary coverage distance (BCD): how far a test set is from covering every boundary value. Boundaries come from equivalence partitions defined by output categories, and a set G of minimal input operations (for example plus or minus one); the distance between inputs is the minimum number of operations (Eq. 6). BCD is the max over partitions of the max over boundary points of the min distance to a test input (Eq. 7, 8). Because all boundary values are hard to list, they give a lower bound (boundary points) and an upper bound (boundary components such as line segments).
  • Algorithms: three MCMC-like optimisers that move random test inputs toward boundaries. A1 accepts a candidate if BCD drops; A2 accepts if it lowers the distance for some boundary points without raising others; A3 accepts with a probability. Combined with three BCD calculations (lower, upper, mean) this gives seven methods; they also tried mean instead of max inside BCD.
  • Experiment: five C programs: triType (41 LOC), nextDate (90), findMiddle (36), English (26, their exam-pass example), miniSAT solver.cc (1,069). Mutation testing with five fault types (off-by-one OBOB, ROR, AOR, SVR, LOR), 21 to 35 mutants per program; a mutant is killed if some input gives a different execution path (branch states from Gcov). Test set sizes n = 30 to 50; 10,000 iterations; uniform proposal. Baselines: random testing (RT), adaptive random testing (ART), KLEE concolic testing.
  • Results (Table 5, kill rate): A1 with mean-BCD: triType 0.95, nextDate 1.0, findMiddle 0.97, English 0.8, miniSAT 0.94, against RT 0.66, 0.54, 0.61, 0.36, 0.65 and ART 0.61, 0.51, 0.63, 0.44, 0.64. KLEE: 0.7, 0.9, 0.88, 0.6, and 0 on miniSAT (KLEE made one test case). Mean-based BCD accepted more candidates than max-based. Generation took 154 to 1,194 s for A1 mean-BCD, against about 0.002 s for RT.
  • Stated limitations: boundary points were found "by manual analysis of the source code"; for "large programs or complex numerical computation programs, the identification of the boundary becomes difficult"; non-numerical inputs "such as an array ... or a string" need "further consideration"; higher time cost.
  • Stated future work: integrate analysis tools or "deep learning techniques to predict boundary points"; handle non-numeric inputs. (The lab's 2025 Array paper on machine-learning-driven BVA is the follow-up; I could not download it.)
  • How the proposal builds on it (v2): BCD is a separate stress test in RQ2, not a failure probability (only 30 to 50 inputs per program). Boundary points come from branch conditions in the merged code that compare a parameter with a constant. These are path-based boundaries, which Remark 2 says differ from the paper's output-based ones; the pilot reports what share of functions has them. Kill rate is reported both as in the paper (different execution path; coverage.py branch data instead of Gcov) and by outputs. For strings and lists (the paper's stated limit) he will try one-element edits as minimal operations, as the paper defined custom operations for miniSAT. Python, not C.

P3. Qiu, Dohi, Wu, Zheng, Okamura: A Semi-Parametric Self-Exciting Software Reliability Model with Time-Varying Base Intensity and Shallow Neural Kernel (read in full)

  • Venue: International Journal of Mathematical, Engineering and Management Sciences 11(5), pp. 1907-1928, 2026 (received 5 Jun, accepted 30 Aug 2026). Open access. DOI 10.33889/IJMEMS.2026.11.5.076. First author is a doctoral student; supported by JST SPRING.
  • Idea: NHPP SRMs assume independent increments, so one detected fault does not raise the chance of the next. Real fault detections cluster ("the detection of one fault may lead testers to inspect related modules, trigger additional test cases, or reveal dependent faults"). A Hawkes process adds an excitation kernel to a base intensity. They combine an exponential, decreasing base intensity with a shallow neural network (ReLU) kernel that is piecewise exponential, so likelihoods stay tractable. Mean value function from a Volterra equation solved numerically. Fitting: maximum likelihood, particle swarm then L-BFGS-B, AIC for parametric models.
  • Data: 8 time-domain fault datasets: DS1 SYS4 (197 faults), DS2 SYS1 (136), DS3 SRC3 (104), DS4 SRC1 (397) from Musa and Lyu, and DS5 to DS8 built from fault-related issue histories of four GitHub projects (labelled ChatGPT, MobX, XGBoost, uni-app; 278, 278, 183, 290 faults). Predictions from 20%, 50% and 80% of the time horizon; measure PMSE.
  • Results: the neural-kernel model "is not always the best" but beats most of the 10 parametric Hawkes kernels pairwise; at the 50% point it beats the best NHPP model on 7 of 8 datasets (for example DS2 PMSE 0.363 against 3.889 for gamma NHPP; DS4 15.220 against 45.212). At 20% it is mixed (DS1 5.350 against 0.413 for exponential NHPP) and at 80% parametric kernels and NHPP models often win.
  • Stated limitations: weaker late-stage prediction, which they attribute to overfitting local fluctuations and few late events to learn the kernel tail.
  • Stated future work: other base intensities (Weibull, Pareto), non-parametric base intensities (splines), fully non-parametric Hawkes SRMs.
  • How the proposal builds on it (v2): the field study is now "if time permits". It would build fix data for agent code from GitHub commit messages, as DS5 to DS8 were built from GitHub issues. Because agent code keeps arriving, it uses m(t) = sum_j omega_j G(t - tau_j) with omega_j = L_j exp(beta'z_j) instead of a finite-fault NHPP; a Hawkes term as in this paper is an optional extension. Counts per repository will be far below the 104 to 397 faults per dataset here, so repositories are pooled.

P4. pysrat (Okamura), see section 1.2. README read in full. Used for NHPP fitting and the PR-NHPP regression in the field study.

P5. Yano, Dohi, Okamura: Performance Comparison of Software Reliability Estimation Algorithms (read the method and conclusion; skimmed the tables)

  • Venue: IEEE Computer 57(4), pp. 26-36, 2024. Open copy in the HU repository (https://hiroshima.repo.nii.ac.jp/record/2006696). Note the first author is printed as Taimu Yano in the PDF and Hiromu Yano in Crossref.
  • What it does: compares Newton, Nelder-Mead, EM, ECM, LL-ECM and a proposed Monte Carlo EM for maximum likelihood in NHPP SRMs on time data (DS1 to DS3, for example DS1 with 136 bugs over 88,682 time units) and group data (DS4 to DS6).
  • Conclusion (quote): "the EM and ECM algorithms are still attractive for ensuring global convergence", while "the Monte Carlo EM algorithms may have potential applicability to deal with more complex software reliability models". Weakness: EM and ECM must be derived for each model.
  • Use: background for the oral exam (why pysrat uses EM). Not cited in the proposal.

P6. Qiu, Li, Dohi, Okamura: Infinite-failure SRMs based on non-homogeneous Markov processes (preprint skimmed)

  • Research Square preprint rs-3507541 (Nov 2023); published in Software Quality Journal 34(4), 53, 2026. 22 NHMP-based SRMs (generalized binomial and generalized Polya processes) with 11 baseline intensities, on 8 time-domain and 8 group datasets; better goodness of fit in many cases, better prediction in a limited number. Not cited.

3. Related work the proposal also builds on (read in full)

R1. Ron, Baudry, Monperrus: N-Version Programming with Coding Agents (arXiv:2606.20158, 18 Jun 2026; KTH and Montreal)

  • Repeats the 1986 Knight and Leveson experiment with coding agents: the original Launch Interceptor Program specification, 15 examples and a realcompare function. 5 harnesses (Cursor, Claude Code, Codex, Gemini, OpenCode), 23 models, 3 languages (Python, Rust, Pascal): 69 configurations, 48 pass the 200-case acceptance test (70%; Claude Code 13 of 15, Codex 11 of 15).
  • Oracle: a Python reference validated by 82 unit tests; failure = any of 241 output bits differs. Campaign of 1,000,000 random inputs.
  • Results: 27 of 48 versions have zero failures; the worst fails 10,469 inputs. Coincident failures K = 429 against 115.36 expected under independence (z = 29.20). Per language, K is 17.5 to 155.1 times the expectation. Failures concentrate in LICs 9 and 14 (many agents compute the circumcircle instead of the minimum enclosing circle); LICs 3 and 10 expose a specification ambiguity. Majority-vote triples (all 17,296): mean failures 387.44 to 130.99; 11,844 triples (68.48%) with zero failures against 27 single versions (56.25%).
  • Limits they state: one specification; one version per configuration, so no within-configuration sampling variability ("Rerunning the generation stage at either a different temperature or at a different date would likely change the exact failure counts").
  • Use: the Knight and Leveson z statistic, reference-oracle differential testing, voting triples. My study differs: real repository tasks, a context file as a shared input, and 3 runs per setting, which gives the within-configuration variability they did not measure.

R2. Nogueira, Pattabiraman, Vieira, Campos: A Systematic Methodology for Evaluating Failure Independence in LLM-Generated Code (arXiv:2607.02808, 2 Jul 2026; Coimbra, UNC Charlotte, UBC)

  • 224 contest problems (PROBE, from CodeNet), 12 models, 5 languages, 3 prompting strategies (baseline, chain of thought, "out of the box"), temperature 0.6, 5 samples per setting. Tests: 10 normal plus about 20.6 edge cases per problem; 96.7% line, 94.8% branch coverage, 86.1% mutation score.
  • Measures: CodeBLEU (structure); a pairwise score Z comparing observed shared failures with the hypergeometric expectation (behaviour); majority-vote reliability and "redundancy effectiveness" (share of the gain under independence that voting realises).
  • Results: mean Z 2.04, 65.9% of pairs significantly correlated; on edge cases 3.39 and 71.78%. Reliability 0.88 alone, 0.90 with N = 3, 0.91 with N = 5; effectiveness 0.43 and 0.44, and only 0.27 and 0.24 when all versions come from one model. Prompting had little effect (0.41 against 0.44). No combination beat the strongest single model.
  • Limits they state: contest problems, not real code; no frontier models; test exchangeability assumption.
  • Use: the pairwise score as a baseline for RQ1 (the beta-binomial model is the main analysis); their finding that same-model triples gain least (0.27) motivates varying agent and model between runs.

R3. Earlier context-file papers (verified for the NAIST proposal; see /Users/mafex/Downloads/NAIST-Interview-Prep/04_Papers/GUIDE_3_cited_and_related_papers.md)

  • AIDev [7]: 932,791 agent PRs from 5 agents (MSR 2026 version).
  • Gloaguen et al. [8]: developer files +2.4% success, not significant (p = 0.21), cost up to 19% higher (p.6). Per-task cost (Table 2): Claude Code with Sonnet-4.5 1.15 to 1.51 USD, Codex with GPT-5.2 0.32 to 0.57, Codex with GPT-5.1 mini 0.18 to 0.22, Qwen3-30B-Coder 0.12 to 0.15 (estimated from OpenRouter prices). The 138-task benchmark (CTXBench in v3, AGENTbench in the code) is public: Hugging Face eth-sri/agentbench (138 rows, 12 repos, Docker images, test commands, merged 2022-08 to 2026-01), harness at github.com/eth-sri/agentbench.
  • Zhang et al. "Guardrails Beat Guidance" [9]: leave-one-out of 18 generic rules on 35 tasks. Using a 5-point threshold, the 3 helpful ("shaping") rules were all prohibitions; three positive rules also lowered the pass rate when removed, by 2.9 points each. Only "do not refactor unrelated code" was individually significant (20 points, McNemar p = 0.016), and the authors call the polarity pattern suggestive (sec. 6.4, Table 4). Screening: 3 baseline runs per task, keep tasks solved 1 or 2 of 3; pilot found 47% always and 27% never solved. About 5 USD per task and condition with Claude Opus 4.6. Superposition test on 5 rule pairs.
  • Xia and Miller [10]: 182 repositories; "4.0% of agentic lines changed by a bug-fixing commit by 180 days compared with 2.7%" of human lines; corrective maintenance sHR 1.46; line-level Cox and Fine-Gray competing-risks models. Rechecked on 26 Oct.
  • AIDev [7]: dataset cutoff 1 August 2025 (p.1), so post-cutoff tasks cannot come from AIDev's PRs.

R4. Eckhardt and Lee 1985 [11] (read in full as the NASA report version)

  • Cited as: D. E. Eckhardt, L. D. Lee, "A Theoretical Basis for the Analysis of Multiversion Software Subject to Coincident Errors", IEEE TSE SE-11(12), pp. 1511-1517, Dec 1985, DOI 10.1109/TSE.1985.231895 (Crossref). The full text read is NASA TM-86369, Jan 1985, "A Theoretical Basis for the Analysis of Redundant Software Subject to Coincident Errors" (https://ntrs.nasa.gov/api/citations/19850015006/downloads/19850015006.pdf), the report version of the same work. He should read the TSE version too before the interview.
  • What it says: theta(x), the intensity of coincident errors, is the share of a population of independently developed versions that fail on input x. For two versions drawn at random, P(both fail) = integral of theta(x)^2 dQ = p^2 + sigma^2 (eqs. 11 to 15). Theorem 2: versions fail independently if and only if theta(x) is constant (variance zero). Section 5: N-version can be worse than one version when theta(x) > 0.5 on some inputs, and system failure probability need not fall monotonically with N.
  • Use: the beta-binomial model for RQ1 puts a Beta distribution on theta(X). Littlewood and Miller (TSE 1989) extend this with forced diversity, which fits the "which change between runs" question, but no full text was found, so it is not cited.
