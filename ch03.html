Part B. The slides (about 6 minutes)

Slide 1. Title (about 30 seconds)

Cue: my name, AGENTS.md, every run reads it, same mistakes, voting

My name is Sudhanshu Pandit. Coding agents like Claude Code and Codex read a rules file in the repository, like this AGENTS.md. And every run of the agent reads the same file.

So my question is simple. If I run the agent three times on the same task, do the runs make the same mistakes? Because the more mistakes they share, the less voting over the runs can help.

First, a bit about me.

Cue: degree, Layerpath, BrandMemory, Magic Editor, Yuki, rules got cut, full time from April

I finished my B.E. in Computer Science at Sri Sairam College of Engineering, under VTU, this May.

Since last November I've been an AI engineer at Layerpath. It's a small startup that makes interactive product demos. I'm on the founding team, and I build its AI features.

On the right are three things I built. BrandMemory gives a company's writing rules to a model. Magic Editor is an AI assistant that edits product demos, and the user approves every edit. And Yuki 2.0 is my side project, a desktop agent for Windows. It's public on GitHub.

Slide 3. Background (about 75 seconds)

Cue: voting needs different mistakes, Eckhardt and Lee, your paper, 429 vs 115, 0.43, no rules file, one helper

Now the background.

Voting only helps if the versions rarely make the same mistakes. In 1985, Eckhardt and Lee showed that two versions from the same process fail independently only if every input is equally hard. But in real software some inputs are harder than others, so versions fail together more often than independence predicts.

Your paper with Prof. Okamura and Prof. Dohi asked whether versions written by generative AI make N-version programming work better. Voting made strong models like GPT-4o more reliable, but helped little with weak ones. And more diversity didn't always mean more reliability.

Two studies this year looked at code written by LLMs. In one, two or more of 48 programs failed together on 429 of a million inputs, where independence predicts about 115. In the other, voting over three versions got only 0.43 of the gain that independence would give.

But neither study used a rules file. In a real repository, every run reads the same one. So say the file tells every run to use one helper, and that helper gets an edge case wrong. Then every run gets the same bug.

[Next slide]

Slide 4. Two research questions (about 45 seconds)

Cue: RQ1 how much they fail together, what lowers it; one number, zero means independent; RQ2 one rule, beyond the tests

So I have two questions.

RQ1: when several runs solve one real task with the same rules file, how much more often do they fail on the same inputs than independence predicts? And what lowers that most: changing the file, the agent, the model, or the temperature?

I measure it with one number from a beta-binomial model. Zero means the runs fail independently. The higher it is, the more they fail together.

RQ2: if I replace one real rule with neutral text, does the code get more or less reliable? Not just on the task's tests, but beyond them.

[Next slide]

Slide 5. Design (about 75 seconds)

Cue: real pull request, five rules, ten runs each, must pass the tests, 10,000 random inputs, count shared failures, 820 runs, pilot

Here's how one test works.

I take a merged pull request from a real project. Its tests fail before the change and pass after it. I start from 138 public Python tasks from Gloaguen and colleagues, plus newer pull requests. I pick about five rules a script can check, with two tasks each.

Then I run each setting ten times: Claude Code, Codex with two models, and my own small harness with an open-weight model at two temperatures. A run only counts if it passes the pull request's tests.

Then I look past the tests. I give each function the tests call at least 10,000 random inputs and compare every answer with the merged code. I check 20 disagreements per task by hand. Your lab's boundary value method comes in here as an extra stress test.

Last, I count how often the runs fail on the same inputs, and fit the model. That also tells me how often a two-out-of-three vote would fail.

In total that's 820 runs, including 120 to screen the tasks first. At the costs in Gloaguen's paper, that's about 420 to 590 dollars. A small pilot comes first, to check the real numbers.

[Next slide]

Slide 6. Plan, and why this lab (about 65 seconds)

Cue: courses first, pilot, main runs, model, paper, thesis; what I hope to end with; probabilistic evaluation; agents from me, reliability models from you

Last, my plan.

In the first half of Year 1, I take probability, statistics and reliability courses, build the harness and run the pilot. Then the main runs and RQ2. In Year 2, I fit the shared-failure model, write a first paper, and then the thesis.

At the end I hope to have a model that tells a team how many runs to vote over for a given cost, an answer on whether one real rule changes reliability, and open data for others.

Why this lab? Your lab's page says you pair each technique with probabilistic evaluation, to show how much the quality really improved. That's exactly what my question needs. I can bring the agent side and the repository mining. What I want to learn here is how to fit and test reliability models.

That's all from me. Thank you, and I'd be glad to hear your advice.
