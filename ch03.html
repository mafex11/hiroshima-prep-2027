Part B. The slides (about 5 minutes)

Slide 1. Title (about 20 seconds)

Cue: same rules file, many runs, do they fail together, voting

My question is on this slide. When you run a coding agent several times on the same task, every run reads the same rules file, the AGENTS.md or CLAUDE.md in the repository. So do those runs fail on the same inputs? And if they do, how much does voting still help?

[Next slide]

Slide 2. About me (about 40 seconds)

Cue: VTU 2026, Layerpath, BrandMemory, Yuki 2.0, full time from April

I finished my B.E. in Computer Science at Sri Sairam College of Engineering, under VTU, this May. Since last November I've been an AI engineer at Layerpath, a small startup. I was on the founding team, and I build its AI features.

I use Claude Code and Codex every day. I review and test their changes, and I keep the rules files they read. At work I once found that some rules we gave a model had no effect, because a length limit cut them first. Since then I check whether a model really follows an instruction.

I also built Yuki 2.0, a desktop agent for Windows, in plain Python. It's public on my GitHub. If I'm admitted, I'll leave my job before April and study full time.

[Next slide]

Slide 3. Background (about 60 seconds)

Cue: Eckhardt and Lee, your paper, 429 vs 115, 0.43, shared file

Voting only helps if the versions rarely fail on the same inputs. Eckhardt and Lee showed that two versions from the same process fail independently only if every input is equally hard.

Your paper with Prof. Okamura and Prof. Dohi asked whether generative AI can make N-version programming work better. Voting made strong models more reliable but helped little with weak ones, and more diversity didn't always mean more reliability.

Two studies this year found that LLM-written versions fail together more than independence predicts. In one, two or more of 48 programs failed together on 429 of a million inputs, against about 115 expected. Voting over three still cut the failures a lot. In the other, voting got only 0.43 of the gain that independence would give, and 0.27 when all three came from one model.

My point is this. Both studies used no rules file. But in a real repository, every run reads the same file. If a rule says "use this helper" and the helper breaks on an edge case, every run gets the same bug.

[Next slide]

Slide 4. Two research questions (about 40 seconds)

Cue: RQ1 fail together, which change lowers it; RQ2 one rule, beyond the tests

So I have two questions.

RQ1: when several runs solve one real task with the same rules file, how much more often do they fail on the same inputs than independence predicts? And which change between runs lowers that most: the file version, the agent, the model, or the temperature? I measure it with the correlation of a beta-binomial model, where zero means independence.

RQ2: if I replace one real rule with neutral text, does the code get more or less reliable, beyond the task's own tests?

[Next slide]

Slide 5. Design (about 70 seconds)

Cue: real PRs, 5 rules x 2 tasks, 10 runs, 820 runs, 10,000 inputs, beta-binomial

A task is a merged pull request whose tests fail before the change and pass after it. I start from the 138 public Python tasks in Gloaguen and colleagues, plus newer pull requests. I pick about five rules a script can check, with two tasks each.

Each setting runs ten times: Claude Code, Codex with two models, and my own small harness with an open-weight model at two temperatures. That's 820 runs, about 420 to 590 dollars.

A run only counts as a version if it passes the pull request's tests. Then I test it on at least 10,000 generated inputs per function, against the merged code, and I check 20 disagreements per task by hand. Your lab's boundary value method comes in as an extra stress test.

For RQ1, if θ of x is the chance a run fails on input x, two runs both fail with probability p squared plus the variance of θ. I fit a beta-binomial model by maximum likelihood, with a bootstrap over runs. From it I get how often a two-out-of-three vote fails.

[Next slide]

Slide 6. Plan and why this lab (about 40 seconds)

Cue: courses first, pilot, main runs, model, paper; your lab's probabilistic evaluation

In the first half of Year 1, I take probability, statistics and reliability courses and build the harness and a pilot. Then the main runs and RQ2. In Year 2, the shared-failure model, a first paper, and the thesis.

At the end I hope to have a fitted model that tells a team how many runs to vote over for a given cost, an answer on whether one real rule changes reliability, and open data.

Why this lab: your lab pairs each technique with probabilistic evaluation, to show how much quality really improved. That's what my question needs. I can bring the agent side and the repository mining. Fitting and testing reliability models is what I want to learn here.

Thank you. I'd be glad to hear your advice.
