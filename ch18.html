Every number and claim in your submitted plan

When and how long: Sun 15 Nov, 45 minutes. Say each line out loud.

What this file is: every number and factual claim in the Research Plan you submitted (Research_Plan.md), in the order it appears. For each one: where it comes from (reference, and the section of that paper), what the paper text says, and one plain line you can say out loud. Then each reference [1] to [12] in two lines.

How it was checked: on 12 Nov 2026, against the paper texts in /Users/mafex/code/personal/masters-research/2027-refresh/hiroshima-application/qbank-2026-11-01/paper_text/ (the PDFs are in 07_Lab_Papers/pdfs/), and again on 13 Nov 2026, when the volume, issue and page numbers were checked on Crossref, the pysrat README and version history on GitHub and PyPI, and the [8] dataset on Hugging Face. [1] and [12] have no full text in the kit, only an abstract, so those lines are checked against the abstract only. [4] is a software package, checked against its README.

Labels:

  • MATCHES: the paper says the same thing.
  • MATCHES (rounded): same number, rounded in the plan.
  • PARTLY: true, but the paper says a bit more or a bit different. Be ready.
  • NOT IN THE PAPER TEXT: true as far as the kit knows, but the source is not the paper itself.
  • ABSTRACT ONLY: checked against the abstract, nothing more.
  • YOUR DESIGN: a choice you made. No source needed, but you must be able to say why.

Read this first: what did not match, or needs care

No number in the plan contradicts its source paper. Every figure (429, about 115, 387, 131, 224, twelve, 0.43, 0.27, 2.4%, p = 0.21, 19%, 18 rules, 5 points, 182, 4.0%, 2.7%, 180 days, 138, 12, 30 to 50, the per-task costs) is in the paper it is cited to. The points below are places where the wording is looser than the paper, or where you need care with a number. They are the places a careful professor could catch.

  1. PARTLY: screening "as in [9]". The plan says "I screen about 20 candidate tasks with 3 runs per agent and drop tasks an agent never solves, as in [9]." In [9] (Section 5, "Discriminative task selection") they screened all 500 SWE-bench Verified tasks with three runs each and kept only the 58 tasks solved 1 or 2 times out of 3. So [9] dropped the always-solved tasks too. You keep them on purpose. If asked, say: "I copy their screening, but unlike them I keep tasks that are always solved, because I measure failures beyond the tests, and those tasks give the most versions." (The earlier proposal said this; the submitted plan dropped that clause.)
  2. WORDING: "the pull request's tests". In [8] most pull requests had no tests of their own. An LLM agent wrote new tests from the task text and the merged change; the authors checked that they fail before and pass after, reviewed them by hand, and added the repository tests that pass on the merged code (Section 3, "Generating Unit Tests"). They cover 75% of the modified code on average (Table 1). Say "the task's tests" if pushed. (Existing answer: 05_Questions_on_My_Proposal/07_questions_on_my_proposal.md Q22.)
  3. NOT IN THE PAPER TEXT, BUT CHECKED: "public with Docker images and test commands". The paper says the agent runs in a Docker container (Appendix A.1) and that an agent wrote a script per task that sets up the environment and runs the tests (Section 3, "Environment Set-Up"). It does not say "public" in the text you have. On 13 Nov 2026 the dataset was on Hugging Face as eth-sri/agentbench: 138 rows, the same 12 repositories with the same counts as the paper's Figure 2, a docker_image and test_commands for each task, and PRs merged from 15 Aug 2022 to 8 Jan 2026. If asked: "The tasks are on Hugging Face with a Docker image and test commands for each."
  4. CARE: "five programs" in [2]. The paper says "five programs" (Section 5.4) and measures them with Gcov, a C/C++ tool; it doesn't say they are all C (one is the miniSAT solver.cc). Say "five small programs", not "five C programs". (An older version of 01_proposal_explained_simply.md said "five C programs"; it is fixed.)
  5. CARE: 0.43 in [6]. The plan's "0.43" is right: it is the overall figure for all three-version sets (Table II, N = 3). It is not the figure for "mixed models": mixed-model triples got 0.44, same-model triples 0.27. Say: "0.43 overall, 0.44 when the models differ, 0.27 when they are the same." (01_proposal_explained_simply.md and 02_glossary.md now say this too.)
  6. TITLE: [11]. You cite the IEEE TSE paper, "A Theoretical Basis for the Analysis of Multiversion Software Subject to Coincident Errors". The version you read is the NASA report TM-86369 (January 1985), titled "... Redundant Software Subject to Coincident Errors". Same authors, same model, same Theorem 2. The TSE title, volume and pages (SE-11(12), 1511 to 1517) match Crossref (checked 13 Nov 2026, DOI 10.1109/TSE.1985.231895). If asked: "I read the NASA technical report version in full. It is the same work."
  7. ISSUE NUMBER: [2]. The PDF header says "Software Quality Journal (2024) 32:543-566". Volume 32 and pages 543 to 566 match. The issue number "(2)" is not printed in the text, but Crossref gives issue 2 (checked 13 Nov 2026), so the reference is right.
  8. ABSTRACT ONLY: [12]. Only the title and abstract were seen. The pages 110 to 119 match Crossref (DOI 10.1109/APSEC.2004.29, checked again 13 Nov 2026). Crossref's full title adds a subtitle, "Unified Modeling and Estimation Framework"; the plan's shorter title is fine. Say so if asked about details.
  9. VERSION: [4] pysrat 0.2.7. The version comes from PyPI (0.2.7 uploaded 21 Sep 2026), not from the README. A newer version, 0.2.8, came out on 28 Oct 2026 (PyPI, checked 13 Nov 2026), before you submitted the plan. Not a mistake, since 0.2.7 was the version you checked, but know it. If asked: "I cited 0.2.7, the version I looked at; 0.2.8 is out now."
  10. LIKELY PUSH: "387 to 131" are means. In [5] the median failure count is 0 for both single versions and triples. The mean is pulled up by a few very bad versions (the worst single version fails 10,469 of a million inputs). Not a mismatch, but be ready (H17 in 05_Questions_on_My_Proposal/02_hard_questions_from_other_professors.md).
  11. LIKELY PUSH: "up to 19%" in [8]. That is the figure for developer-written files (Section 4.2). The paper's abstract says context files raise cost "by over 20% on average", which is about LLM-generated files (20% and 23% on the two benchmarks). If someone quotes 20%, say which file type each number is about.
  12. LIKELY PUSH: the cost "about 420 to 590 US dollars". It matches the arithmetic if you take the full range of Table 2 in [8], across both benchmarks and all three file settings. On their 138 tasks only, it would be about 440 to 545. Both are fine; know which one you used.
  13. CONTEXT: [10] does not use AIDev. Its 182 repositories come from a dataset called "Agents in the Wild", with commits merged from 1 May 2025 to 31 May 2026. Don't link [10] and [7].
  14. CONTEXT: AIDev [7] has no full repository history. It stores commits linked to agent pull requests (SHA, author, message), and its data stop on 1 August 2025. Part 1. Every claim, in order

Background

B1. "In N-version programming, a vote over several versions of a program helps only if the versions rarely fail on the same inputs."

  • Source: the general idea of N-version programming; stated the same way in the introductions of [5] and [11].
  • Check: MATCHES (general statement).
  • Say: "If two of three versions are wrong in the same way on an input, the vote picks the wrong answer."

B2. "Eckhardt and Lee showed that two versions drawn at random from one development process fail independently only if every input is equally likely to make a version fail [11]."

  • Source: [11], NASA TM-86369, Section 3.0 "Independent Errors", equations (10) to (16) and Theorem 2.
  • Paper: "a necessary and sufficient condition for (unconditional) independent failure of the component versions is that θ(x) be constant except on a subset A of Ω for which Q(A) = 0." θ(x) is "the intensity of coincident errors" and Q is the usage distribution.
  • Check: MATCHES.
  • Say: "Independence needs every input to be equally hard, and real inputs never are."

B3. "Zheng, Okamura and Dohi asked whether generative AI can enhance the effectiveness of N-version programming [1]."

  • Source: [1], the title and the abstract.
  • Check: ABSTRACT ONLY.
  • Say: "It's the question of your 2025 paper."

B4. "They compared high-performing models (e.g., GPT-4o) with lower-performing ones, and varied the temperature and whether the conversation history was reused."

  • Source: [1], abstract: "comparing high-performing (e.g., GPT-4o) and lower-performing LLMs, and evaluate two diversity-promoting strategies; i.e., temperature tuning and conversation history reuse."
  • Check: ABSTRACT ONLY, MATCHES. (On 2 Nov Prof. Zheng also told you they used GPT-4o and GPT-4o mini.)
  • Say: "Strong against weak models, and two ways to add diversity: temperature and reusing the conversation."

B5. "Majority voting made the strong models more reliable but helped little with the weak ones."

  • Source: [1], abstract: "generative AI can improve NVP effectiveness when using high-quality models, enabling more reliable outcomes through majority voting. However, the benefits are limited with lower-accuracy models."
  • Check: ABSTRACT ONLY, MATCHES.
  • Say: "Voting helped the strong models, not much the weak ones."

B6. "More diversity did not always mean higher reliability."

  • Source: [1], abstract: diversity can be raised by temperature and history, "such measures do not always translate into improved reliability."
  • Check: ABSTRACT ONLY, MATCHES.
  • Say: "More different versions are not always better versions."

B7. "Two 2026 studies found that LLM-written versions fail together more often than independence predicts."

  • Source: [5] (arXiv, 18 Jun 2026) and [6] (arXiv, 2 Jul 2026), both abstracts.
  • Check: MATCHES.
  • Say: "Two papers this summer, two different set-ups, same answer: not independent."

B8. "Ron et al. had five agent harnesses implement the specification from the 1986 Knight and Leveson experiment."

  • Source: [5], Section III and Table I: "69 coding agents over 5 harnesses (Cursor, Claude Code, OpenAI Codex, Gemini, OpenCode)", in Pascal, Python and Rust, from the Launch Interceptor Program specification.
  • Check: MATCHES.

  • Check: MATCHES (rounded).

B11. "Voting over three programs still cut the mean failure count from 387 to 131 [5]."

  • Source: [5], Section IV.E (RQ5): "the mean failure count drops from 387.44 for single versions to 130.99 for triples", over all 17,296 triples of the 48 versions.

Part 2. The references in two lines each

[1] J. Zheng, H. Okamura, T. Dohi, "Can Generative AI Enhance the Effectiveness of N-Version Programming?", SFPVV 2025, LNCS 16356, pp. 1-16, 2026.

  • What it did: had LLMs write several versions of the same programs, compared a strong model (GPT-4o) with weaker ones, and tried two ways to make versions differ (temperature, conversation history reuse). Voting helped with strong models, little with weak ones, and more diversity did not always mean more reliability.
  • Why it's in the plan: RQ1 takes its question to real repository tasks with coding agents and a shared context file. You have read only the abstract (paywalled); ask for a copy.

[2] X. Guo, H. Okamura, T. Dohi, "Optimal test case generation for boundary value analysis", Software Quality Journal 32(2), pp. 543-566, 2024.

  • What it did: defined boundary coverage distance, a measure of how far a test set is from covering every boundary, and three generators that push inputs towards boundaries; on five small programs (four from earlier studies plus the paper's own example, a program that decides from listening and reading scores whether an English credit is earned, instrumented with the C/C++ tool Gcov) the best one killed 0.8 to 1.0 of the mutants, against 0.36 to 0.66 for random testing.
  • Why it's in the plan: it is the boundary stress test in RQ2. You automate the boundary points that [2] found by hand.

[3] N. Qiu, T. Dohi, J. Wu, J. Zheng, H. Okamura, "A Semi-Parametric Self-Exciting Software Reliability Model with Time-Varying Base Intensity and Shallow Neural Kernel", IJMEMS 11(5), pp. 1907-1928, 2026.

  • What it did: a Hawkes-process reliability model, where each fault found raises the chance of finding more soon, with a decaying base rate and a small neural-network kernel; tested on eight datasets, four built from GitHub issue histories, compared by predictive mean squared error.
  • Why it's in the plan: it shows the lab already builds fault data from GitHub, which is how the optional field study would get its data.

[4] H. Okamura, pysrat, version 0.2.7, 2026, https://github.com/SwReliab/pysrat.

  • What it is: Prof. Okamura's Python package that fits 12 NHPP reliability models with EM, in a scikit-learn style (fit, params_, aic_), plus metrics-based models with covariates.
  • Why it's in the plan: it supplies the delay distribution G for the field model. The plan cites 0.2.7; 0.2.8 has been on PyPI since 28 Oct 2026. You have run 0.2.8: the README quick start, then all 12 models on the Musa SS1A data that comes with it, where log-logistic fitted best by AIC (see 09_Math/13_pysrat_hands_on.md).

[5] J. Ron, B. Baudry, M. Monperrus, "N-Version Programming with Coding Agents", arXiv:2606.20158, 2026.

  • What it did: repeated the 1986 Knight and Leveson experiment with 69 coding-agent configurations (5 harnesses, 3 languages); 48 passed the 200-case acceptance test; on one million inputs, 429 joint failures against 115.36 expected (z = 29.20), yet voting triples cut the mean failure count from 387.44 to 130.99.

[6] R. P. Nogueira et al., "A Systematic Methodology for Evaluating Failure Independence in LLM-Generated Code", arXiv:2607.02808, 2026.

[8] T. Gloaguen et al., "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?", arXiv:2602.11988, 2026.
