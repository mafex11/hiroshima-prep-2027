Anything marked [CONFIRM] must be true before you say it. Anything marked [FILL] is yours to fill. Funding is confirmed: you fund your studies yourself.

About the research

Q1. Can you explain your research in a few sentences? I treat repeated coding-agent runs on one real task as N versions of a program. RQ1 measures how much more often they fail on the same inputs than independence predicts, and which change between runs lowers that most: the context file, the agent, the model or the temperature. RQ2 checks whether replacing one real rule in the context file with neutral text changes reliability beyond the task's own tests. The main result is a fitted model that tells a team how many runs to vote over at a given cost.

Q2. Why reliability? You are an engineer. Why research, and why now? At work I review and test agent changes every day, but tests only cover the cases someone thought of. I have also seen an instruction to a model have no effect at all, while our logs said it was applied. So "the tests passed" doesn't feel like the full answer to me. I want real numbers for how often this code fails and how much voting helps, and that needs probability models I can't build yet.

Q3. Have you read our N-version paper? How is your work different? I've only read the abstract, because the full text is behind the Springer paywall. [CONFIRM: change this if you get the paper and read it before the call.] From it, you compared strong and weak models and two ways to add diversity, temperature and conversation history reuse. My plan takes that question to real repository tasks with coding agents, and adds the shared context file as a possible cause of common failures. Could I ask you for a copy?

Q4. Why can't you just assume the runs fail independently? Eckhardt and Lee showed that two versions from the same process fail independently only if every input is equally hard. Real inputs are not equally hard: some edge cases trip up almost every run. If θ(x) is the chance that a run fails on input x, two runs both fail with probability p^2 + Var θ(X). So any spread in difficulty makes joint failures more likely than p^2.

Q5. How would voting even work with code patches? Each run gives a patch. In practice the vote picks the patch whose outputs agree with most of the other runs, and my model predicts how often that pick is wrong. On an input where a run fails with chance θ, a 2-out-of-3 vote fails with chance 3θ^2 - 2θ^3, and averaged over inputs that is E[3θ^2 - 2θ^3]. I compare that with 3p^2 - 2p^3, what you'd get if runs were independent, and I also find the odd number of runs N that minimises run cost plus expected failure cost.

Q6. Why a beta-binomial model? How will you fit it? θ is a chance between 0 and 1 that changes from input to input, and the Beta distribution is a flexible model for that, so the number of failing runs out of k on one input is beta-binomial. Its intraclass correlation, ρ = 1/(a + b + 1), is zero under independence, so it measures directly how much runs fail together. I fit it per task and setting by maximum likelihood, with intervals from a bootstrap that resamples runs, because the same runs meet every input. If almost every input has zero failures, a zero-inflated version may fit better, and the pilot will show that.

Q7. How will you find failures that the tests miss? A run's change only counts as a version if it passes the pull request's own tests. Then I generate at least 10,000 random inputs per entry point, from the type hints and the values in the PR's tests, and compare each version with the merged code under a fixed rule: a float tolerance, the same exception class, and order ignored for unordered collections. I check 20 disagreements per task by hand and drop inputs where the merged code itself is wrong. The honest limit is that if the merged code has the same bug, this kind of testing can't see it.

Q8. What do you know about probability, statistics and reliability models like NHPP? My only statistics course so far is BCS301 in my third semester. It covered probability distributions, Markov chains, hypothesis tests and ANOVA. I can explain the models in my plan, and the basic NHPP idea that the expected number of faults found by time t follows a mean value function, like ω(1 - e^(-bt)) in the Goel-Okumoto model. I haven't fit an NHPP to real data myself yet [CONFIRM: unless you install pysrat and run its example before the call], which is why statistics and reliability courses come first in my plan.

Q9. Is this realistic in two years, in time and money? My schedule puts courses, the models, the harness and a pilot in the first half of Year 1, the main runs and RQ2 in the second half, the shared-failure model and a first paper in the first half of Year 2, and the thesis last. RQ1 is the core, and the field data part is only if time permits, so it can be dropped. The 820 runs cost about 420 to 590 US dollars at the per-task prices in Gloaguen et al., and newer models may cost more. I'd ask whether that fits a lab budget, and if not, move more runs to the open-weight model. [CONFIRM: add "and I can pay for a small pilot myself" only if you really will.]

Harder follow-ups, if he digs

  • "Why 10 runs per setting?" It balances cost against seeing how many runs fail on each input. The pilot will show whether 10 gives a useful interval for ρ. If not, I'd change it then.
  • "What if every run passes every input?" Then that task's failure probability is close to zero and ρ can't be estimated there. I report that, because it is a result too. But passing the PR tests every time doesn't mean passing every generated input. That's why I keep tasks the agents always solve.
  • "Why not conversation history reuse, like in our paper?" It's not in the plan now. My own harness controls the whole prompt, so I could add it as another setting if you think it's worth it.
  • "How do you know removing the rule changed what the agent did?" A checker script confirms it. I keep a checker only if it agrees with my hand labels on at least 90% of 20 or more examples, and I report Cohen's kappa. Compliance is a check on the setup, not a research question.
  • "Can't you set the temperature in Claude Code or Codex?" As far as I know, neither CLI documents a temperature setting. So I treat each setting as a distribution of runs, and I vary temperature in my own harness.
  • "How unsure are your estimates?" The bootstrap over runs gives intervals for ρ and for the vote failure chance, so I report a range, not one number.
  • "Tell me about the infinite-server queue model." In my field-data part, each merged agent change adds some expected faults that are found after a delay, so m(t) = Σ ω_j G(t - τ_j). Prof. Dohi used the same infinite-server queue idea in 2004 to unify finite and infinite fault NHPP models. [CONFIRM: so far only the abstract of that paper has been read. Say so if he asks for details.]
  • Anything you don't know: "I don't know that yet. I'd start by reading ..., and I'd be glad if you could point me to the right material."
