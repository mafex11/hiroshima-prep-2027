Chapter 34 of 62

CS fundamentals: quick review

When and how long: Day 11.

Informatics professors may ask any CS graduate a few basics: the complexity of quicksort, what a hash table does, why 0.1 + 0.2 is not 0.3. Your plan is about testing code, so the testing section matters most. Keep the answers short: one sentence, one example, stop.

How the answers were checked. The numbers here (binary search comparisons, the Dijkstra example, the counting answers, the floating point examples, the coin-change and LCS values, the birthday probability) were run in Python 3.14 on 12 Nov 2026 and again on 13 Nov 2026; all matched. One surprise worth knowing: in recent Python (your 3.14 does it; it started in Python 3.12, which switched sum() to Neumaier compensated summation for floats), sum([0.1] * 10) == 1.0 is True. Adding 0.1 ten times in a plain loop still gives 0.9999999999999999. So use 0.1 + 0.2 == 0.3 (False) as your example, not the sum. Nothing in this file is marked [CHECK].

1. Big-O

  • Definition. f(n) = O(g(n)) if there are constants c > 0 and n0 with f(n) <= c g(n) for all n >= n0: an upper bound on growth. Omega is a lower bound, Theta is both.
  • Common classes, slowest growth first: 1, log n, n, n log n, n^2, n^3, 2^n, n!.
  • Recurrences you should know: T(n) = T(n/2) + 1 gives log n (binary search). T(n) = 2T(n/2) + n gives n log n (merge sort). T(n) = 2T(n/2) + 1 gives n (tree traversal).
  • Amortised cost: a dynamic array doubles its size when full, so one append may cost O(n), but the average over many appends is O(1).

2. Sorting

Algorithm Best Average Worst Extra space Stable?
Insertion sort n n^2 n^2 1 yes
Merge sort n log n n log n n log n n yes
Quicksort n log n n log n n^2 log n (stack) no
Heapsort n log n n log n n log n 1 no
Counting / radix n + k n + k n + k n + k yes
  • Quicksort's worst case comes from bad pivots, for example always picking the first element of an already sorted array. A random pivot makes it very unlikely.
  • Stable means equal keys keep their original order.
  • Lower bound: any comparison sort needs about log2(n!) comparisons, which is about n log2 n, because a decision tree with n! leaves has height at least log2(n!). (log2(10!) = 21.8.)
  • Python's sorted uses Timsort: stable, n log n worst case, close to n on nearly sorted data.

3. Binary search

  • On a sorted array, compare with the middle and keep the half that can contain the target. O(log n).
  • At most ceil(log2(n + 1)) comparisons: 20 for 1 million items, 30 for 1 billion.
  • Typical bugs: off-by-one in the bounds (a boundary value bug), an infinite loop when lo and hi stop moving, and overflow of (lo + hi)/2 in fixed-width integer languages (write lo + (hi - lo)/2).

4. Hashing

  • A hash function maps a key to a bucket. A hash table gives average O(1) insert and lookup, worst O(n) if many keys collide.
  • Collisions are handled by chaining (a list per bucket) or open addressing (probe the next slots). Keep the load factor (items per bucket) bounded by resizing.
  • Collisions come sooner than you think: with 365 buckets, 23 keys already collide with probability 0.507 (the birthday problem).
  • Python's dict and set are hash tables.

5. Trees and heaps

  • Binary search tree: left subtree < node < right subtree. Search and insert cost O(height): O(log n) if balanced (AVL, red-black), O(n) if you insert sorted keys into a plain BST. In-order traversal gives the keys in sorted order.
  • Binary heap: a complete binary tree where each parent <= its children (min-heap). find-min O(1), insert and extract-min O(log n), build from n items O(n). It is the usual priority queue (Python heapq).

6. Graphs

  • Storage: adjacency list, O(V + E) space (good for sparse graphs). Adjacency matrix, O(V^2).
  • BFS: a queue, level by level. Shortest paths by number of edges in an unweighted graph. O(V + E).
  • DFS: a stack or recursion, as deep as possible first. Cycle detection, topological sort, connected components. O(V + E).
  • Dijkstra: shortest paths from one source with non-negative weights. Repeatedly take the closest unfinished vertex from a priority queue and relax its edges. O((V + E) log V) with a binary heap. It fails with negative edges, because a finished vertex could later get a shorter path. Use Bellman-Ford (O(VE)) then. All pairs: Floyd-Warshall, O(V^3).
  • Worked Dijkstra example. Edges A-B 4, A-C 1, C-B 2, B-D 1, C-D 5 (undirected). From A: take A (0); relax C = 1, B = 4. Take C (1): B = min(4, 1 + 2) = 3, D = 6. Take B (3): D = min(6, 3 + 1) = 4. Take D. Distances A 0, C 1, B 3, D 4; path A-C-B-D.
  • Topological sort orders a DAG so every edge goes forward, for example a build or dependency order.
  • Minimum spanning tree: Kruskal (sort edges, add if no cycle, union-find) or Prim (grow from a vertex).

7. Dynamic programming

  • Use it when a problem has optimal substructure (the best answer is built from best answers to subproblems) and overlapping subproblems (the same subproblem appears many times). Store each subproblem's answer once.
  • Top-down with memoisation, or bottom-up with a table.
  • Examples: Fibonacci in O(n) instead of exponential. Longest common subsequence in O(mn) (LCS of ABCBDAB and BDCABA has length 4). Edit distance O(mn). 0/1 knapsack O(nW), which is "pseudo-polynomial" because W is a number, not an input size. Ways to make 10 from coins 1, 2, 5: 10.

8. P, NP and what is hard

  • P: problems solvable in polynomial time.
  • NP: problems whose yes-answers can be checked in polynomial time, given a certificate (for example a satisfying assignment).
  • NP-complete: in NP, and every NP problem reduces to it in polynomial time. SAT (Cook-Levin), 3-SAT, vertex cover, subset sum, the decision version of TSP.
  • NP-hard: at least as hard as NP-complete problems, but not necessarily in NP (for example the optimisation version of TSP).
  • P is inside NP. Whether P = NP is open. Most people believe P != NP.
  • Undecidable is a different, stronger thing: no algorithm at all. The halting problem is undecidable. A consequence for testing: no tool can decide every program's correctness in general, which is why testing samples inputs.
  • Plain words: "P is what we can solve fast. NP is what we can check fast. Nobody has proved they are different, but nobody has found fast algorithms for the hardest NP problems either."

9. Logic, sets and counting

  • Logic: p -> q is the same as (not p) or q, and as its contrapositive (not q) -> (not p). Not its converse. De Morgan: not(p and q) = (not p) or (not q).
  • Sets: |A or B| = |A| + |B| - |A and B|. A set of n items has 2^n subsets.
  • Functions: injective (one-to-one), surjective (onto), bijective (both, so invertible).
  • Equivalence relation: reflexive, symmetric, transitive. It splits a set into classes, which is the idea behind equivalence partitioning in testing.
  • Counting: n! orderings. n!/(n - k)! ordered choices. C(n, k) = n!/(k!(n - k)!) unordered choices (C(5, 2) = 10). A complete graph on 10 vertices has C(10, 2) = 45 edges.
  • Pigeonhole: n + 1 items in n boxes means some box has two.
  • Induction: prove the base case, then "true for n implies true for n + 1".

10. Floating point pitfalls

  • IEEE 754 double: 1 sign bit, 11 exponent bits, 52 fraction bits (53 significant bits), about 15 to 17 decimal digits. Machine epsilon 2^(-52), about 2.2e-16.
  • 0.1 has no exact binary form, so 0.1 + 0.2 == 0.3 is False in Python (the sum is 0.30000000000000004).
  • Compare with a tolerance, for example math.isclose(a, b, rel_tol=1e-9). Your plan's "float tolerance" rule for comparing outputs exists for this reason.
  • Absorption and cancellation: (1e16 + 1) - 1e16 gives 0.0, because 1 is below the precision at 1e16. Subtracting nearly equal numbers loses relative accuracy.
  • Integers above 2^53 are not all representable: float(2**53 + 1) == float(2**53) is True.
  • NaN != NaN. There is a -0.0. Overflow gives inf. The order of a sum can change the result.

11. Software testing (the part closest to your plan)

  • Levels. Unit test: one function or class alone, often with fakes for its dependencies. Integration test: several parts together (database, API). System and acceptance tests: the whole product against the requirements. Regression tests: re-run old tests after a change.
  • Black-box design.
    • Equivalence partitioning: split inputs into classes the program should treat alike, and test one value per class.
    • Boundary value analysis: bugs cluster at the edges, so test on and next to each boundary. For a valid range 1 to 100: 0, 1, 2, 99, 100, 101.
  • White-box coverage. Statement coverage: every line runs. Branch coverage: every decision goes both ways. MC/DC: each condition independently changes the decision (used in avionics). 100% coverage does not mean no bugs: it says the code ran, not that its output was checked.
  • Mutation testing. Make small changes (mutants) to the code, such as > to >= (relational operator replacement, ROR), + to - (AOR). A test suite kills a mutant if some test fails on it. Mutation score = killed / (total - equivalent). Equivalent mutants behave like the original and cannot be killed. Example: 50 mutants, 5 equivalent, 36 killed gives 36/45 = 0.8. The mutant x > 0 to x >= 0 is killed only by a test with x = 0: boundary values kill ROR mutants, which is the link to the lab's boundary paper [2]. (In [2], a mutant counts as killed when some input takes a different execution path, read from Gcov branch data.)
  • Test oracle problem: knowing the right output for a generated input is hard. Options: a reference implementation, properties (for example "sorting keeps the length and gives non-decreasing order"), or metamorphic relations.
  • Differential testing: run two implementations on the same inputs and flag disagreements. Your plan uses the merged code as the reference. Its limit: a bug that both share is invisible.
  • Property-based testing: generate many inputs from types and check properties (Hypothesis in Python). Your input generator built from type hints is in this family.
  • Flaky tests pass or fail without a code change (timing, order, network). The usual fix is to re-run them and drop the ones that flip. Your plan does not mention flaky tests. It only requires that a task's own tests fail before the change and pass after it. If asked, say that re-running and dropping flaky tests is what you would do.

20 short Q&As (spoken answers)

1. What does O(n log n) mean?

"That the running time grows at most like n log n, up to a constant, for large n. Merge sort is an example."

Follow-ups (each builds on your last answer)

  1. Prof: "You said 'up to a constant, for large n'. Can you state the definition precisely?"
    You: "f of n is O of g of n if there is a constant c greater than zero and a starting point n0 such that f of n is at most c times g of n for every n from n0 on. The constant hides things like machine speed, and n0 lets me ignore small inputs."
  2. Prof: "If the constant is hidden, can an n squared algorithm beat an n log n one in practice?"
    You: "Yes, on small or nearly sorted inputs. Insertion sort is n squared in the worst case, but its constant is tiny and it is very fast when the data is almost in order, so real sorts like Python's Timsort use it on short pieces of a few dozen elements."
  3. Prof: "Why is insertion sort fast on nearly sorted data? Can you make that precise?"
    You: "Its running time is about n plus the number of inversions, which are pairs of elements in the wrong order, because each shift fixes exactly one inversion. A sorted array has no inversions, so it takes linear time, and a reversed array has n times (n minus 1) over 2, so it is quadratic. For 10 reversed items that is 45 shifts."

2. Quicksort or merge sort?

"Quicksort is usually faster in practice and sorts in place, but its worst case is n squared and it isn't stable. Merge sort is always n log n and stable, but needs extra memory."

Follow-ups (each builds on your last answer)

  1. Prof: "When exactly does quicksort hit n squared?"
    You: "When the pivot keeps splitting the array very unevenly, for example taking the first element as pivot on an already sorted array. Then each step removes only the pivot, so the comparisons add up to (n minus 1) plus (n minus 2) and so on, which is n times (n minus 1) over 2."
  2. Prof: "How do you protect against that?"
    You: "I pick the pivot at random, so no fixed input is bad every time, and the expected number of comparisons is about 2 n ln n, roughly 1.39 n log2 n for large n. Libraries also use median of three, or introsort, which switches to heapsort if the recursion gets too deep."
  3. Prof: "A random pivot gives a good expected time. Is that enough for a system with a hard deadline?"
    You: "No. A rare run can still be slow, and with a deadline a slow run is a failure, so what matters is the chance of a slow run, not the mean. There I'd use a sort with a worst-case n log n guarantee, like heapsort or introsort."

3. Why can't a comparison sort beat n log n?

"Each comparison has two outcomes, and the algorithm must tell apart n factorial orderings, so it needs at least log2 of n factorial comparisons, which is about n log n."

Follow-ups (each builds on your last answer)

  1. Prof: "Why is log2 of n factorial about n log n? Show me."
    You: "n factorial is at most n to the n, and at least (n over 2) to the (n over 2), because the top half of its factors are each at least n over 2. Taking log2, it sits between (n over 2) log2 (n over 2) and n log2 n, so it is Theta of n log n. Stirling's formula sharpens it to n log2 n minus about 1.44 n, plus a small log term. For 10 items, log2 of 10 factorial is 21.8, so at least 22 comparisons."
  2. Prof: "That's the worst case. Does the bound also hold on average?"
    You: "Yes. In a binary tree with n factorial leaves, the average depth of a leaf is also at least log2 of n factorial, so even averaged over all input orders a comparison sort needs about n log n comparisons. A random pivot doesn't escape it either."
  3. Prof: "Then how does counting sort run in linear time?"
    You: "It doesn't compare keys. It uses each key as an index into an array of counters, so it sorts n integers between 0 and k in n plus k time. The decision-tree argument doesn't cover it, because one array lookup can have k outcomes, not two."

4. How many comparisons does binary search need for a million items?

"At most about 20, because 2 to the 20 is just over a million. It's O(log n), but only on sorted data."

Follow-ups (each builds on your last answer)

  1. Prof: "You said only on sorted data. If you have to sort first, when is it worth it?"
    You: "Sorting costs n log n once, and then each search is log n instead of n. With k searches that is n log n plus k log n, against k times n for scanning, so sorting wins once k is above roughly log2 n, about 20 searches for a million items, ignoring constants."
  2. Prof: "If you search that often, why not use a hash table instead?"
    You: "For exact matches a hash table is better, about one step per lookup on average. A sorted array also answers questions a hash table can't, like the largest value below x or everything between a and b, and it has no bad worst case."
  3. Prof: "'The largest value below x' is easy to get wrong. What goes wrong, and how would you test it?"
    You: "Off-by-one errors in the bounds: writing lo less than hi where it should be less than or equal, which skips the last candidate, or setting hi to mid instead of mid minus 1, which can loop forever. I'd test the edges, like an empty array, a single element, and x below the first or above the last element, and then compare it with a plain linear scan on thousands of random arrays."

5. Why is a hash table O(1), and when isn't it?

"A good hash spreads keys evenly, so each bucket holds a few items on average. If many keys collide, a lookup degrades to O(n), so the table resizes to keep the load factor low."

Follow-ups (each builds on your last answer)

  1. Prof: "You said a few items per bucket on average. How many exactly, if the load factor is alpha?"
    You: "With chaining and a hash that spreads keys uniformly, a lookup for a missing key checks alpha items on average, and a successful one about 1 plus alpha over 2. So if resizing keeps alpha below a constant, say 0.75, the expected cost is constant."
  2. Prof: "That assumes the hash spreads keys uniformly. What if an attacker chooses the keys?"
    You: "Then they can pick keys that all land in one bucket, and every lookup becomes O(n). That's the hash flooding attack shown against web frameworks in 2011, and it's why Python mixes a random secret seed into its string hashes, using a keyed hash called SipHash."
  3. Prof: "Even with a perfectly random hash, how soon do collisions start?"
    You: "Much sooner than intuition says: with m buckets, the chance of a collision passes one half after about 1.18 times the square root of m keys. With 365 buckets that's 23 keys, probability 0.507, the birthday problem. So collisions are normal, and a table is built to handle them, not to avoid them."

6. BST or heap?

"A balanced BST keeps everything in order, so it supports search, min, max and range queries in log n. A heap only keeps the minimum on top, which is all a priority queue needs, and it's simpler and faster for that."

Follow-ups (each builds on your last answer)

  1. Prof: "Both give log n. Why is a heap simpler and faster for a priority queue?"
    You: "A binary heap is just an array: the children of position i are at 2i plus 1 and 2i plus 2, so there are no pointers and no rebalancing, and memory access is cache friendly. It also has find-min in O(1), and it can be built from n items in O(n)."
  2. Prof: "Why is building a heap O(n) and not n log n?"
    You: "I build it bottom up, sifting each node down, and most nodes are near the leaves, so they move only a short way. About n over 4 nodes move at most one level, n over 8 at most two, and so on, so the total is n times the sum of h over 2 to the (h plus 1), which is at most n."
  3. Prof: "Use that. How would you find the k smallest of n items?"
    You: "Build a heap in O(n) and pop the minimum k times, which is n plus k log n. If the items arrive as a stream, I keep a max-heap of the k best so far and replace its top when something smaller comes, which is n log k with only k items in memory. That's what Python's heapq.nsmallest does."

7. BFS or DFS?

"BFS finds shortest paths by number of edges, because it explores level by level. DFS goes deep first and is natural for cycle detection and topological sorting. Both are O(V + E)."

Follow-ups (each builds on your last answer)

  1. Prof: "How does DFS actually detect a cycle?"
    You: "In a directed graph I colour the vertices: white for unseen, grey while the vertex is on the current path, black when it is finished. If DFS meets a grey vertex, there is an edge back into the current path, and that is a cycle."
  2. Prof: "And how do you get a topological order from the same DFS?"
    You: "I list the vertices in reverse order of finishing time, because a vertex finishes only after everything it points to. If DFS finds a back edge to a grey vertex on the way, there is a cycle and no order exists. Kahn's algorithm is the other way: keep removing a vertex with no incoming edges."
  3. Prof: "What does such a cycle mean in a real code base?"
    You: "A circular dependency: module A imports B and B imports A, so there is no valid build or load order, and in Python it can show up as an ImportError from a partly loaded module. The usual fix is to move the shared part into a third module. My Mermaid-Git app reads the Python and TypeScript imports in each push and draws exactly this graph, so it's one I've worked with."

8. How does Dijkstra work, and when does it fail?

"It repeatedly takes the closest unfinished vertex and relaxes its edges, using a priority queue. It assumes non-negative weights; with a negative edge a finished vertex could still get shorter, so I'd use Bellman-Ford."

Follow-ups (each builds on your last answer)

  1. Prof: "Give me a small example where a negative edge breaks it."
    You: "Take directed edges A to B with weight 2, A to C with 3, and C to B with minus 2. Dijkstra finishes B at distance 2 first, but the path A, C, B costs 1, and B is never updated because it is already finished."
  2. Prof: "Why not just add 2 to every edge so they're all non-negative?"
    You: "Because that adds 2 per edge, so paths with more edges are penalised more. In my example A to B becomes 4 and A, C, B becomes 5, so it picks the direct edge, which is wrong for the original weights. The correct version of that idea is Johnson's algorithm, which adds h of u minus h of v to each edge, so every path between the same two vertices shifts by the same amount."
  3. Prof: "Where does Johnson's algorithm get h from?"
    You: "I add an extra vertex joined to every vertex by a zero-weight edge and run Bellman-Ford once from it, so h of v is the shortest distance to v. Bellman-Ford relaxes every edge V minus 1 times, which is O(V times E), and if one more round still lowers a distance, there is a negative cycle and no shortest path. On my example h is 0 for A and C and minus 2 for B, the new weights are 4, 3 and 0, and Dijkstra then gives B the right distance, 1."

9. What is dynamic programming?

"Solving a problem by combining answers to overlapping subproblems and storing each answer once. Fibonacci goes from exponential to linear time that way."

Follow-ups (each builds on your last answer)

  1. Prof: "How exponential is the naive Fibonacci, exactly?"
    You: "The number of calls satisfies C(n) = C(n minus 1) plus C(n minus 2) plus 1, so it grows like Fibonacci itself, about 1.618 to the n, the golden ratio. For n = 30 that's 2,692,537 calls, against 31 stored values with memoisation."
  2. Prof: "Memoisation or a bottom-up table: which would you use?"
    You: "Bottom up when I need every subproblem anyway, like the n by W table for zero-one knapsack, because there is no recursion, and Python stops at 1,000 nested calls by default. For Fibonacci I only need the last two values, so memory drops to O(1). Top down is easier when only a few subproblems are actually reached."
  3. Prof: "You said an n by W table. Isn't O(nW) polynomial? Then you'd have solved an NP-complete problem."
    You: "No, because W is a number written with only about log2 W bits, so n times W is exponential in the length of the input. Adding one decimal digit to W makes the table ten times bigger. That's why it's called pseudo-polynomial, and knapsack stays NP-complete."

10. Explain P versus NP.

"P is the set of problems we can solve in polynomial time, NP the set whose answers we can check in polynomial time. Every P problem is in NP; whether they are equal is the biggest open question in computer science."

Follow-ups (each builds on your last answer)

  1. Prof: "What does 'check in polynomial time' mean precisely? Give an example."
    You: "For every yes-instance there is a short certificate that a polynomial-time checker accepts, and for a no-instance nothing is accepted. For SAT the certificate is a true or false value for each variable, and I check it by evaluating each clause, which is linear in the size of the formula."
  2. Prof: "Why does SAT matter so much among NP problems?"
    You: "Cook and Levin showed that every problem in NP reduces to SAT in polynomial time, so SAT is NP-complete: a fast algorithm for SAT would give a fast algorithm for all of NP. Yet in practice SAT solvers handle very large industrial formulas, for example in hardware and software verification."
  3. Prof: "If SAT is NP-complete, why do solvers work in practice, and where do they meet testing?"
    You: "NP-completeness is about the worst case, and real formulas have structure that modern solvers exploit, for example by learning a new clause from each conflict. In testing, symbolic execution tools like KLEE turn the branch conditions on a path into a formula and ask a solver for an input that takes that path. Guo, Okamura and Dohi compared their boundary method with KLEE, and KLEE produced only one test case for miniSAT."

11. Is the halting problem NP-complete?

"No, it's undecidable: no algorithm solves it at all, however slow. NP-complete problems can be solved, just not known to be solvable fast."

Follow-ups (each builds on your last answer)

  1. Prof: "Can you sketch why it's undecidable?"
    You: "Suppose a program H could decide, for any program and input, whether that program halts. Build D, which takes a program P, asks H whether P halts when given its own code, and then does the opposite: loops if yes, stops if no. Running D on itself, D halts exactly when it doesn't, which is a contradiction, so H can't exist."
  2. Prof: "Does that mean we can't verify programs at all?"
    You: "No. It rules out one tool that decides it for every program. For particular programs we can still prove termination, and tools can answer yes, no or don't know. Rice's theorem extends it: any non-trivial question about what a program computes is undecidable in general."
  3. Prof: "How does that affect the way your plan judges the agents' code?"
    You: "No tool can decide in general whether a version computes the same function as the merged code, so I sample instead: at least 10,000 generated inputs per entry point, which estimates a failure probability for a stated input distribution but proves nothing. For the same reason, equivalent mutants can't be found automatically in every case."

12. Why is 0.1 + 0.2 not equal to 0.3 in Python?

"Because 0.1 and 0.2 have no exact binary representation, so the sum is 0.30000000000000004. I compare floats with a tolerance, like math.isclose."

Follow-ups (each builds on your last answer)

  1. Prof: "Why does 0.1 have no exact binary form, when it's exact in decimal?"
    You: "A fraction has a finite binary expansion only if its denominator, in lowest terms, is a power of 2. 0.1 is 1 over 10, and 10 has a factor 5, so in binary it repeats forever, 0.000110011 and so on, and it gets rounded to 53 significant bits."
  2. Prof: "How big is that rounding error?"
    You: "At most half a unit in the last place, so a relative error of at most 2 to the minus 53, about 1.1 times 10 to the minus 16. The stored 0.1 is just above 0.1, by about 5.6 times 10 to the minus 18."
  3. Prof: "If each step loses only about 10 to the minus 16, when does it matter?"
    You: "When errors add up, or a big number swallows a small one. Adding 0.1 ten times in a plain loop gives 0.9999999999999999, and (1e16 plus 1) minus 1e16 gives 0, because floats near 1e16 are 2 apart. So two correct programs that add in a different order can disagree in the last digits, which is why my comparison needs a tolerance."

13. How do you compare float outputs in your differential tests?

"With a float tolerance that is fixed in advance, like the realcompare function in Ron et al. It is part of one fixed rule: the same exception class also counts as the same output, and order is ignored for unordered collections. Otherwise harmless rounding differences would count as failures."

Follow-ups (each builds on your last answer)

  1. Prof: "Absolute or relative tolerance, and what value?"
    You: "Relative, like realcompare, because an absolute 1e-9 is too strict for large numbers, where neighbouring floats are already further apart than that, and too loose for tiny ones. But a purely relative test breaks near zero, so I'd combine both, as math.isclose does with rel_tol and abs_tol. I haven't fixed the values yet, and I'd write them down before the main runs."
  2. Prof: "Doesn't a tolerance also hide real bugs?"
    You: "It can, if a wrong formula is off by less than the tolerance, so I'd count how many inputs agree only within the tolerance and not exactly. It can also go the other way: Ron et al. found two angle formulas that are equal in exact arithmetic but gave different decisions under realcompare near a threshold. So in my 20 hand checks per task I'd also note which disagreements sit right at a threshold."
  3. Prof: "How would you choose the tolerance in a principled way, rather than by guessing?"
    You: "I'd measure the noise first: run the merged code itself under harmless changes, like a different summation order or library version, and see how far its outputs move. The tolerance should sit above that spread and well below the size of a real error for the task, and as a sensitivity check I'd report the results again with it ten times tighter and ten times looser."

14. Unit test or integration test?

"A unit test checks one function alone and is fast and precise. An integration test checks that parts work together, so it catches interface bugs that unit tests miss."

Follow-ups (each builds on your last answer)

  1. Prof: "Give me a real example of an interface bug that unit tests would miss."
    You: "The Mars Climate Orbiter, lost in 1999: one team's ground software gave thruster impulse in pound-force seconds, and the navigation software expected newton-seconds. Each part could pass its own unit tests, because each was right by its own convention; only the two together were wrong."
  2. Prof: "Unit tests usually replace the other side with a fake. Doesn't a fake have the same problem?"
    You: "Yes. A fake encodes my assumption about the other side, so if that assumption is wrong, the unit test confirms the bug. Fakes still keep unit tests fast and focused; the fix is a few integration tests with the real parts, or a contract test that checks the real service and the fake against the same expectations."
  3. Prof: "How do you handle that in your own agent, Yuki?"
    You: "In Yuki 2.0 I replay real requests on a copy of the memory database with simulated desktop apps, which is closer to an integration test than a unit test. Its weakness is exactly the fake problem: the simulated apps encode my assumptions about how Windows behaves, so the replays can't find a bug in those assumptions."

15. Does 100% branch coverage mean the code is correct?

"No. It means every branch ran, not that the outputs were checked, and it says nothing about inputs that take a covered branch with a wrong value. That's why I also use mutation testing and generated inputs."

Follow-ups (each builds on your last answer)

  1. Prof: "Give me a concrete example: full branch coverage, and still a bug."
    You: "Say the requirement is 18 or older, and the code says age greater than 18. Tests with age 10 and age 30 take both branches and pass, so branch coverage is 100%, but age 18 gives the wrong answer."
  2. Prof: "Would a stronger criterion like MC/DC catch it?"
    You: "Not this one. MC/DC asks that each condition on its own flips the decision, but there's only one condition here, so the same two tests already satisfy it. What catches it is the boundary value 18: in mutation terms, greater-than and greater-or-equal differ only at 18, so only that input tells them apart."
  3. Prof: "Our lab's boundary paper counted a mutant as killed by a different execution path. Is that the same as a failing test?"
    You: "Not quite. In Guo, Okamura and Dohi a mutant is killed if some input takes a different execution path, read from Gcov branch data, even if the output stays the same, while a mutant that only changes a computed value can change the output without changing the path. Here age 18 changes both, but in general the two rules can disagree, so I'd report both."

16. What is mutation testing?

"I make small changes to the code, like turning greater-than into greater-or-equal, and see whether the tests catch them. The mutation score is killed mutants over non-equivalent mutants, and it measures how strong the tests are."

Follow-ups (each builds on your last answer)

  1. Prof: "You said non-equivalent mutants. How do you know a mutant is equivalent?"
    You: "An equivalent mutant gives the same output as the original on every input. For example, in a loop that finds a maximum, changing 'if x is greater than m' to 'greater or equal' only reassigns an equal value, so nothing changes. Deciding this is undecidable in general, so people check the survivors by hand or use tricks like compiling both versions and comparing the machine code."
  2. Prof: "If you can't always decide equivalence, what does that do to the number you report?"
    You: "The denominator becomes uncertain, so I can only bound the ratio. With 50 mutants and 36 killed, killed over all is 0.72, a lower bound; if I show 5 survivors are equivalent it becomes 36 over 45, 0.8, and it reaches 1 only if all 14 survivors are. Guo, Okamura and Dohi report killed over all mutants, which is the lower bound."
  3. Prof: "Say the ratio comes out at 0.8. Why should killing small planted changes tell you anything about real bugs?"
    You: "It rests on two ideas: real code is usually close to correct, and tests that catch simple faults also catch most complex ones, the coupling effect. Just and colleagues checked this in 2014 on 357 real faults in five Java programs: about 73% were coupled to common mutants, and mutant detection correlated with real fault detection independently of coverage. Whether agent-written bugs look like those small changes is an open question I'd want to check."

17. Boundary values for a function that accepts ages 18 to 65?

"Three classes: below 18, 18 to 65, above 65. Boundary values 17, 18, 19 and 64, 65, 66, plus maybe a non-integer or a negative value."

Follow-ups (each builds on your last answer)

  1. Prof: "You mentioned a non-integer. If age is a float, what is 'just below 18'?"
    You: "Then there's no natural neighbour: the next float below 18 is 18 minus about 3.6 times 10 to the minus 15, and whether 65.5 is still valid depends on the spec, for example whether ages mean completed years. So I'd first fix the type and the smallest step, and the boundaries follow from that choice."
  2. Prof: "That's close to how our lab's boundary paper defines a boundary. How do they define it?"
    You: "Guo, Okamura and Dohi fix a set of minimal operations, like adding or subtracting one, and a boundary point is an input where one operation moves you into a partition with a different output. For integer ages with plus or minus one, that gives exactly 17, 18, 65 and 66, so the 19 and 64 I added are extra inside points, not boundaries by their definition."
  3. Prof: "Here you had a specification. In your plan you only have the merged code. How do you find the boundaries?"
    You: "I take them from branch conditions in the merged code that compare a parameter with a constant: if it says age less than 18, then 17 and 18 are candidates. The weakness, as their Remark 2 says, is that partitions from execution paths can differ from partitions from outputs, so a branch is not always a real output boundary. I state that as a limit, and the pilot will count how many functions have usable conditions like that."

18. What is the test oracle problem, and how does your plan handle it?

"For a generated input, I need to know the right output. I use the merged code from the pull request as the reference, and I check 20 disagreements per task by hand to drop inputs where the merged code itself is wrong."

Follow-ups (each builds on your last answer)

  1. Prof: "Why 20? Is that enough to know how often the merged code is wrong?"
    You: "Twenty is a design choice I can change, not the result of a power calculation. [YOU: Why 20 hand-checked disagreements per task? Is it just a fixed amount of hand work you can afford, or do you have another reason?] If none of the 20 shows the merged code wrong, the 95% upper bound on that share is still about 14%, and the quick rule of three, 3 over 20, gives 15%. So 20 catches a common problem, like illegal inputs from my generator, but not a rare one."
  2. Prof: "How would your generator produce illegal inputs?"
    You: "It builds inputs from the type hints and the pull request's test values, and a hint like float doesn't say 'a price is never negative'. If the function checks and raises an error, that's fine, because the same exception class counts as agreement; the problem is inputs it silently accepts. I'd find those in the hand check and write them down as input constraints, like deciding whether negative prices are legal refunds in that repository."
  3. Prof: "Adding constraints changes the input distribution. Doesn't that change the failure probability you report?"
    You: "Yes. A failure probability only means something for a given input distribution, which in reliability is the operational profile, how inputs are spread in real use. So I'd fix the distribution and the constraints before the main runs, report how many inputs each constraint removed, and say clearly that my distribution only stands in for the real profile."

19. What is the main limit of differential testing?

"It can't see a bug that both implementations share. In my plan that's exactly the shared-helper case, so I state it as a limit."

Follow-ups (each builds on your last answer)

  1. Prof: "Explain the shared-helper case with an example."
    You: "Say the context file tells the agent to round money with a helper, round_cents, and that helper turns negative prices, which are refunds, into zero. If the merged code also used round_cents, the reference and every run that calls the helper would return 0.0 for a refund, so my comparison would see agreement, not a failure."
  2. Prof: "Then how could you see such a shared bug at all?"
    You: "Not with the merged code as the only reference. I'd need a check that doesn't go through the same helper, like a property or a metamorphic relation, or a second reference written without it. The field data could also show it later, as bug-fix commits that touch the helper after merge."
  3. Prof: "Give me a metamorphic relation that would catch it, and its weakness."
    You: "A refund should mirror a sale: a discount applied to minus p should give minus the result for p. With the helper, minus 3 dollars at 10 percent gives 0.0, but the mirror gives minus 2.70, so the relation fails without my knowing the right answer for either input. The weakness is that I must know the relation really holds in that repository, and code that is wrong in a consistent, symmetric way still passes."

20. How many numbers from 1 to 100 are divisible by 2 or 3?

"By inclusion-exclusion: 50 divisible by 2, plus 33 by 3, minus 16 by 6, so 67."

Follow-ups (each builds on your last answer)

  1. Prof: "Now divisible by 2, 3 or 5?"
    You: "Inclusion-exclusion with three sets: 50 plus 33 plus 20 is 103. Subtract the pairs, 16 for 6, 10 for 10 and 6 for 15, which gives 71, then add back 3 for 30. That's 74."
  2. Prof: "Where does inclusion-exclusion show up in reliability?"
    You: "In system reliability. A minimal path set is a smallest group of components whose working keeps the system up, so reliability is the probability that at least one path set fully works, and for that union I add the single terms, subtract the pairs, add the triples, and so on. With m path sets that can be 2 to the m minus 1 terms, so tools use binary decision diagrams instead, and your lab's 2025 note extends that to multi-valued decision diagrams for systems with more than two states."
  3. Prof: "Do it for a 2-out-of-3 system with independent components of reliability r."
    You: "The minimal path sets are components 1 and 2, 1 and 3, and 2 and 3, each working with probability r squared. Every intersection of two or three of them means all three work, r cubed, so R is 3r squared minus 3r cubed plus r cubed, which is 3r squared minus 2r cubed, and for r = 0.9 that's 0.972. It's the same formula as the 2-out-of-3 vote in my plan, 3 theta squared minus 2 theta cubed, with failure in place of success."
