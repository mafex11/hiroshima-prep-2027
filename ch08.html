0. The whole proposal in 30 seconds

Say this out loud until it feels natural:

"When you run a coding agent several times on the same task, you can treat the runs like the versions in N-version programming and vote. But voting only helps if the runs fail on different inputs. Every run in a repository reads the same AGENTS.md or CLAUDE.md file, so that file is part of the specification they all share. If one rule pushes every run to the same buggy helper, every run gets the same bug, and the vote cannot fix it. RQ1 measures how much more often runs fail together than independence predicts, and which change between runs lowers that most. RQ2 asks whether removing one real rule changes reliability beyond the task's own tests. For RQ1 I fit a beta-binomial model, so a team can choose how many runs to vote over at a given cost."

If he wants one sentence:

"I treat repeated coding-agent runs on one real task as N versions, and I measure how much a shared context file makes them fail on the same inputs, and what that means for voting."

1. The title

"Does a shared AGENTS.md make coding-agent runs fail together? Coincident failures, voting and the reliability of agent-written changes"

  • Plain words: if every run reads the same rules file, do the runs break on the same inputs? And if they do, how much does voting still help?
  • Why it is phrased like this: the first half is the question. The second half names the three things a reliability lab cares about: coincident failures, voting and reliability.
  • "Coincident failure" means two or more versions fail on the same input. It is the standard term in N-version programming (Eckhardt and Lee call it "coincident errors").

2. Section 1: Background

Paragraph 1: N-version programming and the lab's paper

"In N-version programming, a vote over several versions of a program helps only if the versions rarely fail on the same inputs."

  • Plain words: you write the same program N times, independently, run all of them on each input, and take the majority answer. If two of three are wrong on the same input in the same way, the vote picks the wrong answer.
  • Why it is there: it is the base idea of the whole proposal. Your study treats agent runs as versions.

"Eckhardt and Lee showed that two versions drawn at random from one development process fail independently only if every input is equally likely to make a version fail [11]."

  • Plain words: imagine many teams write the program. For each input x, let θ(x) be the share of versions that fail on x. If θ is the same for every input, failures are independent. If some inputs are harder than others (θ bigger there), two versions are more likely to fail together than independence predicts.
  • Why it is there: it is the theory your RQ1 model is built on. Your beta-binomial model puts a distribution on θ.
  • What you read: the NASA report version (NASA TM-86369, Jan 1985), which is the report form of the same work. It names θ(x) "the intensity of coincident errors" and Q the "usage distribution". Theorem 2 says independence holds if and only if the intensity is constant.
  • If asked "Have you read Eckhardt and Lee?": "I read the NASA technical report version in full. I have not seen the TSE version itself, but it is the same work."

"Zheng, Okamura and Dohi asked whether generative AI can enhance the effectiveness of N-version programming [1]. They compared high-performing models (e.g., GPT-4o) with lower-performing ones, and varied the temperature and whether the conversation history was reused. Majority voting made the strong models more reliable but helped little with the weak ones. More diversity did not always mean higher reliability."

  • Plain words: the lab's own paper. Strong models plus voting got more reliable. Weak models did not gain much. More variety between versions did not always help.
  • Why it is there: your RQ1 takes their question to real repository tasks with coding agents. They varied temperature and history reuse. You vary file version, agent, model and temperature.
  • Honest limit: all four sentences come from the abstract. Prof. Zheng is the first author. If he asks what you think of the paper, say what the abstract says and ask for a copy (see 05_question_bank_with_model_answers.md, B4).

Paragraph 2: two 2026 studies on LLM versions

"Two 2026 studies found that LLM-written versions fail together more often than independence predicts."

"Ron et al. had five agent harnesses implement the specification from the 1986 Knight and Leveson experiment. Two or more of the 48 accepted programs failed together on 429 of one million inputs, against about 115 expected under independence, and many of these failures traced back to parts of the specification that are hard or ambiguous. Voting over three programs still cut the mean failure count from 387 to 131 [5]."

  • Plain words: a KTH team repeated the famous 1986 experiment, but with coding agents instead of students. Agents wrote 69 programs; 48 passed a 200-case acceptance test. On one million random inputs, joint failures happened on 429 inputs, where independence predicts 115.36 (z = 29.20). But voting over any three programs still lowered the average failure count from 387.44 to 130.99.
  • The five harnesses: Cursor, Claude Code, Codex, Gemini and OpenCode, with 23 models and three languages (Python, Rust, Pascal).
  • Why it is there: it shows agent versions are not independent, and that voting still helps a lot. Both halves matter for you.
  • "Hard or ambiguous": many failures sat in two conditions (LICs 9 and 14) where agents computed the circumcircle instead of the smallest enclosing circle, and LICs 3 and 10 exposed an ambiguity. So the shared specification caused shared failures. That is the same idea as your shared context file.

"On 224 contest problems with twelve models, voting over three versions captured 0.43 of the gain that independent failures would allow, and 0.27 when all three came from one model [6]."

  • Plain words: Nogueira et al. (Coimbra, UNC Charlotte, UBC). "Redundancy effectiveness" is the share of the gain you would get if failures were independent that voting really gives. Mixed models: 43%. All from one model: only 27%.
  • Why it is there: same-model versions share more failures. That is why your design changes agent and model between runs.

Paragraph 3: context files and what we know about them

"Developers steer coding agents such as Claude Code and Codex with a context file, AGENTS.md or CLAUDE.md, that lists rules such as how to run the tests and where new code goes."

  • Plain words: a Markdown file in the repository that the agent reads at the start. Claude Code reads CLAUDE.md, Codex reads AGENTS.md.

"On real Python tasks, files written by the developers raised task success by 2.4% on average (not significant, p = 0.21) and raised cost by up to 19%, although agents did use the tools a file named (uv 1.6 times per task when named, under 0.01 times when not) [8]."

  • Plain words: Gloaguen et al. (ETH Zurich) built 138 tasks from 12 Python repositories that have developer-written context files. Developer files gave a small, not significant gain, and cost more. But agents clearly did what the file said, for example using the uv tool.
  • Why it is there: files change behaviour, but nobody has checked whether that changes reliability. Also, this benchmark is your starting material.
  • Detail you may need: they set temperature 0 for Sonnet-4.5 in Claude Code and for GPT-5.2 and GPT-5.1 mini in Codex, and 0.7 (top-p 0.8) for Qwen3-30B-Coder in Qwen Code. They sampled each agent once per task.

"In a leave-one-out test of 18 generic rules, the only rules whose removal lowered the pass rate by more than 5 points were prohibitions, such as 'do not refactor unrelated code' [9]."

  • Plain words: Zhang et al. ("Guardrails Beat Guidance") removed each of 18 rules one at a time, with Claude Code and Claude Opus 4.6 on SWE-bench Verified. The three rules that mattered by more than 5 points were all "do not" rules. Only one was significant on its own (McNemar p = 0.016), and the authors call the pattern suggestive.
  • Why it is there: single rules can matter. And your task screening copies theirs.

"Neither study tests the code beyond the task's own tests."

  • Plain words: both measured "did the tests pass". Neither asked whether the code fails on inputs the tests do not cover. That is your gap for RQ2.

"Merged agent code also needs more fixes: in 182 repositories, bug-fixing commits changed 4.0% of agent-written lines within 180 days of merge, against 2.7% of human-written ones [10]."

  • Plain words: Xia and Miller tracked lines after merge. Agent lines got touched by bug fixes more often than human lines.
  • Why it is there: passing tests at merge time is not the end of the story. It also motivates the field study.

3. Section 2: Purpose and research questions

The argument

"Every run in a repository reads the same context file, so the file is part of the specification that all runs share."

  • Plain words: in Knight and Leveson, the shared specification caused shared failures. For agents, the task text plus the context file is the specification. So the file can be a source of shared failures.

"A rule can push every run toward the same design: if it tells the agent to use one helper and that helper mishandles an edge case, every run inherits the bug."

  • Plain words: this is the mechanism. Diversity between runs disappears where the rule forces one choice. Section 9 shows it with an example.

"Ron et al. [5] and Nogueira et al. [6] used no context file. As far as I know, no study has measured how often repeated agent runs on real tasks with a developer's own context file fail together, or whether removing one real rule changes reliability beyond the tests."

  • Plain words: the gap. Three parts together: real repository tasks, a developer's own context file, and failures measured beyond the tests.
  • Why "as far as I know": the field moves every week. Never say "first" or "no one has done this".

The research questions

"RQ1. When several agent runs solve one real task with the same context file, how much more often do they fail on the same inputs than independence predicts, and which change between runs (file version, agent, model, temperature) lowers it most?"

  • Plain words: two parts. (a) How strongly do runs fail together? (b) If you want more diverse runs, what should you change: the file, the agent, the model or the temperature?
  • How it is measured: the intraclass correlation ρ of a beta-binomial model (section 4.6), and the covariance between settings.

"RQ2. Does replacing one real rule with neutral text change the reliability of the code, measured as the failure probability on the pull request's tests and on generated inputs beyond them?"

  • Plain words: take one real rule out, put neutral text of about the same length in its place, and compare two numbers: the pass rate on the PR's tests, and the failure probability on 10,000+ generated inputs.
  • Why "neutral text" and not "delete": deleting changes the file length too. Neutral text keeps the length, so the difference is the rule's content. (Zhang et al. found that even random rules raised the pass rate, so length or "having some rules" can matter by itself.)

"A checker confirms that each manipulation changed what the agent did. I report compliance but do not test it as an RQ."

  • Plain words: a small script checks, for example, whether the code calls the helper the rule names. If removing the rule does not change what the agent does, the RQ2 comparison means little. So the checker is a manipulation check, not a research question.
  • Why not an RQ: compliance is empirical software engineering. This lab cares about reliability. Compliance is only there to show the experiment worked.

4. Section 3: Plan

4.1 Tasks and rules

"The 138 tasks of [8], from 12 Python repositories with developer-written context files, are public with Docker images and test commands."

  • Plain words: you do not build a benchmark from zero. Gloaguen's benchmark is on Hugging Face as eth-sri/agentbench (CTXBench in the paper, AGENTbench in the code), with Docker images and test commands, PRs merged from Aug 2022 to Jan 2026.

"I start from them and add newer merged pull requests from the same repositories, where possible merged after the models' training cutoff."

  • Why newer PRs: contamination. If a model saw the merged code in training, it may copy it from memory.

"A task's own tests fail before the change and pass after it."

  • Plain words: the SWE-bench idea. The PR's tests prove the task: they fail on the old code and pass on the merged code.

"The agent starts from the code just before the merge, with the context file of that time, no git history, and a task text that does not mention the rule."

  • Why no git history: so the agent cannot look up the real answer. Gloaguen also removed the history and remotes.
  • Why the task text does not mention the rule: otherwise you measure the prompt, not the file.

"I pick about 5 rules that a script can check and that change what code is written (such as which helper to use) rather than where files go, each with 2 tasks."

  • Plain words: 5 rules x 2 tasks = 10 tasks. Only rules that change the code itself can change reliability. A rule like "put tests in tests/" changes where code goes, not how it behaves.

"A checker is kept only if it agrees with my hand labels on at least 90% of 20 or more examples, and I report Cohen's kappa."

  • Plain words: before trusting a checker, you label at least 20 cases by hand. The checker must agree on 90% or more. Kappa corrects that agreement for chance.

"As in [9], I screen about 20 candidate tasks with 3 runs per agent and drop tasks an agent never solves (27% in [9]). Unlike [9], I keep tasks it always solves, since I measure failures beyond the tests."

  • Plain words: a task no run can solve gives no admitted versions, so it is useless. Zhang et al. also dropped always-solved tasks, because they measured only pass rate. You keep them: a run that always passes the PR's tests can still fail on generated inputs, and these tasks give the most versions.

4.2 Settings and runs

"Claude Code reads the file as CLAUDE.md and Codex as AGENTS.md, both pinned to fixed versions in a clean container; Codex also runs a second, smaller model to separate model from agent."

  • Plain words: same text, two file names. Fixed CLI and model versions, a fresh container each run. The second Codex model (in the cost list: GPT-5.1 mini) lets you compare two models inside one agent.

"The third agent is a small harness I will write in plain Python, as I built my desktop agent Yuki 2.0. It shows me the exact prompt the model receives and lets me set the temperature, which, as far as I know, neither CLI documents. It runs an open-weight model, Qwen3-30B-Coder as in [8], at two temperatures."

  • Plain words: with your own harness you see every prompt and you control temperature. The model is open-weight, so you can run it yourself or cheaply.
  • Be careful: Gloaguen et al. say they set temperature 0 inside both CLIs. So never say "the CLIs cannot set temperature". Say only that neither CLI documents it, as far as you know.
  • Model detail: the Hugging Face name is Qwen3-Coder-30B-A3B-Instruct, a mixture-of-experts model with 30.5B parameters in total and about 3.3B active per token.

"That makes 820 runs: 400 main runs (10 tasks, 2 file versions, 2 agents, 10 runs), 100 for the second Codex model and 200 for the harness (both on the original file only), and 120 for screening."

The arithmetic, which you must be able to do on paper:

Main:            10 tasks x 2 file versions x 2 agents x 10 runs = 400
Codex model 2:   10 tasks x 1 file version  x 10 runs            = 100
Harness:         10 tasks x 1 file version  x 2 temperatures x 10 runs = 200

"At the per-task costs in [8] (Claude Code with Sonnet 4.5 1.15 to 1.51 US dollars; Codex 0.32 to 0.57 with GPT-5.2, 0.18 to 0.22 with GPT-5.1 mini; Qwen3-30B 0.12 to 0.15), that is about 420 to 590 US dollars."

Claude Code: 200 main + 60 screening = 260 runs x 1.15 to 1.51 = 299 to 393

"Newer models may cost more: [9] reports about 5 US dollars per task and condition with Claude Opus 4.6. I would ask whether this fits a lab budget, and otherwise move more runs to the open-weight model."

  • Plain words: the estimate uses early-2026 prices from Gloaguen's tasks. Your tasks and today's models may cost more. You do not assume the lab pays. If not, the open-weight model takes more of the runs.
  • Never say: "I will pay for the pilot myself" unless it is true. That sentence was removed on 28 Oct.

4.3 Failures beyond the tests (RQ2)

"A run's change is admitted as a version only if it passes the pull request's tests, as in Knight and Leveson's acceptance test and [5]."

  • Plain words: a run that fails the PR's own tests is not a working program, so it is not a "version". In 1986 the student programs also had to pass a 200-case acceptance test. Ron et al. did the same.

"Inputs go to the entry points those tests call, so every admitted version implements them."

  • Plain words: you test the functions the PR's tests call, because every admitted version must have them. A helper the agent invented may not exist in another run.

"The merged code is the reference [5], and two outputs count as the same under a fixed rule: a float tolerance (like realcompare in [5]), the same exception class, and order ignored for unordered collections."

  • Plain words: the human merged code is the oracle. A version fails on an input if its output differs from the merged code's output under one fixed rule, decided before you look at results:
    • floats: equal within a tolerance (the Knight and Leveson specification has a realcompare function for this);
    • errors: both raise the same exception class (the message can differ);
    • sets and dicts: order does not matter.

"Failure probability is the share of failing inputs under a declared distribution: random inputs built from the type hints and the values in the pull request's tests, at least 10,000 per entry point."

  • Plain words: the failure probability depends on which inputs you draw. You say in advance how you draw them: types come from the type hints, and values mix random draws with the values the PR's tests use. Then failure probability = failing inputs / all inputs.
  • Why 10,000: a failure probability of 1 in 1,000 gives about 10 failing inputs, enough to see. Ron et al. used one million on a much simpler program.

"I check 20 disagreements per task by hand and drop inputs where the merged code itself is wrong."

  • Plain words: sometimes the human code is the wrong one, or the input is not a legal input. You read 20 disagreements per task and drop those inputs.

"RQ2 compares this probability and the test pass rate between the two file versions, with task as a random effect."

  • Plain words: some tasks are harder than others. A mixed model gives each task its own baseline and estimates one effect of the file version across tasks. In R style: failed_inputs out of inputs ~ file_version + (1 | task).

4.4 Boundary inputs (the lab's BCD method)

"I also use the boundary coverage distance (BCD) method of Guo, Okamura and Dohi [2], but only as a stress test: with 30 to 50 inputs per program it cannot estimate a failure probability."

  • Plain words: BCD measures how far a test set is from covering every boundary value, and an MCMC-like search moves test inputs toward the boundaries. It finds off-by-one bugs well. But 30 to 50 hand-picked inputs are not a random sample, so they cannot give a probability.
  • What [2] found: on five C programs, the best method (A1 with mean BCD) killed 0.8 to 1.0 of the mutants, against 0.36 to 0.66 for random testing.

"In [2] the boundary points were found by hand; I take them from branch conditions in the merged code that compare a parameter with a constant."

  • Plain words: [2] says its boundary points came from "manual analysis of the source code". You automate a simple version: if the merged code has if percent > 100:, then 100 is a boundary for percent.

"These are path-based boundaries, which [2] notes (Remark 2) differ from output-based ones; the pilot will report how many functions have them."

  • Plain words: in [2], partitions are defined by output categories. A branch in the code is not always an output boundary. You say so, and you count how many functions have usable branch conditions.

"I report the kill rate as in [2] (a mutant is killed when its execution path differs; here from coverage.py branch data) and by outputs."

  • Plain words: a mutant is a copy of the merged code with one small planted bug (like < changed to <=). [2] counts it as killed if some input takes a different path (they used Gcov). You use coverage.py branch data for the same rule, and also report the stricter "different output" rule.

"For strings and lists, which [2] leaves open, I will try one-element edits as minimal operations."

  • Plain words: for numbers, the smallest step is plus or minus one. For a string or list, the smallest step could be adding, removing or changing one element. [2] lists non-numeric inputs as future work.

4.5 (The figure is in section 8.)

4.6 Shared failures (RQ1): the maths, slowly

"For setting s, let θs(x) be the chance that a run fails on input x."

  • Plain words: a "setting" is one combination, for example Claude Code with the original file. θ is a number between 0 and 1 for each input. On an easy input θ is 0. On a hard one maybe 0.7.

"Two runs both fail with probability E[θs(X)²] = ps² + Var θs(X), where ps is the mean failure probability, so independence needs Var θs = 0 [11]."

  • Plain words: pick an input X at random. Given θ, two runs both fail with θ x θ. Average over inputs: E[θ²]. And E[θ²] = (E[θ])² + Var θ, which is just the definition of variance. So joint failures exceed p² by exactly the variance. They equal p² only if every input is equally hard.
  • Tiny example to say out loud: half the inputs are easy (θ = 0), half are hard (θ = 0.4). Then p = 0.2. Independence says both fail with 0.04. But really, half the time both fail with 0.16 and half the time never, so 0.08. The extra 0.04 is Var θ.

"I model θs(X) with a Beta distribution, so the number of failing runs among k on one input is beta-binomial, and its intraclass correlation ρs measures dependence (ρs = 0 means independence)."

  • Plain words: the Beta distribution is a flexible shape for numbers between 0 and 1. If θ follows Beta(a, b), then on one input the count of failing runs out of k is beta-binomial.
  • Formulas to know: mean p = a/(a + b). ρ = 1/(a + b + 1). Var θ = p(1 - p)ρ. So P(two runs both fail) = p² + ρ p(1 - p). The variance of the count is k p(1 - p)[1 + (k - 1)ρ], larger than the binomial k p(1 - p). That extra spread is called overdispersion.
  • Why it is a good measure: ρ is 0 for independence and 1 when all runs always fail together. It is a size, not just a test.

"A 2-out-of-3 vote then fails with probability E[3θ² - 2θ³]."

  • Plain words: on an input with failure chance θ, the vote fails if at least 2 of 3 fail: 3θ²(1 - θ) + θ³ = 3θ² - 2θ³. Average over inputs. Under independence it would be 3p² - 2p³.
  • Assumption to admit: this counts a vote as failed whenever two runs fail. That is right when the wrong outputs agree, and on the safe side when they differ.

"I fit the model per task and setting by maximum likelihood. Because the same runs meet every input, I take intervals from a bootstrap that resamples runs."

  • Plain words: maximum likelihood picks a and b that make the observed failure counts most likely. The inputs are not independent samples of runs: the same 10 runs are tested on all 10,000 inputs. So you resample runs (not inputs) with replacement, refit, and take the middle 95% of the results.

"For runs from two settings a and b, the chance that both fail is pa pb + Cov(θa, θb), so I can ask which change between runs lowers the covariance most."

  • Plain words: mix a Claude Code run and a Codex run. They fail together with p_a p_b plus a covariance. If changing the agent lowers the covariance more than changing the temperature, changing the agent is the better way to buy diversity.
  • Background: this is the Littlewood and Miller idea of forced diversity (TSE 1989). You know it only from its abstract and from Ron et al., so it is not cited. Do not claim more.

"The Knight and Leveson z of [5] and the pairwise score of [6] serve as baselines."

  • Plain words: K = number of inputs where two or more versions fail. Under independence, the expected K is T x Pm, where Pm = 1 - P0 - P1 comes from each version's failure rate. z = (K - T Pm) / sqrt(T Pm (1 - Pm)). Nogueira's pairwise score compares the shared failures of two versions with a hypergeometric expectation, F_i F_j / T. You report both so your results can be compared with [5] and [6].

"The fitted model also gives the odd number of runs N that minimises c_run N + c_fail P(majority of N fails)."

  • Plain words: each run costs money. A failure in use costs more. More runs lower the failure chance only if runs do not fail together. The model tells you where adding a run stops paying. Odd N avoids ties.
  • Link to Prof. Zheng's work: his rejuvenation papers find the restart time that maximises availability. This is the same kind of "best number" question. You can say that plainly.

"In practice the vote would pick the patch whose outputs agree with most other runs, and the model predicts how often that pick is wrong."

  • Plain words: in real use you do not keep N programs running and vote on every input. You pick one patch. You pick the one whose outputs agree most with the others. If most runs share a bug, the pick is the buggy patch. The model predicts how often that happens.

4.7 Field data (if time permits)

"Agent code keeps arriving, so a finite-fault NHPP for one fixed code base does not fit."

  • Plain words: classic NHPP models like Goel-Okumoto assume a fixed program with a fixed number of faults that testing slowly removes. In a repository where agents merge new code every week, new faults keep coming in.

"Instead, each merged agent change j (merge time τj, Lj added lines, covariates zj) adds ωj = Lj exp(β′zj) expected faults, found after a delay with distribution G, so m(t) = Σj ωj G(t - τj), with G from pysrat [4]."

  • Plain words: every merged change brings some expected faults, more for bigger changes (L_j lines) and depending on features z_j (for example which agent wrote it). Each fault is found after a random delay with distribution G. The expected number of faults found by time t is the sum over changes of "faults it brought" x "chance a fault is found by now". pysrat supplies the families for G (exponential, gamma, log-normal and others).

"This is an infinite-server queue, which Dohi, Osaki and Trivedi used to unify finite and infinite fault NHPP models [12]."

  • Plain words: faults "arrive" with changes and "leave" when found, and there is no waiting line, so it is like a queue with infinitely many servers (M/G/∞). Prof. Dohi used this view in 2004.
  • Honest limit: you have seen only the title and abstract of [12]. If asked for details, say so. [CONFIRM: change this line if you read the paper before the meeting.]

"I would build fix data for about 20 AIDev repositories [7] from commit messages, as Qiu et al. did from GitHub issues [3]."

  • Plain words: find fix commits (for example "fix: ...") that touch agent-written lines, and use their times as fault-detection times. Qiu et al. built four of their eight datasets from GitHub issue histories.

"Unlike the line-level Fine-Gray analysis of [10], this predicts how many fixes remain. Counts will be far below the 104 to 397 faults per dataset in [3], so I would pool repositories."

  • Plain words: Xia and Miller estimate the hazard of a line being fixed. Your model gives the expected number of faults still not found. Small counts per repository mean wide intervals, so you share parameters across repositories.

4.8 Limits

"The results cover only Python and only functions whose inputs can be generated. Differential testing cannot see a bug that the merged code shares, which is exactly the shared-helper case above."

  • Plain words: two honest limits. (1) Python, and functions with inputs you can build from type hints. (2) If the human also used the buggy helper, the merged code has the same bug, so the version and the reference agree and you see nothing. You name this yourself before anyone else does.

9. One concrete example, end to end

Everything in this section is imaginary. The repository, the rule, the pull request and every number are made up to show how the method works. They are not results. If you use this example in the meeting, say "for example, imagine ...".

Step 1: the repository and its rule

An imaginary Python repository shopkit sells things and also stores refund lines, which have negative prices. Its CLAUDE.md:

# CLAUDE.md
## Commands
- Run tests with `pytest -q`.
## Code
- Use type hints on public functions.
- Round money with shopkit.money.round_cents(). Never call round() on prices.   <- rule R
- Raise ValueError for bad arguments.

The helper the rule names was written in 2021 for shelf prices, which are never negative:

# shopkit/money.py
def round_cents(x: float) -> float:
    return max(0.0, math.floor(x * 100 + 0.5) / 100)   # clamps anything below 0 to 0.0

So round_cents(-2.70) returns 0.0. That is the edge case the helper mishandles.

Rule R is a good rule for the study: a script can check it (does the new code call round_cents?), and it changes what code is written, not where files go.

Step 2: the task

A real merged pull request, imaginary number #318: "Add apply_discount(price, percent). It returns the price after a percent discount, rounded to cents. percent must be between 0 and 100, otherwise raise ValueError."

The human who merged it wrote:

def apply_discount(price: float, percent: float) -> float:
    if percent < 0 or percent > 100:
        raise ValueError("percent must be between 0 and 100")
    new = Decimal(str(price)) * (100 - Decimal(str(percent))) / 100
    return float(new.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))

The PR's 4 tests (they fail before the PR and pass after):

apply_discount(100.0, 10) == 90.0
apply_discount(80.0, 25)  == 60.0
apply_discount(0.0, 50)   == 0.0
apply_discount(10.0, 150) raises ValueError

None of the tests uses a negative price. None uses percent = 100.

The agent gets the code just before #318 (no git history), the CLAUDE.md of that time, and a task text from the PR description. The text does not mention rule R. It does not get the 4 tests.

Step 3: the two file versions

Version The line where rule R was
Original - Round money with shopkit.money.round_cents(). Never call round() on prices.
Neutral - This project started as a small weekend shop in 2021, run by two friends. (about the same length, no instruction)

Everything else in the file stays the same.

Step 4: the runs

For this task, the settings are: Claude Code x 2 file versions, Codex (GPT-5.2) x 2 file versions, Codex (GPT-5.1 mini) on the original file, and the harness (Qwen3-30B-Coder) at two temperatures on the original file. Each setting has 10 runs in a fresh container. That is 70 runs for this one task. Below, only the two Claude Code settings are shown.

Claude Code, original file, 10 runs:

Run Passes PR tests? Admitted? Calls round_cents? What it wrote
r1 yes yes yes helper
r2 yes yes yes helper
r3 yes yes no Decimal, like the human
r4 yes yes no Decimal, but checks percent >= 100 (off by one)
r5 to r9 yes yes yes helper
r10 no no yes returned the discount amount, 10.0, not the new price

So 9 runs are admitted as versions. 7 of the 9 use the helper.

Claude Code, neutral file, 10 runs: all 10 pass the PR tests and are admitted. 3 of them still find and call round_cents (it is in the code base). 7 use Decimal or similar correct rounding.

The manipulation check: the checker looks in the added lines for a call to round_cents. With the rule: 8 of 10 runs. Without: 3 of 10. So replacing the rule clearly changed what the agent did. The check passes. (Before that, the checker itself was tested on 20+ hand-labelled diffs and agreed on at least 90%.)

Test pass rate (the old way of measuring): 9 of 10 with the rule, 10 of 10 without. Almost the same. The PR's tests cannot see the refund bug.

Step 5: the generated inputs

The declared distribution for apply_discount(price, percent), for example:

  • price: float from the type hint; random values between -20.00 and 980.00, mixed with the test values 100.0, 80.0, 0.0, 10.0. About 2% of inputs, around 200 of 10,000, have a negative price.
  • percent: random values between 0 and 100 with two decimals, mixed with 10, 25, 50 and 150 from the tests.

Each admitted version and the merged code run on all 10,000 inputs. Outputs are compared with the fixed rule (float tolerance, same exception class).

Step 6: which inputs fail together

A few rows of the result table (X = differs from the merged code):

Input (price, percent) Merged code 7 helper runs r3 r4
(100.00, 10) 90.0 90.0 90.0 90.0
(-3.00, 10) -2.70 0.0 X -2.70 -2.70
(-15.50, 0) -15.50 0.0 X -15.50 -15.50
(250.00, 100) 0.0 0.0 0.0 ValueError X
(10.00, 150) ValueError ValueError ValueError ValueError

What you see:

  • On every negative-price input, the same 7 of 9 versions fail, and they all give the same wrong answer, 0.0.
  • On positive prices, 0 of 9 fail.
  • r4's bug shows only at percent = 100.00 exactly. With random two-decimal values that comes up about once in 10,000 inputs, so random testing sees it once at most, and only by luck.

The hand check: you read 20 disagreements. For (-3.00, 10), is -2.70 right? The repository stores refunds as negative prices, so yes: the merged code is right and the input is legal. If negative prices were never legal in this repository, you would drop these inputs, and the "failures" would disappear. The declared distribution must match the real input domain.

Step 7: the numbers (rounded)

For each input, count failing versions. For Claude Code with the original file, θ is about 7/9 = 0.78 on the 2% negative inputs and 0 elsewhere (ignoring r4's one or two inputs at percent = 100).

Original file Neutral file
θ on negative inputs 7/9 = 0.78 3/10 = 0.30
Failure probability p of one run 0.02 x 0.78 = 0.016 0.02 x 0.30 = 0.006
Two runs both fail, if independent (p²) 0.00024 0.00004
Two runs both fail, from the model (E[θ²]) 0.012 0.0018
Intraclass correlation ρ about 0.77 about 0.30
2-out-of-3 vote fails, if independent 0.0007 0.0001
2-out-of-3 vote fails, from the model 0.0175 0.0043

How to read it:

  • RQ2: the test pass rate barely moved (9/10 vs 10/10), but the failure probability beyond the tests is about 2.6 times higher with the rule (0.016 vs 0.006). Across 10 tasks, the mixed model with task as a random effect gives one estimate of this effect.
  • RQ1: with the rule, runs fail together much more strongly (ρ 0.77 vs 0.30). Both are far from independence.
  • The vote: with the rule, a 2-out-of-3 vote fails more often than one run (0.0175 vs 0.016). On the hard inputs most runs are wrong (θ > 0.5), so the majority is wrong too. Eckhardt and Lee pointed this out in 1985: voting can make things worse when θ(x) > 0.5 on some inputs. Without the rule, the vote helps (0.0043 vs 0.006).

Picking a patch in practice: take the 9 admitted patches and pick the one whose outputs agree with the most other runs. The 7 helper patches agree with each other on every input, so the pick is a helper patch, and it is wrong on every refund. The model predicts this: with ρ = 0.77, the "most agreed" patch is usually the shared bug.

Step 8: how many runs to pay for

Say one run costs 1 unit and one failure in use costs 2,000 units. Expected cost = N + 2,000 x P(majority of N fails):

N Original file Neutral file
1 32.1 13.0
3 38.0 11.6
5 41.9 11.5
7 45.1 12.0

With the rule, the best N is 1: more runs only repeat the same bug. Without it, 3 to 5 runs are best. This is the kind of answer the model gives a team.

Step 9: the baselines

Knight and Leveson z for Claude Code with the original file: 7 versions fail on 2% of inputs, 2 never fail. Under independence, P0 = 0.98^7 = 0.868, P1 = 0.124, so Pm = 0.0079 and the expected K is 79. Observed K is about 200. z = (200 - 79) / sqrt(10,000 x 0.0079 x 0.992), about 13.8. Independence is clearly rejected.

Only if asked why you need ρ at all: for the neutral file, z comes out at about 55, larger than 13.8, even though runs share less (ρ 0.30 vs 0.77). z is a test statistic: it says how surprising the joint failures are under independence, and it depends on each version's failure rate and on the number of inputs. ρ is a size of dependence, from 0 to 1, and it goes straight into the vote formula. That is why ρ is the main measure and z is a baseline.

Step 10: the boundary stress test on the same task

The merged code has two branch conditions that compare a parameter with a constant: percent < 0 and percent > 100. So the boundary points for percent are 0 and 100 (and their neighbours, one minimal step away). BCD moves 30 to 50 test inputs toward them.

  • With percent = 100.00 in the set, r4 fails at once. The random inputs found it once at most, by luck.
  • A mutant of the merged code with > changed to >= (an ROR mutant) takes a different path at percent = 100, so the BCD set kills it for sure. The random set kills it only if it happens to draw exactly 100.00.
  • The refund bug is not found by BCD, because the merged code has no branch on price. Path-based boundaries only see branches. This is why BCD is a stress test next to the random inputs, not a replacement.

Step 11: the limit, in this example

Suppose the human who merged #318 had also called round_cents. Then the merged code would return 0.0 for refunds too. Every helper run would agree with the reference, and the bug would be invisible. That is the "Limits" sentence in the proposal: differential testing cannot see a bug that the merged code shares.

Step 12: from one task to the study

  • Do the same for 10 tasks (about 5 rules x 2 tasks) and all settings.
  • One table row per (task, setting, run, input) with fail or pass.
  • Fit the beta-binomial model per task and setting; bootstrap over runs for intervals of ρ and the vote failure.
  • For RQ1's second part, compare covariances between settings: does changing the agent, the model, the temperature or the file lower them most?
  • For RQ2, fit the mixed model over the 10 tasks: failure probability and test pass rate by file version, task as a random effect.
