1. Layerpath in general

W1. What does Layerpath do, and what exactly is your role?

Layerpath is a small remote startup that makes interactive product demos. I joined in November 2025 as an AI engineer on the founding team, and I build its AI features: Path AI, Magic Editor and BrandMemory.

If they push ("'Founding AI Engineer': are you a founder?"): "No. It's the title for one of the first engineers. I don't hold any shares or stock options; I'm paid a salary." If they push ("How big is the team?"): "A small team, about seven people."

Follow-ups (each builds on your last answer)

  1. Prof: "You said you build its AI features. Do you train the models yourself, or build on models from other companies?"
    You: "I build on models from other companies through their APIs, like Gemini, Claude and OpenAI's models, and Deepgram and ElevenLabs for speech; I don't train models at Layerpath. My part is everything around the model: what goes into the prompt, the structured output it must return, the checks on that output, and the pipeline that runs it."
  2. Prof: "Then the model can change under you. If the provider updates it, how would you notice that your feature got worse?"
    You: "Today, partly from failures. In July 2026 Google changed the model behind the 'latest' name we used and our create-with-AI video jobs started failing, so I pinned an exact model version in code and added a fallback for when a model is rejected. And before a planned switch, we compare models on a fixed set of real inputs, like four Gemini Flash versions in September. The proper way is to pin the model version, keep a fixed set of inputs, and re-run them whenever the version changes, comparing the share of failures before and after."
  3. Prof: "Say 6 of 50 fixed inputs fail before the update and 10 of 50 after. Is that a real change?"
    You: "Not on its own. That's 12% against 20%, and with the pooled share of 16% the standard error of the gap is the square root of 0.16 times 0.84 times 2 over 50, about 0.073, so a gap of 0.08 is only about 1.1 standard errors. Since it's the same 50 inputs, a paired test fits better: if 4 inputs went from pass to fail and none went the other way, McNemar's exact test gives 2 times 0.5 to the power 4, which is 0.125, still not significant. And because the model answers differently on each run, I'd run each input several times, not once."

W2. You wrote that you use Claude Code and Codex every day. What do you let them do, and what do you check yourself?

Follow-ups (each builds on your last answer)

  1. Prof: "You run the tests and then try the feature yourself. If the tests pass, what is left for you to find?"
    You: "Tests only check the cases someone thought of, and if the agent also wrote the tests, the tests and the code can share the same wrong idea. When I try the feature, I catch things no test looks at, like an empty input or a screen that breaks. That gap, code that passes its tests but still fails, is what my plan measures with generated inputs beyond the tests."
  2. Prof: "You said the tests can share the code's wrong idea. How would you check whether a set of tests is strong enough?"
    You: "One standard way is mutation testing: I plant a small fault in a copy of the code, called a mutant, for example a less-than changed to less-than-or-equal, and see whether the tests notice. The share of mutants they catch is the kill rate. Your lab's boundary value paper uses a kill rate like this to compare sets of test inputs, and my plan reports it the same way."
  3. Prof: "What is the weakness of the kill rate as a measure?"
    You: "First, some mutants don't change the output at all, called equivalent mutants, so no output check can kill them and the rate looks worse than it is. Your lab's paper counts a mutant as killed when an input takes a different execution path, but a different path doesn't always mean a wrong output, so I'd report the output version too. And a small planted fault isn't the same as the real faults an agent makes, so a high kill rate doesn't prove the tests catch those."

W3. Have you ever seen two agent runs make the same mistake?

Not with a coding agent, but with a model pipeline at work, yes. In September we ran our video-to-guide pipeline on Gemini twice, with the same short tutorial video and the same prompts, and both runs of the local-file version made the same mistake: no step for the first 80 seconds or so. That's only two runs, so it's a hint, not a measurement. Comparing coding-agent runs on the same task side by side is exactly what I want to do properly.

Why they ask: it checks whether your research question really comes from your work.

Follow-ups (each builds on your last answer)

  1. Prof: "If you did compare runs side by side, how would you decide that two runs made 'the same mistake'? Their code can look completely different."
    You: "I wouldn't compare the code, I'd compare behaviour. I'd run both versions on the same inputs and compare each output with the merged code's output under a fixed rule: a float tolerance, the same exception class, and order ignored where order doesn't matter. Two runs fail together on an input if both outputs differ from the reference there."
  2. Prof: "And if both fail on the same input but give different wrong outputs, is that still the same mistake?"
    You: "For my measure, yes: both versions failed on that input, so it's a coincident failure, as in Knight and Leveson and the Eckhardt and Lee model. It also matters for a vote: with two different wrong outputs and one right one, a 2-out-of-3 vote finds no two outputs that match, so it can't return the right answer. I'd count identical wrong outputs separately, because only those make the vote return a wrong answer instead of no answer."
  3. Prof: "Then give me the basic number. If three versions each fail independently with probability 0.1, how often does a 2-out-of-3 vote fail?"
    You: "It fails when at least two of the three fail. That's 3 times p squared times 1 minus p, plus p cubed: 3 times 0.01 times 0.9 is 0.027, plus 0.001, so 0.028. That's 3p squared minus 2p cubed, the formula in my plan with a fixed p, so the vote fails a bit more than a quarter as often as one version. But that holds only under independence; if the versions tend to fail on the same inputs, the vote helps less."

W4. How is your Layerpath work related to reliability?

Every feature I build depends on a model that can give a different or wrong answer each time. In BrandMemory, the system logged that a rule was applied, but the rule never reached the model. The system said it worked and it didn't, and no error showed it. That's a reliability problem, and a test that only checks "did it run" can't catch it.

If they push ("Did you measure a failure rate?"): "No, not with an interval. That's the part I want to learn here."

Follow-ups (each builds on your last answer)

  1. Prof: "You said a test that only checks 'did it run' can't catch it. What kind of test would have caught it?"
    You: "A test on what the model actually receives, not on the log. For example, build the final prompt for a brand with a known rule and check that the rule's text is still in it after all the cutting; after my fix I checked that, and no section was cut.   2. Prof: "You ran that pair once, with one output on each side. What can one pair tell you, and what can't it?"
    You: "It shows the rule reached the model and changed the text in that case: contractions went from 6 to 0, and 'you' and 'your' from 15 to 1.   3. Prof: "Suppose you ran 30 pairs and the rule showed up in 27. What would you report?"

2. Path AI

W6. How does Path AI work?

It's a voice agent that phones sales leads and qualifies them through a conversation with several stages. It runs on a real-time voice pipeline: the caller's speech becomes text, a model decides the next reply, and the reply is spoken back. The hardest part is keeping replies fast enough for a natural call.

If they push ("Which tools?"): "Pipecat for the pipeline, Daily for the audio connection, Deepgram for speech to text, a language model set per agent, Gemini by default, and ElevenLabs or Cartesia for the voice. Silero VAD detects when the caller has stopped." Your CV's LiveKit and Whisper are not in Path AI, so don't name them.

Follow-ups (each builds on your last answer)

  1. Prof: "You said replies must be fast enough for a natural call. How fast is that, and where does the time go?"
    You: "People usually start their reply within a few hundred milliseconds, and a silence of about a second already feels long on the phone. The time adds up across the stages: noticing the caller has stopped, speech to text, the model's first words, and text to speech. I don't have a measured breakdown for Path AI, so to find the slowest stage properly I'd timestamp every stage on real calls and compare their 95th percentiles."
  2. Prof: "How does the system notice that the caller has stopped, and what goes wrong there?"
    You: "Usually with voice activity detection, a small model that says whether someone is speaking, plus a silence timeout: if there's no speech for a set time, the turn is over. Path AI uses Silero VAD, and the turn ends after 0.8 seconds of silence. The trade-off is that a short timeout makes the agent cut in when people pause to think, and a long one adds that wait to every reply."
  3. Prof: "How would you choose that timeout properly, rather than by feel?"
    You: "From recorded calls I'd collect the pauses inside a caller's turn, where they stopped briefly but weren't finished. For a timeout t, the chance of cutting in on a pause is the share of those pauses longer than t, and every reply waits about t. Then I'd pick the t that minimises a weighted sum of the two, with the weight saying how much worse an interruption is than a slow reply, and check it on calls I didn't use to choose it."

W7. Your CV says 85% accuracy. Accuracy of what, and how was it measured?

The call count comes from our system; the accuracy was an internal team figure, not a careful study, so I won't defend it as a research number. If I measured it properly, I'd define a correct call first, have two people label a random sample of a few hundred calls, and report their agreement and a confidence interval.

If they push ("What would the interval be?"): "For example, if 170 of 200 labelled calls were right, that's 85% with a 95% interval of about plus or minus 5 points, because the standard error is the square root of 0.85 x 0.15 / 200, about 0.025." (Made-up numbers, only to show the method.) Same rule for "1,500+ calls a month" and "75% less than a human rep": "The call count comes from our system. The 75% is a cost figure from work, not a study. Properly, I'd compare the full cost per qualified lead for the agent and for people over the same period."

Follow-ups (each builds on your last answer)

  1. Prof: "Then define it. What would count as a correct call for a qualification agent?"
    You: "I'd call it correct if the result the agent records, qualified or not, matches what a trained person decides after listening to the whole call, and the call didn't break, for example the agent dropping it halfway. The person labels the call without seeing the agent's answer, so it can't sway them."
  2. Prof: "People disagree too. How would you know your human labels are reliable?"
    You: "I'd have two people label the same sample independently and report Cohen's kappa, which is their agreement corrected for the agreement you'd get by chance. If kappa is low, the definition is unclear, and I'd fix it before measuring the agent. My plan uses the same idea for its rule checkers: a checker must agree with my hand labels on at least 90% of 20 or more examples, and I report kappa."
  3. Prof: "Compute it. Two people agree on 90% of calls, and each says 'qualified' 80% of the time. What's kappa?"
    You: "Chance agreement is 0.8 times 0.8 plus 0.2 times 0.2, which is 0.68. Kappa is observed minus chance, over one minus chance: 0.90 minus 0.68 is 0.22, divided by 0.32, about 0.69. So 90% raw agreement is only 'substantial' on the usual scale, because when one label is that common, a lot of agreement happens by chance."

W8. What goes wrong in Path AI calls?

The ones I've fixed in its code: speech to text mishearing our names, like 'layer parts' for Layerpath, a caller's short 'yeah' or 'okay' cutting the agent off mid-sentence, broken words and doubled transcripts, conversations stuck in the qualifying stage or dropping a demo request, and sessions where the agent never replied after a model problem. Then: "Most of them only show up in real calls, not in our tests, which is the same gap my plan is about."

Follow-ups (each builds on your last answer)

  1. Prof: "You said these failures show up in real calls but not in your tests. Why?"
    You: "Because our test input is cleaner than real calls: fixed text messages, whole conversations with another model playing the lead, and 25 prepared audio clips, some with background noise or fast or slow speech. Real calls have line noise, accents, people talking over the agent and answers nobody planned for. The tests cover the situations we thought of; real callers bring the ones we didn't."
  2. Prof: "So how would you build test input that is closer to real calls?"
    You: "I'd start from real calls rather than invent them: take recorded caller turns, from callers who agreed to recording, and replay them into the pipeline, plus variations with added noise or other accents. My plan does the same for code: it builds inputs from the type hints and the values in the real tests, not only from cases I write by hand."
  3. Prof: "But in a conversation the caller's next words depend on what the agent just said. Doesn't replay break that?"
    You: "Yes, that's its weakness: replay only works one turn at a time, because once the agent says something different, the real caller's next answer no longer fits. For whole calls I'd need a simulated caller, another model playing the lead, but then I'm testing against a model's idea of a caller. So I'd use replay for single turns, like speech recognition, and simulated callers for the flow, and check both against a small sample of real calls."

W9. If you had to measure Path AI's reliability properly, how would you do it?

I'd first define a failure for one call, for example "the qualification it records differs from what a person decides after listening". Then I'd take a random sample of calls, label them without seeing the agent's answer, and report the failure share with an interval, per model version. For speed, I'd report a high percentile of reply delay, not just the average.

Why they ask: this question shows the step from engineer to researcher. They want a definition, a sample and an interval.

Follow-ups (each builds on your last answer)

  1. Prof: "Why a high percentile of the delay and not the average?"
    You: "Because delay is skewed: most replies are quick, but a few are very slow, and those few are what make a caller think the line went dead. The average hides them, while the 95th percentile says one reply in twenty is slower than this value. In a call with 20 replies, that's about one bad pause per call."
  2. Prof: "Then what's the chance that a 20-reply call has no reply slower than the 95th percentile?"
    You: "If replies are independent, it's 0.95 to the power 20, about 0.36. So almost two calls in three have at least one reply slower than the 95th percentile. That's why for whole calls I'd use a higher percentile, like the 99th, or report directly the share of calls with any pause above a set limit."
  3. Prof: "You assumed the replies are independent. Are they?"

If they push ("What happens when it's rejected?"): "That action isn't applied, but the rest of the batch still goes through, and the agent is told which one failed and why, for example 'element X was not found on step Y'. Follow-ups (each builds on your last answer)

  1. Prof: "A schema checks the shape of the object. How does it know an edit is impossible, say element X doesn't exist?"

W20. How is the confidence score computed?

Follow-ups (each builds on your last answer)

W44. Yuki keeps a confidence score for what it learned: (S + 1) / (S + F + 2), times a time decay. What is that formula?

W63. What does the central limit theorem say, and where does it show up in your plan?

The average of many independent values from the same distribution is close to normally distributed, whatever that distribution is, as long as its variance is finite. It's why the Knight and Leveson z can be compared with a normal distribution, and why a normal interval for a failure probability works when there are enough failures.

If they push ("When does it break?"): "With very few failures. With 0 failing inputs the normal interval is useless, so I'd use an exact interval or the rule of three."

Follow-ups (each builds on your last answer)

  1. Prof: "Walk me through that z. What exactly is counted, and why is it close to normal?"

W82. You wrote that a 2026 result impressed you: 429 joint failures against about 115 expected. Where does 115 come from?

From each program's own failure rate. Under independence you can compute the chance that two or more of the 48 programs fail on one input, from the chance that none fail and that exactly one fails. Times one million inputs, that gives about 115 inputs. Ron et al. saw 429, almost four times more. But voting over three programs still cut the mean failure count from 387 to 131.

If they push ("Write the test."): "K is the number of inputs where two or more fail. The expected value is T times P_m, with P_m = 1 - P_0 - P_1, and z = (K - T P_m) / sqrt(T P_m (1 - P_m)). They got z = 29.2."

Follow-ups (each builds on your last answer)

  1. Prof: "Write P_0 and P_1 for us."
    You: "P_0, the chance that none of the 48 fails on an input, is the product of 1 minus p_i over all the programs. P_1, the chance that exactly one fails, is the sum over i of p_i times the product of 1 minus p_j over all the others. Each p_i is that program's own failure count divided by the million inputs."
  2. Prof: "Their mean failure count was about 387 per million. If all 48 failed at exactly that rate, what would you expect?"
    You: "About 167 inputs, close to 1,128 pairs times p squared, so more than 115. The real rates are very unequal: 27 programs never failed, and the worst failed on 10,469 inputs. For the same total, unequal rates give fewer expected pairs, because the sum of p_i p_j is the square of the total minus the sum of the squares, over two."
  3. Prof: "Then under independence, how often would a 2-out-of-3 vote fail?"
    You: "A triple fails when at least two of its programs fail, so I need the average p_i p_j over pairs: about 115 per million spread over 1,128 pairs, roughly 1 in 10 million per pair, times three pairs, so about 0.3 inputs per million. They saw 131, over 400 times more. So voting still cut failures to about a third, from 387 to 131, but nowhere near what independence promised."

W86. How do you test software whose output changes from run to run?

I fix what I can, like versions and, where possible, the temperature. Then I run it several times, check properties instead of exact strings, and count failures across runs. I treat one setting as a distribution of runs, not one output. That's also how my plan treats agent runs.

Follow-ups (each builds on your last answer)

  1. Prof: "You said you run it several times. How many runs do you need?"
    You: "It depends on the question. To see, with 95% chance, at least one failure that happens in one run in ten, I need 29 runs, because 0.9 to the 29 is just under 0.05. To estimate a failure rate to within 5 points with 95% confidence, I need up to about 385."
  2. Prof: "Your plan has 10 runs per setting. What can 10 runs miss?"
    You: "Anything that only a few runs do. If one run in ten picks a buggy design, all 10 runs miss it about 35% of the time, since 0.9 to the 10 is 0.35. Each run's own failure probability is still measured well, from at least 10,000 inputs, so what 10 runs limit is how clearly I see the spread across runs, and the pilot tells me whether that's enough."
  3. Prof: "What does that spread tell you?"
    You: "Whether runs fail on the same inputs. For each input I count how many of the 10 runs fail; if those counts are more spread out than a binomial allows, with more inputs where none fail and more where many fail, the failures cluster, and the beta-binomial's rho says how much. If runs fail on 10% of inputs on average, a binomial gives all 10 runs failing on the same input a chance of 10 to the minus 10, so even one such input among 10,000 is strong evidence."

W87. Give an example of a common-mode failure in your own systems.

The BrandMemory limit. The same 3,200-character cut removed the brand voice from every generation in the same way. It wasn't random, so running the generation again would never have fixed it. That's the same idea as a shared rule giving every agent run the same bug.

Follow-ups (each builds on your last answer)

  1. Prof: "You said running it again would never fix it. Which failures would a re-run fix?"
    You: "Ones that come from timing or chance rather than the input: a model call that times out, a rate-limit error, or one unlucky sample where the model ignores an instruction. Those change from run to run, so a retry or a vote helps. The BrandMemory cut failed the same way every time for the same input."
  2. Prof: "Is there a name for those two kinds of fault?"
    You: "Grottke and Trivedi call them Bohrbugs and Mandelbugs. A Bohrbug fails the same way under well-defined conditions, while a Mandelbug's failures are hard to reproduce because they depend on timing or hidden state, and aging-related bugs, the ones rejuvenation deals with, are a kind of Mandelbug. A retry or a restart can get past a Mandelbug, but a Bohrbug comes back every time, so it has to be fixed, or masked by a version built differently, which is the N-version idea."
  3. Prof: "In your plan's model, what does a Bohrbug that every run inherits look like?"
    You: "If it fails every run on the inputs it touches, theta of x is 1 on those inputs, and if nothing else fails, 0 everywhere else. Then E of theta squared equals E of theta, so two runs both fail with probability p, not p squared, and the intraclass correlation, the variance of theta over p times 1 minus p, is exactly 1. That's the most dependent case: the runs always agree, so a vote gains nothing."
