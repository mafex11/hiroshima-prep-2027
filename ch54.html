1. The paper your RQ1 builds on

Generative AI and N-version programming (Zheng, Okamura, Dohi, SFPVV 2025, LNCS 16356, 2026)

What it does, in plain words: N-version programming runs several independently written versions of a program and votes on the answer. It is rarely used, because writing many versions is expensive. So the paper asks whether LLMs can write the versions cheaply. It checks the generated code for correctness and diversity. It compares high-performing models (for example GPT-4o) with weaker ones. It also tries two ways to add diversity: changing the temperature and reusing the conversation history. Majority voting made the strong models more reliable but helped little with the weak ones. More diversity did not always mean more reliability.

Link to your proposal: RQ1 takes the same question to coding-agent runs on real repository tasks, and adds the shared context file as a possible cause of runs failing together.

Honest line: "I've read the abstract; the full text is behind the Springer paywall. Could I ask you for a copy?"

Basics to know

  • N-version programming: several versions of one program run on the same input, and a vote picks the output.
  • 2-out-of-3 vote: the output is wrong only if at least 2 of the 3 versions are wrong. If each version fails with chance θ on an input, the vote fails with 3θ² − 2θ³.
  • Coincident failure: two or more versions failing on the same input. Eckhardt and Lee showed that two versions from one process fail independently only if every input is equally hard, that is, Var θ = 0.
  • Temperature: a setting that makes an LLM's output more random, so repeated answers differ more.

  • Newer models don't let you set the temperature, so they did not compare new models.

Q1. (Prof. Zheng) Have you read our N-version paper?

Follow-ups (each builds on your last answer)

  1. Prof: "You mentioned strong and weak models. Do you remember which models we used?"
    You: "Yes, you told me on 2 November: GPT-4o and GPT-4o mini, if I heard you right. You also said newer models don't let you set the temperature, which is why you didn't compare them."
  2. Prof: "Right. So if you can't set the temperature on newer models, where will the diversity in your study come from?"
    You: "Mostly from changing other things between runs: the file version, the agent and the model. I keep the temperature comparison in my own harness with the open-weight model, where I can set it. And even at one fixed setting, repeated agent runs often end with different code, so I treat each setting as a distribution of runs."
  3. Prof: "Is that run-to-run difference real diversity, or just noise around the same solution?"
    You: "That's exactly what I want to measure. If it's just noise around one design, the runs will fail on the same hard inputs, so ρ, the intraclass correlation, will be high. If runs from two different agents share fewer failures than two runs from the same agent, then changing the agent is the diversity worth paying for."

Q2. (Prof. Zheng) In our paper, voting helped the strong models much more than the weak ones. How would you use that in your study?

It suggests voting pays off mainly when each run is already usually right. Claude Code and Codex run strong commercial models, so I expect voting to help there, and I want to measure how much a shared context file takes away from that gain. If the open-weight model in my harness turns out weaker, I can also check your weak-model result on real tasks.

If he pushes ("Why would voting not help a weak model?"): "Say versions fail on an input more often than not, so θ is above 0.5 there. Then the majority is usually wrong on that input, and adding versions makes it worse. Eckhardt and Lee showed this. I can't say that is the reason in your paper, since I've read only the abstract."

Follow-ups (each builds on your last answer)

  1. Prof: "You said you'd measure how much the shared file takes away from the voting gain. How would you put a number on that?"
    You: "I compare the vote's failure probability from my fitted model with what it would be if runs failed independently. Under independence a 2-out-of-3 vote fails with 3p squared minus 2p cubed, and with shared failures it's the average of 3θ squared minus 2θ cubed over the inputs. The gap is the gain lost to shared failures, and I compare that gap between the two file versions."
  2. Prof: "Can you work out the independent case for me, if each run fails 10% of the time?"
    You: "3 times 0.1 squared is 0.03, and 2 times 0.1 cubed is 0.002. So the vote fails with 0.03 minus 0.002, which is 0.028. That's 2.8% instead of 10%, more than three times better."
  3. Prof: "And if the runs are correlated, say with ρ equal to 0.3?"
    You: "Then two runs both fail with p squared plus ρ times p times 1 minus p, which is 0.01 plus 0.027, so 0.037. With a Beta model, the chance that all three fail comes to about 0.019. So the vote fails with 3 times 0.037 minus 2 times 0.019, about 0.073. Voting now only takes 10% down to about 7.3%, not to 2.8%."

Q3. (Prof. Zheng or Prof. Dohi) We found that more diversity does not always mean more reliability. Why do you think that is?

I can only guess, since I've read just the abstract. Code that looks different can still fail on the same hard inputs, so diversity in the code is not the same as diversity in failures. And a setting that adds diversity, like a higher temperature, might also make each version fail more often. That's why I measure how often runs fail on the same inputs, not how different the code looks.

Note for you: you already asked Prof. Zheng this on 2 Nov, and he said he would show you his team's new results. If Prof. Zheng is in the meeting, you can say: "On 2 Nov you mentioned new results on this. I'd be glad to hear them."

Follow-ups (each builds on your last answer)

  1. Prof: "You said diversity in the code is not diversity in failures. How do you measure diversity in failures, then?"
    You: "On each input I count how many of the k runs fail. If runs failed independently, that count would be binomial, but if they fail together it spreads out more, with many inputs where none fail and some where most fail. The beta-binomial model measures that extra spread with one number, ρ, which is 0 for independence and 1 when the runs always fail together."
  2. Prof: "How much extra spread? Can you give me the formula?"
    You: "The binomial variance of the count is k times p times 1 minus p. The beta-binomial variance is that times 1 plus k minus 1 times ρ. So with 10 runs and ρ of 0.2, the factor is 1 plus 9 times 0.2, which is 2.8. The variance of the count is 2.8 times what independence predicts."
  3. Prof: "Can runs ever fail together less often than independence predicts?"
    You: "Not within one setting: two runs from the same process both fail with p squared plus a variance, and a variance can't be negative. Across two settings it can, if one setting finds hard the inputs the other finds easy, so the covariance is negative. That's Littlewood and Miller's forced diversity idea, and it's why I compare settings by their covariance."

Q4. (Prof. Zheng) Why didn't you include conversation history reuse, like we did?

It's not in my plan now. My own harness controls the whole prompt, so I could add it as one more setting if you think it's worth it. Could I ask how you did it? My guess is that the model sees its earlier versions in the same chat, but I'm not sure from the abstract.

If he pushes ("How do you think we measured diversity?"): "The abstract doesn't say, so I'd rather ask you. How did you measure it?"

Note for you only, not a line to say: Nogueira et al. describe this paper as using AST-based similarity between solutions. You haven't checked that in the paper, so don't say it.

Follow-ups (each builds on your last answer)

  1. Prof: "Suppose you're right and the model sees its earlier versions. Are your runs then still independent draws, as your model assumes?"
    You: "No. Run two then depends on run one, so the runs are no longer separate draws from one setting, and my beta-binomial model doesn't fit them as they are. I'd have to treat the position in the chat as part of the setting."
  2. Prof: "How would you analyse it then?"
    You: "I'd make the whole chat the unit: say 10 separate chats per task, each writing three versions in a row. Across chats I'd estimate each position's failure rate and how often two versions from one chat fail on the same input. My covariance formula assumes runs are linked only through the input, which isn't true inside a chat, so I'd measure that joint rate directly."
  3. Prof: "Would you expect the later versions in a chat to be as good as the first?"
    You: "Not necessarily. If the model is asked for something different from what it already wrote, it may move away from the most natural design, which is often the right one, so later versions could fail more often. That would be another case of more diversity without more reliability, and estimating each position separately would show it."

2. The boundary value papers (your RQ2)

Boundary coverage distance (Guo, Okamura, Dohi, Software Quality Journal 2024)

What it does, in plain words: Boundary value analysis tests inputs at the edges where a program's behaviour changes. This paper defines boundary coverage distance (BCD). It counts how many minimal steps, like plus or minus one, a test set is from covering every boundary value. Three MCMC-like algorithms move random test inputs toward the boundaries to make BCD small. On five programs (four small ones and the miniSAT solver), the best variant killed 0.8 to 1.0 of the planted mutants. Random testing killed 0.36 to 0.66. The paper's stated limits: boundary points were found by hand, and strings and arrays need more work.

Link to your proposal: RQ2 uses BCD only as a stress test, with boundary points taken from branch conditions in the merged code instead of by hand, and the kill rate measured with coverage.py branch data.

Honest line: "I've read the abstract, the BCD definition with Remarks 1 and 2, and the results in Section 5.6."

Basics to know

  • Equivalence partition: a group of inputs that give the same kind of output. The paper's example is a program that takes a student's English listening and reading scores and has three outputs: invalid input, credit, no credit.
  • Boundary value: an input where one minimal step (for example plus one) moves you into another partition. That small English example already has 963 of them.
  • Distance: the smallest number of minimal steps from one input to another.
  • BCD: for each boundary value, find the nearest test input, then take the worst case over all boundary values and partitions. Small BCD means every boundary has a test input close to it. Listing every boundary value is hard, so the paper computes a lower limit from chosen boundary points and an upper limit from boundary segments.
  • Mutation testing and kill rate: plant small faults (mutants), like changing < to <=, and count the share a test set catches. In this paper a mutant is killed if some input takes a different execution path.

Q5. (Prof. Okamura) Can you explain BCD in simple words?

For every boundary value, I look for the nearest test input, counting the distance in minimal steps like plus or minus one. BCD is the worst of those distances. If BCD is small, every boundary has a test input close to it. Since listing every boundary value is hard, the paper uses a lower and an upper limit instead.

If he pushes ("In our experiment the mean worked better than the max. Why?"): "With the max, only the worst-covered boundary counts, so most proposed moves change nothing and are rejected. With the mean, every boundary point counts, so more moves are accepted. Your Table 6 shows the higher acceptance rate for the mean."

Follow-ups (each builds on your last answer)

  1. Prof: "In our English example, what is the distance from (−1, −1) to (0, 0)?"
    You: "Two. With only plus or minus one on each value, I need one step to raise the first value and one to raise the second, and I can't do it in fewer."
  2. Prof: "And if we also allow raising both values at once?"
    You: "Then it's one step. And (−1, −1) becomes a boundary value itself, because that one step takes it to (0, 0), which is in the no-credit partition. That's your Remark 1: the boundaries depend on which operations you allow."
  3. Prof: "So does adding operations always make BCD smaller?"
    You: "Not always. Distances get shorter, but more inputs become boundary values, so there are more points to cover, and the worst case can go either way. So BCD values only compare fairly under one fixed set of operations, and I'd fix that set for each input type before the runs."

Q6. (Prof. Okamura) In our paper the boundary points were found by hand. How will you find them?

I take them from branch conditions in the merged code that compare a parameter with a constant. For example, if the code says if n > 100, then 100 and 101 are boundary points for n. These are path-based boundaries, which your Remark 2 says can differ from output-based ones, so the pilot will report how many functions have them.

Why he asks: finding boundaries by hand is the paper's own main limit, so he wants to see if your answer works.

Follow-ups (each builds on your last answer)

  1. Prof: "What if the condition is on a computed value, like a plus b greater than 120?"
    You: "Then it isn't one parameter against a constant, so my simple rule misses it. The boundary is now a whole line of points where a plus b is 120 or 121, so I'd have to solve for points on it, for example fix a and set b to 120 minus a and 121 minus a. That's what a constraint solver would do for me."
  2. Prof: "Why not use a solver, or concolic testing, for every condition then?"
    You: "For simple linear conditions I could. But a solver usually gives one input per path, and your 2024 paper found concolic testing weak on off-by-one bugs, with KLEE making only one test case for miniSAT. So I'd use a solver only to find boundary points, and keep BCD to place inputs close to them."
  3. Prof: "A solver finds where the path changes. Is that the same boundary our paper defines?"
    You: "Not always. Your paper defines partitions by output categories, and Remark 2 says partitions by execution path can differ. If a function uses a fast formula above 100 and a simple loop otherwise, with the same answer, then 100 is a path boundary but not an output boundary, so I report kills both ways, by path as in your paper and by output."

Q7. Why do you use BCD only as a stress test, and not to estimate a failure probability?

BCD picks 30 to 50 inputs on purpose, close to the boundaries. They are not drawn from a declared distribution, so the share that fail is not a failure probability. For the estimate I use at least 10,000 random inputs per entry point. The BCD inputs are there to catch bugs that random inputs rarely hit, like off-by-one errors.

If he pushes ("How will you decide a mutant is killed?"): "I report it both ways. As in your paper, a mutant is killed if its execution path differs, using coverage.py branch data instead of Gcov. I also report it by outputs, because a different path with the same output is not a failure for the user."

Follow-ups (each builds on your last answer)

  1. Prof: "Why at least 10,000 random inputs? How precise is that estimate?"
    You: "If the failure probability is 1 in 1,000, 10,000 inputs give about 10 failures. With 10 failures, the exact 95% interval runs from about 0.0005 to 0.0018. So it pins the rate down to within about a factor of two, which is enough to tell 1 in 1,000 from 1 in 100."
  2. Prof: "And if none of the 10,000 inputs fail?"
    You: "Then I can't say the probability is zero. The 95% upper limit is 1 minus 0.05 to the power 1 over n, which is about 3 over n, the rule of three, so about 3 in 10,000. I'd report it as below 0.0003, not as zero."
  3. Prof: "Below 0.0003 under your own generator. Is that what real users would send?"
    You: "No, and that's the weak point. The number holds only for the input distribution I declare, built from the type hints and the pull request's test values, not for the operational profile, meaning the inputs real users send. But I give both file versions the same inputs, so the comparison between them is still fair even if the absolute number isn't the field number."

Q8. (Prof. Okamura) We said strings and arrays need more work. What will you do?

I'll try one-element edits as the minimal operations: insert, delete or replace one character or element. A chain of them can turn any string into any other, which is close to the second property of your operation set in Section 2. But strictly, none of these edits is a bijection like plus one and minus one, so I'd like to check with you whether that matters.

If he pushes ("And floats?"): "Your conclusion suggests a Gaussian or a similar method to find nearby points for continuous inputs. I'd start with a small fixed step around the constant in the branch condition, and see what the pilot shows."

Follow-ups (each builds on your last answer)

  1. Prof: "Why is inserting one character not a bijection?"
    You: "Adding an 'a' at the end can never give the empty string, or any string that doesn't end in 'a', so it isn't onto. Its partner, deleting the last character, sends 'ab' and 'ac' to the same 'a', so it isn't one-to-one. So neither has a true inverse, and your definition needs one."
  2. Prof: "So how would you make strings fit our framework?"
    You: "One way is to drop the bijection and use the Levenshtein distance, the fewest inserts, deletes and replacements between two strings, so 'the nearest test input' still makes sense. The other way is to fix the length and only shift one character to the next or previous letter, wrapping around. That is a bijection, but then I lose the boundaries on length."
  3. Prof: "Do length boundaries matter that much? Can you give me an example?"
    You: "Yes. In Python, max of an empty list raises a ValueError, so code that forgets the empty case fails only at length zero. And a limit like 'at most 255 characters' written with less-than instead of less-than-or-equal fails only at exactly 255, one insert away from inputs that pass."

Machine learning for boundary values, journal version (Guo, Okamura, Dohi, Array 2025)

What it does, in plain words: This paper automates boundary value analysis for white-box testing in two steps. First, a machine learning discriminator is trained to tell whether a boundary lies between two test inputs. Its output gives a "boundary density", computed in two ways called pointDensity and pairDensity. Then Markov chain Monte Carlo generates test inputs guided by that density. The method beat manual boundary analysis on five of eight programs, and concolic testing on four of eight.

Link to your proposal: It finds boundaries automatically with machine learning. The same authors published the same two-step method at DSA 2023, before the 2024 paper, which cites it. The 2024 paper also names automatic boundary finding as future work. Your plan uses a simpler rule (branch conditions), so this is the natural next step if few functions have such branches.

Honest line: "I've read the abstract only."

Basics to know

  • MCMC (Markov chain Monte Carlo): propose a small random move, then accept or reject it by a rule, so that over many steps the samples follow a target density. Here the density is high near boundaries, so most generated inputs land near them.
  • Discriminator: a classifier. Here it takes two inputs and answers "is there a boundary between them?"
  • Concolic testing: run the program on real inputs while tracking the path conditions as symbols, then solve them to get inputs that take new paths. KLEE is one such tool.

Q9. (Prof. Okamura) Our newer work learns the boundary with machine learning. Why do you use branch conditions instead?

Branch conditions are simple to find in the merged code, and easy to check. If the pilot shows that many functions have no such branch, your machine learning method is the natural next step, and I'd like to learn it here. I've read only its abstract so far.

Follow-ups (each builds on your last answer)

  1. Prof: "You said branch boundaries are easy to check. How would you check one?"
    You: "I'd run the merged code on the two points, say 100 and 101 for n greater than 100, and confirm with coverage.py branch data that they really take different branches. If they don't, for example because n was changed earlier in the function, I drop that point."
  2. Prof: "How often do you think a parameter is changed before the branch in real code?"
    You: "I don't know yet. The pilot will count it: for each entry point, how many boundary points pass that check, and how many conditions compare only computed values. If most are computed, the simple rule finds little, and that's where your machine learning method or a solver would come in."
  3. Prof: "What number from the pilot would make you switch?"
    You: "I haven't fixed one yet. For example, if fewer than half of the entry points have at least one usable branch boundary, I'd add another method. I'd like to agree that number with you before the pilot, not after I see the data."

Q10. What does the discriminator learn, and where could its training labels come from?

From the abstract, it takes two test inputs and says whether a boundary lies between them. Since the paper focuses on white-box testing, my guess is that the labels come from running both inputs and checking whether they take different paths. I'd need to read the paper to be sure.

If he pushes ("What are pointDensity and pairDensity?"): "The abstract names them as two ways to turn the discriminator's output into a boundary density. I don't know the details yet."

Follow-ups (each builds on your last answer)

  1. Prof: "Is 'the two inputs take different paths' the same as 'a boundary lies between them'?"
    You: "Not exactly. Take a branch that checks whether n is even: 4 and 6 take the same path, but 5 between them takes the other one, so two boundaries lie between 4 and 6. So a different path shows that at least one boundary is crossed, but the same path doesn't prove there's none."
  2. Prof: "So how would you choose the training pairs?"
    You: "I'd use pairs that are close together, one or a few minimal steps apart. Then there's rarely more than one boundary between them, so 'different path' is close to 'a boundary lies between'. That's my guess, and I'd check in the paper how you chose them."

Basics to know

Aging means software slowly gets worse while it runs, for example through a memory leak, until it fails. Rejuvenation means restarting it on purpose before that, to clear the built-up state. Your work finds the restart timing that keeps the system available the most.

Why he asks: rejuvenation is one of his main topics, with papers from 2013 on and a 2026 Springer handbook chapter on software aging and rejuvenation. A clear two-line answer shows you looked at his work.

Follow-ups (each builds on your last answer)

  1. Prof: "Why not just restart very often, then?"
    You: "Because every restart costs downtime too, even if it's shorter than recovering from a crash. Restart too often and you lose time to restarts; too rarely and the software fails and needs a longer repair, so the best interval is somewhere in between."
  2. Prof: "Write the availability as a function of the restart interval T."
    You: "Take one cycle that ends either in a failure or in a restart at time T. The mean uptime is the integral of the survival function R(t) from 0 to T. The mean downtime is μ_f, the mean repair time, times F(T), the chance of failing before T, plus μ_r, the mean restart time, times R(T). Availability is uptime over uptime plus downtime, and I choose T to maximise it."
  3. Prof: "And if the failure time is exponential?"
    You: "Then the best T is infinity: never restart. The exponential is memoryless, so a restart doesn't lower the future risk, it only adds downtime. Rejuvenation can only pay off when the failure rate rises with time, which is what aging means, and a restart is quicker than a repair."

Q41. Why model the test profile as a Markov chain?

A Markov chain picks the next component from the current one with fixed probabilities, so it can make long, realistic sequences of use. Aging bugs need long runs to show, because their effect builds up. Short, separate tests would miss them.

Follow-ups (each builds on your last answer)

  1. Prof: "You said fixed probabilities, but our framework adjusts the test profile during testing. Why?"
    You: "You're right, I simplified. The abstract says the profile is adjusted gradually during testing, so that the tests imitate aging. My guess is that it also steers the tests toward components that look linked to the build-up, but I'd need to read how you adjust it."
  2. Prof: "Why would steering matter? Say a component is entered with probability 0.001 at each step. How long a sequence do you need to reach it?"
    You: "The number of steps to the first visit is geometric, so on average 1 over 0.001, which is 1,000 steps. To be 95% sure of at least one visit, I need 0.999 to the power n below 0.05, so n is about the natural log of 20, which is 3, over 0.001, roughly 3,000 steps. And an aging bug needs many visits, not one, so raising that probability saves a lot of testing time."
  3. Prof: "But once you change the profile, what happens to a reliability estimate from those tests?"
    You: "It's biased, because the tests no longer follow real usage, so failures may show up far more often than users would see them. To correct it, I'd weight each test sequence by its probability under the real profile over its probability under the test profile, which is importance sampling. For a Markov chain that weight is just the product of the ratios of the transition probabilities along the path."

Q42. Would your generated inputs find aging-related bugs?

Probably not. Each of my inputs calls one function once, so a bug that builds up over many calls, like a slow leak, would not show. That's another limit of my plan, and I'd state it in the thesis.

Follow-ups (each builds on your last answer)

  1. Prof: "Could you change your setup so that it would catch them?"
    You: "Partly. Instead of one fresh call per input, I'd call each admitted version many times in one long-lived process, say 100,000 calls from the same input distribution, and record memory with Python's tracemalloc module every thousand calls. In Python, typical leaks are a cache with no size limit or a module-level list that keeps growing."
  2. Prof: "Memory goes up and down with garbage collection. How do you tell a real trend from noise?"
    You: "I'd force a garbage collection before each reading, then use a trend test that doesn't assume normal noise, the Mann-Kendall test, with Sen's slope to estimate how fast memory grows. Garg and colleagues used Kendall-type trend tests with Sen's slope on aging data back in 1998, and because readings next to each other are correlated, there's also a modified Mann-Kendall test for that."
  3. Prof: "Say the slope is 2 kilobytes per call and the process has 512 megabytes to spare. When does it fail?"
    You: "512 megabytes is 524,288 kilobytes, so dividing by 2 gives 262,144 calls. If it serves 100 calls a second, that's about 2,600 seconds, roughly 44 minutes, which Garg and colleagues called the estimated time to exhaustion. So I'd restart well before that, and choosing exactly when, given what a restart costs, is your optimal rejuvenation problem."

Follow-ups (each builds on your last answer)

  1. Prof: "What would you expect 'adaptive' to mean in testing?"
    You: "That the next test depends on what earlier tests showed, instead of following a plan fixed in advance. A known example is adaptive random testing, which draws a few random candidates and runs the one farthest from the inputs already tried, so the tests spread out evenly."
  2. Prof: "Would adaptive random testing help with aging-related bugs?"
    You: "Probably not much on its own. It spreads inputs out because failures tend to cluster in regions of the input space, but an aging bug depends on how long and in what order the system has been used, not on where one input lies. So for aging, the adaptive part should decide the sequence, like which component to load next and for how long."
  3. Prof: "How would you show that adapting the sequence beats a fixed profile?"
    You: "I'd plant aging bugs, like a slow leak, in a few components of some programs, and run both policies many times, since both are random. Then I'd compare how often each one points to the right component within the same testing budget, and how long it takes when it does. I don't know yet how your paper measured it, so I'd like to read it."

Q44. If you had to learn a testing policy, how would you set it up?

I'd frame it as a learning loop. The state is what the tests have seen so far, the action is which component to exercise next, and the reward is a sign of aging, like memory growing. That's a general reinforcement learning idea, and I don't know if your paper does this.

Follow-ups (each builds on your last answer)

  1. Prof: "Memory growth comes slowly and with noise. What problem does that make for learning?"
    You: "The reward is delayed and noisy, so it's hard to tell which earlier action caused it, which is called the credit assignment problem. I'd measure the reward over blocks, for example the memory growth over a thousand calls after each choice, so that each choice gets its own signal."
  2. Prof: "Would you start with full reinforcement learning, then?"
    You: "No, I'd start simpler, with a multi-armed bandit: each arm is a component, pulling it runs one block of calls on it, and the reward is the memory growth in that block. That ignores the order of actions, but it's much easier to learn, and if order turns out to matter, I'd move to a full Markov decision process."
  3. Prof: "How would a bandit choose? Show me with numbers."
    You: "With UCB1, and rewards scaled between 0 and 1, I pick the arm with the highest mean plus the square root of 2 times the natural log of t, over n, where n is how often that arm was tried. After 12 blocks, say arm A has mean 0.5 from 10 tries and arm B has 0.3 from 2 tries. A's bonus is the square root of 2 log 12 over 10, about 0.70, so 1.20, and B's is the square root of 2 log 12 over 2, about 1.58, so 1.88. So I try B next, because two tries are too few to rule it out."
