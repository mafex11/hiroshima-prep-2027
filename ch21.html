Glossary: every term you may hear

When and how long: Look things up when needed.

What this file is: every technical term in your proposal, plus the terms Prof. Zheng, Prof. Okamura or the oral exam panel may use. Each term gets 1 to 3 plain sentences. Where it helps, the last sentence says how the term shows up in your own plan.

How to use it: read one section a day. Cover the definition with your hand, say it out loud, then check. The terms marked (must know) are the ones most likely to come up in the meeting on 2 Nov and in the oral exam.

Sources: the proposal and make_proposal.py; DOSSIER.md; the paper texts in review_papers/ (checked 30 Oct 2026); Eckhardt and Lee as NASA TM-86369. Paper facts named here were checked on the web on 30 Oct 2026 (Crossref, NASA NTRS, arXiv, Hugging Face, the AISQ site). Anything you have not read yourself is marked "(not read)". Do not cite those papers as if you had read them.

A. Reliability basics

Fault, error, failure (must know). A fault is the bug in the code. An error is the wrong internal state it causes when it runs. A failure is when the wrong result reaches the user, for example a wrong output on an input.

Reliability (must know). The probability that a system works without failure for a given time or a given number of uses. For a single function call, it is 1 minus the failure probability on that call.

Failure probability (must know). The chance that a program gives a wrong output on one input drawn from a stated input distribution. In your plan it is the share of failing inputs among 10,000 or more generated inputs per entry point.

Failure rate and hazard rate. The failure rate is how often failures happen per unit of time. The hazard rate h(t) is the chance of failing in the next moment, given no failure so far: h(t) = f(t) / (1 - F(t)).

MTTF, MTBF, MTTR. Mean time to failure, mean time between failures, and mean time to repair. For a repairable system, MTBF = MTTF + MTTR.

Availability. The share of time a system is up and working. In steady state it is MTTF / (MTTF + MTTR).

Dependability. The lab's umbrella word for trusting a system: reliability, availability, safety, security and maintainability together. The lab page says "dependable" unifies fault tolerance and fault avoidance.

Fault tolerance vs fault avoidance. Fault avoidance tries to stop faults getting in (good design, testing). Fault tolerance accepts some faults will get in and keeps the system working anyway, for example by voting over redundant versions.

Redundancy. Running more than one copy so that one failure does not stop the system. Hardware redundancy copies the same part; software needs different versions, because identical copies of a program have identical bugs.

Triple modular redundancy (TMR). Three copies and a 2-out-of-3 vote. With independent copies of reliability R, the system reliability is 3R² - 2R³.

Software aging and rejuvenation. Aging means software slowly gets worse while it runs, for example through memory leaks. Rejuvenation means restarting it on purpose before it fails. Prof. Zheng finds the restart timing that gives the highest availability.

Checkpointing. Saving the state of a running program now and then, so less work is lost after a failure. It is often studied together with rejuvenation.

B. N-version programming and coincident failure

N-version programming (NVP) (must know). Several teams build the same program independently from one specification, all versions run on each input, and a vote picks the output. Algirdas Avizienis described the approach (for example IEEE TSE, 1985, not read). It works only if the versions rarely fail on the same input.

Version (must know). One independently built program that implements the specification. In your plan, a version is one agent run's change that passes the pull request's tests.

Specification. The description every version is built from. In your plan it is the task text plus the context file, which is why a shared rule can cause shared failures.

Majority voting (must know). The system output is the answer most versions give. With 3 versions, a 2-out-of-3 vote is correct as long as at most one version is wrong.

2-out-of-3 vote failure. On an input where each version fails with chance θ, the vote fails with chance 3θ²(1 - θ) + θ³ = 3θ² - 2θ³. Your plan averages this over inputs: E[3θ² - 2θ³].

Coincident failure (must know). Two or more versions failing on the same input. Eckhardt and Lee call the related idea "coincident errors".

Common-mode failure. A failure that hits several redundant parts for the same reason, such as a shared design mistake. A buggy helper that every run is told to use would cause a common-mode failure.

Independence assumption (must know). The assumption that whether one version fails on an input tells you nothing about whether another does. If it held, two versions with failure probability p would both fail with probability p².

Diversity (design diversity) (must know). Differences between versions (different teams, languages, algorithms, tools) meant to make them fail on different inputs. The lab's paper [1] found that more diversity did not always mean more reliability.

Forced diversity. Deliberately making versions differ, for example by giving them different methods or tools. Littlewood and Miller studied this in theory. In your plan, changing the agent, model, temperature or file version between runs is forced diversity.

Intensity of coincident errors θ(x) (must know). Eckhardt and Lee's name for the share of all possible versions that fail on input x. In your plan, θ_s(x) is the chance that a run from setting s fails on input x.

Usage distribution (operational profile). How often each input occurs in real use. Eckhardt and Lee call it Q. A failure probability is always "under some input distribution", which is why your plan declares its distribution in advance.

Eckhardt-Lee model (must know). For two versions drawn at random, P(both fail) = E[θ(X)²] = p² + Var θ(X). So they fail independently only if θ is the same for every input, which is unrealistic because some inputs are harder (Theorem 2). They also showed that voting can be worse than one version when θ(x) > 0.5 on some inputs.

Littlewood-Miller model. An extension of Eckhardt and Lee (IEEE TSE 15(12), 1989) to versions built with different methods. With different methods A and B, P(both fail) = p_A p_B + Cov(θ_A, θ_B), and the covariance can even be negative, so diverse methods can do better than independence. You know it from its abstract only (no full text found), so do not cite it as read.

Knight and Leveson experiment (must know). In 1986, 27 versions of the "Launch Interceptor Program" were written independently at two universities and tested on one million inputs. Joint failures were far more common than independence predicts (IEEE TSE 12(1), 1986; a free PDF exists on the KTH site, read it before the exam if you can).

Launch Interceptor Program. The specification used by Knight and Leveson and repeated by Ron et al. [5]: 15 geometric conditions on input points that lead to a launch decision. Some conditions (like the smallest circle around three points) are known fault attractors.

Knight-Leveson K and z. K is the number of test inputs on which two or more versions fail. Under independence the expected K is T x Pm, where Pm = 1 - P0 - P1 comes from each version's failure rate, and z = (K - T Pm) / sqrt(T Pm (1 - Pm)). Ron et al. found K = 429 against 115.36 expected, z = 29.20.

realcompare. A function in the Knight and Leveson specification that compares two real numbers with a tolerance. Your output rule uses a float tolerance "like realcompare".

Pairwise score Z (Nogueira et al.). For two versions that fail F_i and F_j of T tests, the expected overlap under independence is F_i F_j / T (a hypergeometric count). Z is the observed overlap minus that, divided by its standard deviation.

Redundancy effectiveness. Nogueira et al.'s share of the gain independence would allow that majority voting really achieves. They found 0.43 for mixed triples and 0.27 when all three came from one model.

Acceptance test. A test a version must pass before it is accepted into the set. Knight and Leveson used one with 200 cases. Your acceptance test is the pull request's own tests.

Recovery block. Another fault-tolerance scheme: run a primary version, check the result with an acceptance test, and switch to a backup version if it fails. Not used in your plan, but it is the classic alternative to NVP.

C. Probability and statistics

Random variable, expectation, variance (must know). A random variable is a number that depends on chance. Its expectation E[X] is the long-run average, and its variance Var X = E[X²] - (E[X])² is the average squared distance from that mean. The Eckhardt-Lee formula is just this identity applied to θ.

Covariance and correlation. Covariance measures whether two random variables go up together. Correlation is covariance scaled to lie between -1 and 1.

Bernoulli and binomial distribution. A Bernoulli trial has two outcomes, fail with chance p or pass. The binomial gives the number of failures in k independent trials: mean kp, variance kp(1 - p).

Poisson distribution. Counts of rare events in a fixed window: P(N = n) = e^(-λ) λ^n / n!. Mean and variance are both λ.

Exponential distribution. The waiting time between events of a Poisson process, with mean 1/λ. It is memoryless: having waited does not change how much longer you will wait.

Beta distribution (must know). A flexible distribution for a number between 0 and 1, with two shape parameters a and b and mean a/(a + b). Beta(1, 1) is uniform, and with a and b below 1 it is U-shaped. Your plan uses it for θ, the chance a run fails on an input.

Beta-binomial distribution (must know). A binomial count where the success chance itself varies, following a Beta distribution. In your plan, it is the number of failing runs out of k on one input, when θ varies from input to input.

Intraclass correlation ρ (must know). For the beta-binomial, ρ = 1/(a + b + 1): the correlation between two runs' fail/pass results on the same input. ρ = 0 means independence and ρ = 1 means all runs always agree; P(two fail) = p² + ρ p(1 - p).

Overdispersion (must know). When counts vary more than a binomial (or Poisson) model allows. A beta-binomial count has variance kp(1 - p)[1 + (k - 1)ρ], larger than kp(1 - p) whenever ρ > 0.

Zero inflation. Many more zeros than the model expects, for example most inputs with no failing run at all. A zero-inflated model mixes "always zero" with the usual distribution, and you said the pilot will show whether you need it.

Likelihood and maximum likelihood (must know). The likelihood is the probability of the observed data, seen as a function of the parameters. Maximum likelihood picks the parameters that make the data most likely; usually you maximise the log-likelihood.

EM algorithm. A way to compute maximum likelihood when some data are missing or hidden: guess the hidden part (E step), maximise (M step), repeat. The likelihood never goes down, and pysrat uses EM for its NHPP models.

Bootstrap (must know). Resample your data with replacement many times, recompute the estimate each time, and use the spread as the uncertainty. In your plan you resample runs, not inputs, because the same runs meet every input.

Parametric bootstrap. Simulate new data from the fitted model instead of resampling the data, then refit. The lab (Dr. Jingchi Wu and others) uses it for intervals of NHPP models.

Confidence interval. A range built so that, over many repeats of the study, it contains the true value a stated share of the time, for example 95%. The percentile bootstrap interval takes the middle 95% of the bootstrap estimates.

Hypothesis test and p-value. You assume a null hypothesis (for example "no effect") and ask how surprising the data would be under it. The p-value is that probability; a small p-value is evidence against the null, not the size of an effect.

Statistical significance. Usually p < 0.05. Gloaguen's +2.4% (p = 0.21) was not significant, so it may be chance.

McNemar test. A test for paired yes/no outcomes, for example the same task with and without a rule, using only the pairs that disagree. Zhang et al. used it; their one significant rule had p = 0.016.

Fixed effect and random effect (must know). A fixed effect is something you set on purpose and want to measure, like the file version. A random effect lets each group, like each task, have its own baseline, because some tasks are harder; your RQ2 has task as a random effect.

Mixed effects (logistic) regression. A regression with both fixed and random effects. For pass/fail outcomes it uses the logistic link, for example failed out of inputs ~ file_version + (1 | task).

AIC. Akaike information criterion, 2k - 2 log L, where k is the number of parameters. Lower is better; it rewards fit and punishes extra parameters.

Cohen's kappa (must know). Agreement between two raters corrected for chance: κ = (p_o - p_e) / (1 - p_e). 1 is perfect agreement and 0 is what chance gives; you report it for the rule checker against your hand labels.

Hypergeometric distribution. Counts when you draw without replacement, like drawing cards. Nogueira's expected shared failures F_i F_j / T is the mean of a hypergeometric count.

Markov chain. A random process where the next state depends only on the current state. It was in your BCS301 course, and the lab uses Markov models for availability.

Monte Carlo and MCMC. Monte Carlo means estimating something by random simulation. MCMC (Markov chain Monte Carlo) moves step by step through random proposals; Guo et al.'s test generators [2] are MCMC-like.

Central limit theorem. The average of many independent values is close to normally distributed. It is why the Knight-Leveson z can be compared with a normal distribution.

D. Software reliability growth models

Software reliability growth model (SRGM) (must know). A model of how the number of faults found grows during testing, used to decide when to stop testing and how reliable the software is at release. Most of the lab's reliability papers are about SRGMs.

NHPP (non-homogeneous Poisson process) (must know). A counting process like a Poisson process, but the rate changes over time. N(t), the number of faults found by time t, is Poisson with mean m(t).

Mean value function m(t) and intensity λ(t) (must know). m(t) is the expected number of faults found by time t, and λ(t) = m′(t) is the rate at time t. Most finite-failure models write m(t) = ω F(t), where ω is the expected total number of faults and F is a detection-time distribution.

Goel-Okumoto model (must know). The exponential NHPP, m(t) = ω(1 - e^(-bt)) (Goel and Okumoto, IEEE Transactions on Reliability, 1979). Expected remaining faults at time t are ω e^(-bt).

Software reliability R(x | t). The chance of no failure in the next x time units after testing up to t: R(x | t) = exp(-[m(t + x) - m(t)]).

Finite-failure vs infinite-failure NHPP. In a finite-failure model, m(t) levels off at ω, because the code is fixed and has a fixed number of faults. In an infinite-failure model, such as the Musa-Okumoto logarithmic Poisson model, m(t) keeps growing.

Log-likelihood for time data. For fault times t_1 ... t_n observed up to T: log L = Σ log λ(t_i) - m(T). Maximising it gives the parameter estimates.

Time data vs group data. Time data are the exact times each fault was found. Group data are counts per interval, for example faults per week; pysrat handles both.

Hawkes process (self-exciting). A process where each event raises the chance of more events soon after: λ(t) = μ(t) + Σ φ(t - t_i) over past events. Qiu et al. [3] use it because fault detections cluster.

Infinite-server queue (M/G/∞) (must know). A queue where every arrival is served at once, so nobody waits, and each stays for a random time with distribution G. In your field model, faults "arrive" with each merged change and "leave" when they are found; Dohi, Osaki and Trivedi used this view in 2004 to unify finite and infinite fault NHPP models (title and abstract only).

Delay distribution G. In your field model, the distribution of the time from merge until a fault is found. pysrat supplies the families (exponential, gamma, log-normal and others).

Covariates and exp(β′z). Extra facts about each change (for example which agent wrote it) that scale its expected faults. ω_j = L_j exp(β′z_j) means bigger changes bring more faults, and each covariate multiplies the count by exp(β).

Cox proportional hazards model. A model where covariates multiply a baseline hazard: h(t | z) = h_0(t) exp(β′z). pysrat's metrics-based cloglog model becomes a Cox model with an offset.

Competing risks and Fine-Gray. Competing risks means more than one kind of event can end the follow-up, and only the first one counts. Xia and Miller [10] followed each line until it was changed by one kind of maintenance (for example a bug fix or a refactoring), and Fine-Gray regression models the chance of one kind while treating the others as competing events.

PMSE. Predictive mean squared error: how far predicted fault counts are from the real ones after the fitting window. Qiu et al. compare models with it.

pysrat (must know). Prof. Okamura's Python package for software reliability (MIT licence, on PyPI). It fits 12 NHPP models with EM in a scikit-learn style (fit, params_, aic_), and has metrics-based and PR-NHPP models; install it and run one example before you talk about it.

Rsrat, SRATS. The lab's R package and the older Excel tool for the same models.

Phase-type distribution. The time until a small Markov chain reaches its end state. It can approximate almost any positive distribution, and the lab has many papers on fitting it with EM.

Markov regenerative process (MRGP). A process that "starts fresh" at certain moments but may have non-exponential waits in between, like a fixed restart timer. Prof. Zheng works on its sensitivity and on phase expansion to solve it.

Stochastic Petri net. A graph model of states and timed transitions, used for availability and performance. Prof. Zheng used one for 5G handover (INFOCOM 2026) and one for rejuvenation with checkpointing (2021).

E. Testing

Test oracle (must know). Whatever tells you if an output is right. In your plan the oracle is the merged human code, compared under a fixed output rule.

Reference implementation. A version trusted to be right, used as the oracle. Ron et al. used a Python reference checked by 82 unit tests.

Differential testing (must know). Run two programs on the same inputs and flag any difference. Its blind spot: if both share the same bug, they agree and you see nothing.

Output equivalence rule. Your fixed rule for "same output": floats within a tolerance, the same exception class, and order ignored for unordered collections. It is decided before the results, so it cannot be tuned to them.

Fail-to-pass tests. A pull request's tests that fail on the code before the change and pass after it. They prove the task and act as your acceptance test.

Regression test. A test that checks old behaviour still works after a change.

Flaky test. A test that sometimes passes and sometimes fails on the same code, for example because of timing or randomness. It could admit or reject a run by luck, so a task's tests should be rerun on the merged code first.

Entry point. The function the PR's tests call. You send generated inputs to entry points because every admitted version must implement them.

Type hints. Python annotations like price: float. Your input generator reads them to know what kind of value to build.

Random testing (RT). Inputs drawn at random from a distribution. It gives an honest failure probability, but it rarely hits exact boundary values.

Adaptive random testing (ART). Random testing that spreads inputs out over the input space. It was a baseline in [2].

Property-based testing. Generating many inputs automatically and checking a property for each. The Python library Hypothesis can build inputs from type hints; your differential test is a property-based test whose property is "same output as the merged code".

Equivalence partitioning. Splitting inputs into groups that should behave the same, then testing one value from each. In [2] the partitions are defined by output categories.

Boundary value analysis (testing) (must know). Testing the edges of each partition, where off-by-one bugs live, for example percent = 100 when the rule is "0 to 100".

Boundary point. A pair of inputs one minimal step apart that fall in different partitions. Guo et al. [2] use boundary points to compute BCD.

Boundary coverage distance (BCD) (must know). From Guo, Okamura and Dohi [2]: how far a test set is from covering every boundary, measured in minimal operations. The generator moves test inputs to make BCD smaller.

Minimal operation. The smallest change to an input, like plus or minus 1 for an integer. For strings and lists, which [2] leaves open, you plan to try one-element edits.

Path-based vs output-based boundary. An output-based boundary separates inputs with different output categories (the definition in [2]). A path-based boundary comes from a branch condition in the code; [2] notes in Remark 2 that the two can differ.

Concolic / symbolic testing (KLEE). Running a program with symbolic inputs to find inputs that reach each path. KLEE was a baseline in [2] and made only one test case for miniSAT.

Mutation testing, mutant (must know). Planting a small fault in a copy of the code (a mutant) to see if the tests notice. It measures how good a test set is, not how good the code is.

Kill rate (mutation score). The share of mutants a test set kills. In [2] a mutant is killed if some input takes a different execution path; you also report a stricter "different output" rule.

Mutation operators. Standard ways to plant a fault: ROR (relational operator, < to <=), AOR (arithmetic operator), LOR (logical operator), SVR (scalar variable replacement) and OBOB (off-by-one). [2] used these five.

Code coverage, branch coverage. Which lines or branches the tests ran. coverage.py measures it for Python; Gcov does it for C, as in [2].

F. Agents, models and context files

Large language model (LLM). A model trained on a lot of text that predicts the next token. It can write code and follow instructions.

Token and context window. A token is a piece of a word the model reads. The context window is how many tokens the model can see at once; your BrandMemory bug was a section cut by a length limit before it reached the model.

Coding agent (must know). An LLM in a loop with tools: it reads files, edits them, runs commands and tests, and repeats until it thinks it is done. Claude Code and Codex are coding agents.

Harness (scaffold) (must know). Everything around the model: the tools, the prompt, the loop and what context it sees. Model plus harness = agent, and Ron et al. call Claude Code, Codex and the others "agent harnesses".

Claude Code. Anthropic's command-line coding agent. It reads CLAUDE.md at the start of a session.

Codex. OpenAI's command-line coding agent. It reads AGENTS.md.

Context file, CLAUDE.md, AGENTS.md (must know). A Markdown file in the repository that tells an agent about the project and its rules, such as how to run tests. Claude Code reads CLAUDE.md and Codex reads AGENTS.md; your plan gives both agents the same text under the right name.

Rule. One instruction in a context file, like "Round money with round_cents()". Your unit of study is one rule.

Neutral text. The sentence that replaces a rule in your second file version: about the same length, but no instruction. It separates the rule's content from just having more text.

Compliance. Whether the agent's code follows a rule. In your plan it is only a manipulation check, not a research question.

Manipulation check. A check that your experimental change really changed behaviour. If replacing a rule does not change what the agents write, a "no effect" result would mean nothing.

Rule checker. A small script that decides, from the diff, whether a run followed a rule, for example by finding a call to a named helper in the added lines. It is kept only if it agrees with your hand labels on at least 90% of 20 or more cases.

Temperature (must know). A setting that controls how random the model's word choices are: 0 is close to always picking the most likely token, higher values give more variety. The lab's paper [1] used it as a way to get diverse versions, and your harness runs two temperatures.

Top-p sampling. The model samples only from the smallest set of tokens whose probabilities add up to p. Gloaguen ran Qwen3-30B-Coder at temperature 0.7 with top-p 0.8.

Seed and non-determinism. A seed would make random choices repeatable. Agents give different code on the same input, which is why you run each setting 10 times.

Open-weight model. A model whose weights are published, so you can run it yourself. Your harness uses one so you control the prompt and the temperature.

Qwen3-30B-Coder. The open-weight coding model in Gloaguen et al. and in your harness; its Hugging Face name is Qwen3-Coder-30B-A3B-Instruct. It is a mixture-of-experts model with 30.5B parameters in total and about 3.3B active per token.

Conversation history reuse. One of the two diversity strategies in the lab's paper [1], with temperature. From the abstract you cannot tell exactly how it was done; a likely reading is generating each new version in the same chat so the model sees its earlier ones [CONFIRM when you read [1]].

Headless mode. Running an agent from a script without the interactive screen, for example claude -p or codex exec. You need it to run 820 runs the same way.

Pinned version. A fixed version of the agent software and model. Every run uses the same one, so results can be repeated.

Container (Docker). A clean, isolated copy of the environment for each run. Nothing from one run leaks into the next.

pass@k (must know). The chance that at least one of k samples passes the tests. It assumes something can tell which sample passed; voting has no such oracle, which is why your plan models the vote instead.

pass@1. The chance a single sample passes; with n samples of which c pass, the estimate is c/n. For pass@k, Chen et al. 2021 (the Codex paper, not read) give the unbiased estimate 1 - C(n - c, k) / C(n, k).

SWE-bench, SWE-bench Verified, SWE-bench Lite. Benchmarks of real GitHub issues in Python repositories, solved when hidden tests pass. Zhang et al. used SWE-bench Verified (500 tasks); Gloaguen et al. used the Lite split (300 tasks) next to their own 138.

CTXBench / agentbench. Gloaguen et al.'s 138 tasks from 12 Python repositories with developer-written context files. It is public on Hugging Face as eth-sri/agentbench, with Docker images and test commands.

AIDev. A dataset of pull requests made by AI coding agents on GitHub (Li, Zhang and Hassan, MSR 2026). The paper version has 932,791 agent PRs from five agents, collected up to 1 Aug 2025; you would use it only for the field study.

Pull request, merge, base commit, diff. A pull request proposes a change; merging accepts it into the main code. The base commit is the code just before it, and the diff is the exact lines added and removed.

Training cutoff and contamination. The training cutoff is the date after which the model saw no data. Contamination means the model may have seen the answer during training, which is why you prefer PRs merged after the cutoff.

Leave-one-out (ablation). Remove one part, keep everything else, and see what changes. Zhang et al. did it for 18 rules; your RQ2 does it for one real rule per task, with neutral text in its place.

AST (abstract syntax tree). The tree structure of a program that a parser builds. Some studies measure how different two versions are by comparing their ASTs.

CodeBLEU. A similarity score for code that mixes word overlap, syntax-tree matches and data-flow matches. Nogueira et al. used it to measure how different versions look.

G. Study design words

Setting (must know). One combination of agent, model, temperature and file version, for example "Claude Code with the original file". Each setting gets 10 runs per task.

Run. One execution of an agent on one task in a fresh container. It may or may not become a version.

Admitted version. A run whose change passes the pull request's tests. Only admitted versions go on to the 10,000 generated inputs.

Screening. A quick first pass to drop useless tasks. You run about 20 candidate tasks 3 times per agent and drop those an agent never solves.

Pilot. A small first study to check cost, time and whether the method works, before the main runs. It is in the first half of Year 1.

Declared input distribution. The input distribution you write down before testing. A failure probability is only meaningful relative to it.

Construct validity. Do you measure what you say you measure? For example, does "differs from the merged code" really mean "wrong"; your hand check of 20 disagreements per task is there for this.

Internal validity. Is the effect really caused by what you changed? Changing only one rule, pinning versions and fresh containers protect it.

External validity (generalisation). Do the results hold beyond your sample? Ten Python tasks and about 5 rules limit it, and you say so.

Effect size. How big a difference is, not just whether it exists. ρ is an effect size; a p-value is not.

H. Venues, programs and places

ISSRE. The IEEE International Symposium on Software Reliability Engineering, the main venue for this field.

AISQ. The International Workshop on Advanced Intelligent Software Applications, held with ISSRE. Prof. Dohi co-chaired it in 2025, and the 2026 edition (the 3rd) mentions "prompt engineering and harness engineering" on its home page.

QRS. The IEEE International Conference on Software Quality, Reliability and Security. Prof. Zheng's group published there in 2025.

Software Quality Journal (SQJ). A Springer journal. Guo, Okamura and Dohi's BCD paper [2] is there.

SFPVV and LNCS. SFPVV is the International Symposium on Software Fault Prevention, Verification, and Validation; the 2025 edition was in Shanghai. Its proceedings are in Springer's Lecture Notes in Computer Science (LNCS 16356), co-edited by Prof. Okamura, and contain the lab's N-version paper [1].

APSEC. The Asia-Pacific Software Engineering Conference. Dohi, Osaki and Trivedi's infinite-server queue paper [12] appeared there in 2004.

IEEE TSE. IEEE Transactions on Software Engineering. Eckhardt and Lee (1985), Knight and Leveson (1986) and Littlewood and Miller (1989) are all in TSE.

MSR. The Mining Software Repositories conference. The AIDev paper [7] is MSR 2026.

arXiv. A preprint server. Ron et al., Nogueira et al., Gloaguen et al., Zhang et al. and Xia and Miller are arXiv preprints, so they are not peer reviewed yet.

Dependable Systems Laboratory (REL). Prof. Dohi, Prof. Okamura, Assoc. Prof. Zheng and Dr. Jingchi Wu, in the Graduate School of Advanced Science and Engineering, Higashi-Hiroshima campus. Its page says each technique is paired with "conventional probabilistic evaluation".

Informatics and Data Science Program. The master's program you are applying to, in the Graduate School of Advanced Science and Engineering. You apply through the Special Selection for International Students living outside Japan, April 2027 entry.

UCARO. The online system for the application: account, form, photo and the 30,000 yen fee, open 2 to 13 Nov 2026.

Consent Form. The form your prospective supervisor signs to confirm he will supervise you. It is document 8 in the guideline, and Prof. Zheng is the one who signs it.

Support Office. The Support Office for the fields of Engineering, which receives your documents (kou-gaku-daigakuin@office.hiroshima-u.ac.jp). It already knows Prof. Zheng agreed.

Oral examination. Online by Teams or Zoom on one day between 24 Nov and 2 Dec 2026. It tests "academic abilities regarding knowledge in the specialized field, application capability, and problem-solving abilities", and it and your documents are each graded A, B or C.

JST. Here, Japan Standard Time, which is IST plus 3 hours 30 minutes. (JST is also the Japan Science and Technology Agency, which funded [2] in part and funds the JST SPRING doctoral grant in [3].)
